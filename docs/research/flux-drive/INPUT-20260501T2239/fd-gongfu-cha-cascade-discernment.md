Verdict: risky

### Summary
The Track B6 proposal has a severe circular calibration problem: the same model family (GPT-5.5 / Opus) is both the judge that fills missing labels in bead .19.3 and implicitly the reference model behind the interspect calibration data that anchors the ≥0.85 holdout target. A cha shi would recognize this immediately — the apprentice is being graded by his own teacher pretending to be an external examiner. The ≥90% agreement success criterion in the epic is meaningless if the "calibrated baseline" was itself produced by the judge's family. Additionally, the eval design judges the router on single-call metrics (per-call accuracy, pass@1) without aggregating across a full sprint — a router that always slightly demotes C3 calls to C2 will pass every individual eval while silently drifting the sprint-level quality distribution. Finally, the by-time holdout window (last 2 weeks, bead .19.2) straddles the Qwen3.6-35B-A3B promotion at routing.yaml line 733 (updated 2026-04-29), meaning the holdout ground truth was generated under a routing regime different from the one the router trains against.

### Issues Found

GC-1. P0: Circular calibration — GPT-5.5/Opus anchors both the judge labels and the holdout target.

Bead .19.3 specifies: "Judge augmentation: where dataset lacks ground truth, prompt GPT-5.5 with `(task, model_options) → 'which tier?'` to fill gaps." Bead .19.2 draws training data from `.clavain/interspect/routing-calibration.json` — the interspect calibration data that records hit rates per agent/model. The interspect verdicts are themselves generated by flux-drive agents running at Sonnet/Opus tiers (the same model family as the judge). The epic's success criterion states "≥ 90% agreement with calibrated baseline on holdout" — but the calibrated baseline is derived from pass/fail outcomes where Opus/Sonnet was both the executing model and the judge of quality.

Concrete failure scenario: A router trained to mimic "what Opus would have recommended" and evaluated for agreement with "what Opus actually did" is not detecting an independent signal — it is learning to imitate the evaluator. The ≥0.85 accuracy target becomes trivially achievable for a model that collapses to "use the same model Opus would have used," which defeats the entire purpose of routing.

Fix: Separate the judge for label augmentation (bead .19.3) from the source of the calibrated baseline. Use a different model family (e.g., Gemini 2.5 or a local Qwen3.6-35B consensus) as the augmentation judge, OR measure holdout agreement against observed pass@1 outcomes (actual task results) rather than against Opus's routing recommendations.

GC-2. P0: The ≥90% success criterion in the epic body is anchored to the same judge family.

The epic success criterion reads: "≥ 90% agreement with calibrated baseline on holdout (else it regresses B3)." The B3 calibration (`.clavain/interspect/routing-calibration.json`) was constructed from interspect verdicts where the executing model at Sonnet/Opus tier was also the implicit quality judge (did the task pass?). If the pass/fail signal comes from a Sonnet/Opus run, and the augmentation judge is also Sonnet/Opus (bead .19.3), the model is calibrating against itself. This is the exact master-apprentice contamination pattern.

Concrete failure scenario: The router achieves ≥90% agreement in holdout, ships to shadow mode, and then underperforms on tasks that require genuine tier discrimination — because it learned to match the teacher's posterior, not the objective task-difficulty signal. This won't be caught until enforce mode, at which point rollback requires deleting the calibration file and re-running a sprint.

Fix: Specify in bead .19.3 that the augmentation judge must come from a different provider than the B3 calibration source. Add a gate to bead .19.4: "holdout agreement is measured against observed downstream pass@1, not against the B3 calibrated model's prior."

GC-3. P1: Eval harness reports per-call accuracy and pass@1 with no sprint-aggregate regret metric.

Bead .19.4 specifies five metrics: router accuracy, downstream pass@1, latency, cost proxy, routing distribution. None of these aggregate across a full sprint trajectory. A router with per-call accuracy of 91% that is systematically biased toward demoting C3 calls to C2 (saving ~1 cloud round trip per call) will show a healthy accuracy score while slowly degrading the quality of C3 tasks over the course of a sprint (hundreds of calls). The cumulative regret is invisible in per-call metrics.

Concrete failure scenario: Router ships to enforce mode. Over the course of a 6-hour sprint, 40% of C3 tasks get routed to C2 (local Qwen3.6-35B-A3B instead of cloud). Each individual misroute passes pass@1 on the first attempt but produces slightly lower quality outputs that require follow-up reviewer agents (fd-correctness, fd-quality) to catch. Sprint-level throughput degrades by ~15% but no single per-call metric ever fires.

Fix: Add a required metric to bead .19.4's eval matrix: `sprint_regret = Σ(oracle_quality - router_quality) / sprint_length` across the replayed-bead-history workload. Gate shadow → enforce on sprint_regret < 5% of baseline.

GC-4. P1: By-time holdout straddles the 2026-04-29 routing regime change.

Bead .19.2 specifies: "Holdout split is by-time (last 2 weeks) not random." The routing.yaml (line 733) was updated 2026-04-29 to promote C2 from Qwen3.5-9B to Qwen3.6-35B-A3B. If "last 2 weeks" extends before 2026-04-29, the holdout contains examples where C2 tasks were routed to Qwen3.5-9B — a lower-quality model. The router trained on pre-cutoff data will have learned routing decisions appropriate for the old model mapping, then be evaluated on holdout data where the correct answer changed.

Concrete failure scenario: Router learns "C2 tasks should go to local:qwen3.5-9b-4bit." Holdout contains post-2026-04-29 examples where the oracle would say "local:qwen3.6-35b-a3b-4bit." Router accuracy looks artificially low on holdout (true regime mismatch, not router failure) leading to a failed gate and wasted iteration — or artificially high if the pre-cutoff period dominates the holdout window.

Fix: In bead .19.2 "Done when" criteria, add: "Holdout split boundary must align with a stable routing-yaml snapshot; document the routing.yaml git hash at the holdout boundary and exclude examples from the 3 days before/after any routing.yaml change."

GC-5. P2: Training corpus mixes routing regimes without tagging them.

The bead .19.2 sources include "Sprint logs in `.clavain/` and session JSONLs in `~/.claude/projects/`" spanning all historical sprints. These sessions were run under different versions of routing.yaml (e.g., before and after B3 calibration enforce on 2026-04-01, before and after B4 delegation enforce, before and after C2 model change). The proposal does not require tagging each training example with a `routing_regime_version`. Without this, confusion matrix analysis cannot distinguish "router wrong about task difficulty" from "router trained on outdated routing scheme."

This is P2 rather than P0/P1 because it affects debuggability rather than immediate launch safety, but it will make the inevitable first confusion investigation expensive.

GC-6. P2: Missing model-availability feature (the "water" in vessel-leaf-water).

Bead .19.1's input feature candidates are: `(prompt text, agent_name, phase, file_count, prior_calibration_score)`. None of these capture which local models were available at inference time. If the microrouter is deployed while B5 local_models is in shadow mode (current state per routing.yaml line 728), a routing decision to "local:qwen3.6-35b-a3b-4bit" will fall through to cloud — the router is deciding based on features that don't include the execution environment state. When B5 transitions from shadow to enforce, the router's behavior changes without retraining.

### Improvements

GC-I1. Sprint-aggregate regret as primary metric — add `sprint_regret` computation to bead .19.4's eval matrix. Tie shadow → enforce gate to `sprint_regret < 5%` in addition to existing gates.

GC-I2. Routing-regime versioning in dataset — in bead .19.2, add `routing_yaml_hash` and `b5_mode` fields to each training tuple so per-regime model analysis is possible during bead .19.4 investigation.

GC-I3. Aftertaste channel — in bead .19.4, pair each eval run with a 24-hour lookback: did any task that was initially passed by the router-selected model get re-opened or receive a follow-up correctness failure? This is the hui gan signal — first-pass pass@1 is not the full taste.

## Findings

### dispatch-log-does-not-exist-yet
- **Severity:** P0
- **Where:** §2 table row 5 ("Sprint v2 artifact bus... OPEN") and §3.3 ("Extend the EXISTING `/clavain:work` + `/flux-review` dispatch log (already records wall-time, task-sum, agent-count)"); bead `sylveste-4b5.8` description repeats the same "already records" claim verbatim
- **What:** Grepped the actual command implementations. `os/Clavain/commands/work.md` has no dispatch-log writer (only a generic commit-cadence note at line 96). `interverse/interflux` has no `dispatch_log`/`DispatchLog` symbol anywhere in its Go sources. The only concrete `dispatch_log` SQLite table in the entire monorepo is defined in `docs/plans/2026-03-12-mycroft-fleet-orchestrator-v01.md` (Step 1, "SQLite schema... dispatch_log, tier_state, tier_transitions, recovery_log tables") and implemented under `apps/Autarch/internal/mycroft/`.
- **Evidence:** `grep -rln "dispatch_log" --include=*.go --include=*.md` across the repo returns zero hits in `work.md` or `interflux/`; the only Go-side dispatch/tier/scheduler code lives under `apps/Autarch/internal/mycroft/{patrol,scheduler,tier,spawn}`.
- **Suggestion:** Correct §3.3's premise before it reaches a charter: either (a) Rimsky's v1 telemetry work is "create a dispatch log for `/clavain:work`+`/flux-review`" (new work, not an extension — changes v1's size estimate), or (b) Rimsky should write conflict-rate/merge-resolution-time into Mycroft's *existing* `dispatch_log` table, which reframes Q2 from "different layer" to "Rimsky is a producer into Mycroft's telemetry store" — a much tighter coupling than §5 Q2's three options contemplate. This is a decision-procedure input for Q1's sibling question (Q2) that the brief currently gets backwards by assuming infrastructure that isn't there.

### q1-sequencing-claim-inverted-by-priority
- **Severity:** P1
- **Where:** §5 Q1 ("lbkd is OPEN and unstarted — the answer determines sequencing"); §6 collision map lists bead priorities: `4b5.7`/`4b5.8` unspecified in the map but confirmed P2 live, `lbkd` confirmed P3 live
- **What:** The brief treats Q1 as an open sequencing gate with real stakes, but never surfaces that lbkd already sits at P3 — one full priority tier below Rimsky's own substance beads (4b5.7, 4b5.8 are P2) and two below the P1 epic. In this codebase's beads convention, priority already encodes "does this block the parent" in practice (P1 epics don't typically wait on P3 children unless a dependency edge says so) — and the live dependency graph on `sylveste-3kol` lists only 4b5.7/4b5.8/4b5.17 as blockers, NOT lbkd. lbkd is not a declared dependency of the epic at all.
- **Evidence:** `sylveste-3kol`'s `dependencies` array in the jsonl contains exactly three `depends_on_id` entries (4b5.17, 4b5.7, 4b5.8); `lbkd` does not appear. `sylveste-lbkd`'s own record shows `"priority":3`, `"dependency_count":0,"dependent_count":0"` — nothing depends on it, it depends on nothing.
- **Suggestion:** The live graph already answers Q1 at the metadata level: lbkd is orthogonal (no dependency edge either direction) and low-priority. This doesn't resolve the *substantive* question (should it be a dependency, or subsumed) but it does mean the brief's framing of lbkd as a live sequencing risk needing melange's attention is overstated relative to what's actually wired in beads. Recommend the Q1 write-up state the dependency-graph finding explicitly ("no edge exists; if the substantive answer is (a) dependency, an edge must be added") rather than leaving it implicit.

### mycroft-litmus-test-untested-against-shipped-code
- **Severity:** P1
- **Where:** §5 Q2 ("Mycroft already does fleet monitor + T0/T1 suggest/approve dispatch across sessions... Do not build a second fleet orchestrator by accident"); §2 table cites only the plan doc `docs/plans/2026-03-12-mycroft-fleet-orchestrator-v01.md`
- **What:** Mycroft is not just planned, it is substantially built: `apps/Autarch/internal/mycroft/` contains `briefing/`, `patrol/`, `scheduler/`, `spawn/`, `tier/`, `escalate/`, `db.go`, `types.go`, plus test files for each — matching essentially all of Steps 1-8 in the plan (scaffold, registry, patrol loop, failure detection, selector, tier FSM, dispatch execution, escalation). The brief's Q2 litmus test ("Rimsky = within-goal task fan-out; Mycroft = cross-session fleet coordination") is asserted against a plan doc, not validated against what the shipped `scheduler/selector.go` (priority-first bead ranking) and `scheduler/conflict.go` (pre-dispatch interlock conflict check) already do — which look structurally identical to Rimsky's §3 constraint 2 ("intra-repo fan-out requires... interlock dry-run BEFORE spawning").
- **Evidence:** `ls apps/Autarch/internal/mycroft/` shows the full directory tree; plan Step 5 names `scheduler/conflict.go` as "Pre-dispatch interlock conflict check" — the same mechanism Q5 asks Rimsky to mandate.
- **Suggestion:** Before writing the Q2 bead verdict, diff Rimsky's proposed pre-spawn conflict check (Q5: intermap change_impact + interlock dry-run) against Mycroft's already-shipped `scheduler/conflict.go` pre-dispatch check. If they're the same mechanism at a different call site (within-goal fan-out vs. cross-session dispatch), that's evidence for "Rimsky consumes/calls Mycroft's conflict-check code" (Q2 option c), not merely "different layer" (option a) — a materially different implementation and ownership answer.

### q1-three-way-framing-omits-a-real-fourth-answer
- **Severity:** P2
- **Where:** §5 Q1 options (a) dependency / (b) subsumed / (c) orthogonal
- **What:** `docs/plans/2026-03-19-sprint-v2-artifact-bus.md` describes lbkd's actual problem narrowly: `set-artifact`/`get-artifact` in `clavain-cli` silently fail without an active Intercore run (`resolveRunID()` failure), fixed by a `bd set-state` fallback. That's a fix to an existing lifecycle-artifact command, not a new channel Rimsky's flat fan-out would need — Rimsky's fan-out (§1) is explicitly *not* a sprint-lifecycle system, it's parallel task dispatch. None of Q1's three options say "lbkd solves a problem Rimsky v1 doesn't have yet because v1 has no inter-stage handoff at all (flat fan-out, single stage)."
- **Evidence:** lbkd plan's own scope line: "Task 5: Pilot — wire artifact bus into strategy.md" — a single-command pilot, unrelated to N-parallel fan-out coordination.
- **Suggestion:** Add a fourth framing to Q1's decision procedure: "does v1's flat, single-stage fan-out have any inter-stage handoff need at all?" If not (which the brief's own §3 constraint 1 — flat depth-1, no recursion — suggests), Q1 is moot for v1 by construction, and the real question is deferred to whatever v2 looks like (matches the fd-scope-governance lens's Q6 concern, noted here only because it changes how Q1 should be *phrased*, not how it should be governed).

## Verdict
The brief's two headline subsumption questions (Q1, Q2) are well-posed in the abstract but under-verified against the live repo: the epic's "empty description" premise is already false, lbkd carries no dependency edge and sits at P3 (the graph already leans "orthogonal"), and Mycroft is materially shipped code with a pre-dispatch conflict checker that looks like Rimsky's own Q5 mechanism — not just a plan doc to layer-differentiate against. The most load-bearing gap is the phantom "existing dispatch log" (§3.3): Rimsky's v1 telemetry plan assumes infrastructure that doesn't exist in `/clavain:work`/`/flux-review`, and the only real dispatch_log belongs to Mycroft — which reframes Q2 from a layering question into a build-vs-integrate decision that should be resolved before any bead verdict is written.

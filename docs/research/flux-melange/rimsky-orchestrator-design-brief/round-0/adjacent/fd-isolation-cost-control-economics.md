## Findings

### q3-cost-figure-not-in-cited-contract
- **Severity:** P0
- **Where:** §5 Q3 ("worktree setup itself has cost (contract notes ~200-500ms + disk per worktree)"), citing `docs/guide-worktree-first-coordination.md`
- **What:** Read the full contract doc. It discusses two layers (isolation vs. coordination), `worktree.baseRef`, `.worktreeinclude`, and the nested-repo sharp edge — but contains zero numeric timing or disk-cost figures. The only cost-adjacent line is a retirement note: "`core/intermute/scripts/worktree-setup.sh` hand-rolls `git worktree add` plus manual copies... is slated for retirement." No "~200-500ms" string, nor any millisecond figure, appears anywhere in the file.
- **Evidence:** `grep -n "ms\|cost\|second\|disk\|setup"` against the full contract text returns only the `worktree-setup.sh` retirement line (§1) and a table-of-contents mention (§4 header) — no cost claim.
- **Suggestion:** Before Q3's crossover question can be answered even qualitatively, the brief needs to either (a) find the real source of the "~200-500ms + disk" figure if it exists elsewhere (possibly a different doc or a verbal estimate that got attributed to the contract in error), or (b) mark it as an unmeasured placeholder and add a measurement task ("time `git worktree add` cold + warm on zklw and Clavain, N=10 each") as an explicit precondition to any crossover-width decision. Right now Q3 is being stress-tested against a number that doesn't exist in its cited source — the crossover computation has a fabricated left-hand side.

### telemetry-source-doesnt-exist-so-signal-cant-accrue
- **Severity:** P0
- **Where:** §3 constraint 3 / bead `4b5.8` ("Extend the EXISTING `/clavain:work` + `/flux-review` dispatch log... Ship the instrument, not the numbers. The dynamic kill-rule controller... DEFERRED... GATED on the telemetry returning a non-trivial conflict rate"); §5 Q4
- **What:** Per the adjacent-lens grounding, no dispatch log currently exists for `/clavain:work` or `/flux-review` to "extend" — the only real `dispatch_log` is Mycroft's SQLite table. This means Q4's entire falsifiability chain (telemetry → conflict rate → controller-build decision) has an un-built first link. The brief frames this purely as a measurement-bias risk (interlock suppresses conflicts to ~zero) but misses the more basic risk: the clock hasn't started at all, because the instrument itself is unbuilt, and "instrument, not numbers" in §3.3 undersells that this is new construction, not an extension.
- **Evidence:** Same grep evidence as the sibling topology finding — no `dispatch_log`/`DispatchLog` symbol in `work.md` or `interflux/` Go sources.
- **Suggestion:** Q4's "evidence that flips the gate" section needs an explicit precondition: name the telemetry-instrument bead as a hard prerequisite with its own estimated ship date, and state the earliest possible date the conflict-rate signal could exist (instrument ship date + N fan-outs at width ≥ some minimum, per the near-miss/actual-conflict split the severity calibration for this lens already implies). Without that, "GATED on telemetry" reads as already-satisfied infrastructure when it's actually a new-build dependency of the gate.

### q5-check-cost-has-no-comparator-because-mycroft-already-pays-it
- **Severity:** P1
- **Where:** §5 Q5 ("Is that check cheap enough to run unconditionally, or does it need its own gate... Could the check itself become the bottleneck it's meant to prevent?"); cf. Mycroft plan Step 5 `scheduler/conflict.go` ("Pre-dispatch conflict check: Query interlock for file scope overlap before selecting")
- **What:** Mycroft already runs an interlock-based pre-dispatch conflict check in its selector step, on every patrol cycle (30-60s), across the fleet. That's a live-adjacent cost data point Rimsky's Q5 could use directly instead of treating the check's cost as unknown — Mycroft's `patrol.go` even has a documented per-source timeout budget (5s) and staleness-gating fallback specifically because MCP round-trips were anticipated to be slow. This prior art directly answers "does an interlock round-trip in a hot path need its own gate" — Mycroft's answer was yes (staleness gate + timeout), and Rimsky's Q5 doesn't cite it.
- **Evidence:** Mycroft plan §Step 3: "Timeout per source (5s), continue with stale data" listed in the Risk Register as mitigation for "MCP tool calls slow down patrol cycle."
- **Suggestion:** Pull Mycroft's timeout-and-staleness-gate pattern into Q5's answer directly: propose the same shape (timeout budget on the intermap+interlock pre-spawn check, degrade to a conservative default — e.g., serialize instead of parallelize — on timeout, don't block indefinitely) rather than treating this as a novel unknown. This also gives Q5 a concrete N-tasks-threshold analog: Mycroft's cycle cadence (30-60s) implies a rough tolerance for how much per-check latency is acceptable before it eats the loop's own budget — worth measuring against Rimsky's expected fan-out latency budget.

### toctou-461-threshold-imported-without-provenance-check
- **Severity:** P2
- **Where:** §3 constraint 3 ("operationalizing the orphaned `toctou-analysis.md:461` recommendation ('>1% conflict rate → escalate')"); `docs/research/toctou-analysis.md` lines 458-465 (section "C) Mutation injection (fault injection for TOCTOU)" under "7. Validation/Test Harness")
- **What:** Read the cited line in context. `toctou-analysis.md` is a design document for a *hypothetical* Go concurrency-simulation and mutation-injection test harness for a kernel-logged merge-event system (HEAD advances via kernel-logged merge events, gate binding, lease locks) — it is not a report of a measured conflict rate from Sylveste's actual interlock usage. The ">1% conflict rate → escalate" line appears to be a proposed test-harness assertion threshold for a different, more elaborate conflict-detection system than interlock's current file-reservation model, not an empirically derived number from production telemetry.
- **Evidence:** Section 7 of `toctou-analysis.md` (lines 440-474) is explicitly a "Validation/Test Harness" spec with subsections for invariants, a Go concurrency-simulation harness, mutation injection, property-based tests, and telemetry — read end-to-end, there's no separate empirical study establishing 1% as measured; it reads as a proposed harness assertion.
- **Suggestion:** Before 4b5.8 treats 1% as the operative escalation threshold, verify (a) whether toctou-analysis.md's harness was ever built and run, and if so what conflict rate it actually measured, or (b) if it's a design-time placeholder, say so explicitly in Rimsky's telemetry spec rather than presenting it as a validated recommendation being "operationalized." This affects Q4's evidence-flip criteria directly: if 1% is itself unvalidated, gating the controller-build decision on crossing it inherits that same unvalidated status.

## Verdict
Both of Q3 and Q4's numeric anchors fail grounding checks: the worktree cost figure Q3 stress-tests doesn't exist in its cited contract, and Q4's telemetry precondition assumes an already-built dispatch log that isn't there — meaning the measurement clock for the controller-build decision cannot even start under the brief's current framing. Q5 has a real, uncited comparator already in production-adjacent code (Mycroft's timeout+staleness-gated pre-dispatch check) that should directly inform Rimsky's answer instead of treating the check's cost as an open unknown.

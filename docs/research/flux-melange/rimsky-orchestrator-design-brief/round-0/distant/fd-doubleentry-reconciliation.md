## Findings

### toctou-citation-posted-to-wrong-account
- **Severity:** P1
- **Where:** §3.3, "operationalizing the orphaned `toctou-analysis.md:461` recommendation (`>1% conflict rate → escalate`)"
- **What:** I read `docs/research/toctou-analysis.md` at line 461 and the surrounding block (lines 400-440): it is a "30/60/90 Roadmap" section about hermetic tool execution and TLA+ formalization — no ">1% conflict rate" text anywhere in that 500-line file (confirmed by full-file grep for "1%"). The actual quote — "If conflicts occur at >1% of multi-agent sessions, escalate to Phase 3" — lives in a **different file**: `docs/research/research-toctou-in-multi-agent-coding.md:461`. Same line number, different file, near-identical filename. This is a classic double-posting error: the same transaction recorded against the wrong account (file), and it traces back further than the brief — bead `Sylveste-4b5.8`'s own description contains the identical wrong citation, so the brief faithfully propagated a pre-existing broken entry rather than introducing a new one.
- **Evidence:** `grep -n "1%" docs/research/toctou-analysis.md` → no matches. `grep -n ">1%" docs/research/research-toctou-in-multi-agent-coding.md` → line 461: `**Recommended approach:** Implement Phase 1 with telemetry to measure our actual conflict rate. If conflicts occur at >1% of multi-agent sessions, escalate to Phase 3. If they don't, stop at Phase 1.` Bead `Sylveste-4b5.8` description field contains: "operationalizing the orphaned toctou-analysis.md line 461 recommendation ('>1% conflict rate -> escalate')" — same wrong filename.
- **Suggestion:** Fix the citation in the brief to `docs/research/research-toctou-in-multi-agent-coding.md:461` (one-line edit), and file a matching one-line correction to bead `Sylveste-4b5.8`'s description so the wrong entry doesn't keep propagating into whatever implements 4b5.8 next. Cheap fix, but load-bearing: anyone chasing "the orphaned recommendation" from the brief alone lands on the wrong document and finds nothing.

### 4b5-17-clearing-condition-unmet-while-brief-assumes-closed
- **Severity:** P1
- **Where:** §0 ("currently empty description"), §6 (collision map: "`sylveste-4b5.17` (open) ... fixes the empty description")
- **What:** Bead `Sylveste-4b5.17`'s acceptance criteria is exactly: "3kol has a non-empty description recording breadth-not-depth + no-recursive-sub-coordinators." I checked the live bead store: `sylveste-3kol`'s `description` field is `""` (empty string) as of this read — even though the bead's `notes` field *does* carry the Rimsky-rename rationale (added 2026-07-23). The brief's §0 correctly reports "empty description," but neither §0 nor §6 flags that this is a **currently-failing acceptance criterion for an open sub-bead whose entire scope is this one field**, sitting unreconciled at the exact moment the brief is being used to charter the epic. A suspense account with a one-line clearing condition that's still open two lines away from where a design brief is being drafted is precisely the kind of thing that should be called out, not passed over silently as background color.
- **Evidence:** Direct read of `.beads/issues.jsonl` for `sylveste-3kol`: `"description":""`. Bead `Sylveste-4b5.17` acceptance_criteria: "3kol has a non-empty description recording breadth-not-depth + no-recursive-sub-coordinators." The rename rationale exists only in `notes`, a different field, which does not satisfy the stated acceptance criterion.
- **Suggestion:** Either (a) treat 4b5.17 as nearly-free to close right now — move the `notes` rationale into `description` (the content already exists, it's in the wrong field) — or (b) if the brief intends `notes` to count, update 4b5.17's acceptance criteria to say so explicitly and close it. Either way, don't let this specific, cheap, already-drafted-content account sit open into the charter.

### mycroft-account-not-opened-before-rimsky-books-open
- **Severity:** P2
- **Where:** §2 (substrate table, "Mycroft (Autarch app, shipped v0.1)"), §5 Q2
- **What:** Q2 poses the Mycroft overlap as a question for melange to resolve, but the brief's own evidence trail for what Mycroft *actually does* is thin — one plan doc reference (`docs/plans/2026-03-12-mycroft-fleet-orchestrator-v01.md`) with no mention that Mycroft is a real, built, running codebase (`apps/Autarch/cmd/mycroft/main.go`, `apps/Autarch/internal/mycroft/`, `apps/Autarch/pkg/fleet/`) with its own SQLite dispatch_log/tier_state schema. Per the ledger discipline this lens applies: before deciding whether two accounts should merge, you open both account books and read the balances. The brief opens Rimsky's book in detail (§1-§4) but only references Mycroft's plan doc, not its shipped implementation surface — the v0.1 plan itself scopes Mycroft to "fleet monitor + T0 (observe/shadow) + T1 (suggest/approve). No autonomous dispatch (T2/T3)" which is a materially narrower claim than "fleet orchestrator" alone suggests, and matters directly for the (a)/(b)/(c) verdict Q2 asks for.
- **Evidence:** `apps/Autarch/cmd/mycroft/main.go` exists; `docs/plans/2026-03-12-mycroft-fleet-orchestrator-v01.md` frontmatter: `scope: v0.1 — fleet monitor + T0/T1 only`, body: "No autonomous dispatch (T2/T3), no auto-recovery, Claude Code runtime only." The brief's §2 table cites the plan doc but not this scope constraint, and §5 Q2 asks the overlap question without surfacing that Mycroft's actual authority ceiling (T1 suggest/approve, human in the loop) is well below what "fleet orchestrator" implies for the (b) "same thing rediscovered" branch.
- **Suggestion:** Before melange scores Q2, add one line to §2's Mycroft row: Mycroft v0.1 = observe + suggest/approve only, no autonomous dispatch — narrowing the overlap surface. This makes (a) "different layer" a much easier verdict to reach cleanly, since Mycroft doesn't currently do within-goal task fan-out at all (it dispatches at the session/fleet level, not the task level) — the account boundary is more separable than Q2's framing implies.

### lbkd-dependency-direction-not-fixed-as-transfer-or-consolidation
- **Severity:** P2
- **Where:** §5 Q1, §6 (collision map)
- **What:** Q1 correctly frames three candidate verdicts (dependency / subsumed / orthogonal) with a note that "the answer determines sequencing." But §6's collision map — the place where the brief's own bookkeeping of in-play beads lives — lists `sylveste-lbkd` as an undifferentiated open bullet, identical in form to `sylveste-bzy` and `sylveste-cpd`. None of the three Q1 verdicts is pre-wired into that ledger as a dependency edge (blocks/discovered-from/parent-child), so whichever verdict the charter reaches has no designated slot to land in — the account exists but has no chart-of-accounts entry showing which column (dependency, consolidated-subaccount, or unrelated-ledger) it belongs to.
- **Evidence:** §6 lbkd bullet: "`sylveste-lbkd` (open) — Sprint v2 artifact bus. **Q1.**" — no dependency-type annotation, unlike how `sylveste-3kol` itself carries typed `blocks` dependencies on 4b5.7/4b5.8/4b5.17 in the live bead store (confirmed via `.beads/issues.jsonl`). The brief has the vocabulary (blocks-type dependency) available and used elsewhere in this very repo's beads but doesn't apply it prospectively to lbkd.
- **Suggestion:** When the Q1 verdict lands, encode it as an actual typed bead dependency (e.g., `sylveste-3kol` `blocks`-depends-on `sylveste-lbkd` if (a) wins, or no edge if (c) wins) rather than leaving it as brief-prose — this is the mechanism the repo already uses (3kol → 4b5.7/4b5.8/4b5.17) and skipping it for lbkd is an inconsistent posting standard within the same document.

Separately, the epic's own bookkeeping shows an open, cheap-to-close account (4b5.17's empty-description criterion) sitting unreconciled at the exact moment this brief proposes to open Rimsky's books, and the collision map doesn't yet apply the repo's own typed-dependency ledger convention to the Q1 verdict it's asking melange to reach.

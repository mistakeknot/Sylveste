# fd-changeringing-conductor — round 1

## Findings Index
- [P1] no-stand-the-band-primitive — Rimsky's brief has zero abort/cancel/drain vocabulary for an in-flight fan-out, while shipped prior art (Mycroft `pause --drain`) already has one (§1, §5 Q4, §7)
- [P2] no-catching-hold-guard — Rimsky specifies no compare-and-swap / claim-collision guard for concurrent dispatch, though Mycroft's dispatch.go already carries one for the identical hazard (§4, §5 Q5)

## Findings

### no-stand-the-band-primitive

- **Severity:** P1
- **Where:** `docs/brainstorms/2026-07-23-rimsky-orchestrator-design-brief.md` §1 ("Is/Is not"), §5 Q4, §7 (candidate completion shape) — the whole document
- **What:** The brief specifies what triggers a fan-out (the pre-dispatch cost gate, §3.2) and what *might eventually* throttle one mid-flight (the deferred dynamic controller, §3.3/Q4), but never specifies what happens to the N already-spawned, already-committed agents when a human or the instrument decides the fan-out was a mistake *after* spawn. In ringing terms: pulling off is "ringing up" — once a bell is up and struck, it carries momentum a single ringer cannot dump instantly; a conductor's job is to hold a clean 'stand' call in reserve at all times, one signal that sets every rope at rest safely, precisely because an uncontrolled abandonment of a rung-up bell (letting go mid-swing) is how ringers get hurt and ropes get tangled. Rimsky's only stop-related vocabulary in the whole brief is the word "kill" inside "dynamic kill-rule controller" (§3.3) — and that's a *conflict-rate* trigger for the deferred v2 controller, not a v1 operational abort path for N already-running agents. Nothing in §7's "done" shape mentions a coordinated stop.
- **Evidence:** `grep -n "abort\|cancel\|kill\|stop\|rollback"` against the brief returns exactly one hit, line 71, inside "dynamic kill-rule controller" — a deferred-to-P3 detection mechanism, not an abort primitive. Compare to shipped prior art one table-row away in the brief's own §2: `docs/plans/2026-03-12-mycroft-fleet-orchestrator-v01.md` Step 8 already ships `mycroft pause --drain` — "paused + send graceful-stop signal to in-flight agents" — as a first-class v0.1 operational command, distinct from `pause` (stop new dispatch only) and from `override` (bypass selector). Mycroft solved "stand the band" for its own (cross-session, T0/T1) fan-out shape; Rimsky's brief, chartering a *within-goal* N-parallel fan-out that is structurally closer to "many bells up at once" than Mycroft's suggest/approve loop, does not carry the equivalent primitive forward, and Q2 doesn't ask whether Rimsky should inherit it.
- **Suggestion:** Add a `rimsky stand` (or equivalent) command/verb to the v1 (instrument + flat fan-out + cost gate) scope in §7, explicitly distinguished from the deferred v2 controller: a single call that (a) sends graceful-stop to every spawned worktree-isolated agent, (b) releases every interlock reservation those agents hold, (c) leaves worktrees in an inspectable-not-corrupted state for manual resume/discard. This is cheap to scope now (it's a coordination primitive, not a policy decision) and expensive to retrofit once N-parallel fan-out is load-bearing — exactly the asymmetry the anti-abandonment doctrine (Q6) is designed to catch, but Q6 as written only asks about *build sequencing* (v1 vs v2 controller), not about *whether v1 is safely abortable*.

### no-catching-hold-guard

- **Severity:** P2
- **Where:** `docs/brainstorms/2026-07-23-rimsky-orchestrator-design-brief.md` §4 (nested-repo rule), §5 Q5 (pre-spawn conflict check cost)
- **What:** Q5 asks whether the pre-spawn conflict check (intermap change_impact + interlock dry-run) is cheap enough to run unconditionally. That's the right question for the *first* dispatch decision, but the brief has no vocabulary at all for the second hazard the same mechanism exists to prevent in Mycroft: two dispatchers (or two Rimsky invocations, or a human retry racing an in-flight run) trying to claim/spawn against the same task window concurrently — "catching hold" of a rope someone else is already ringing. In full-circle ringing, briefly seizing a moving rope you don't control (rather than waiting for your own call) is exactly how a true touch goes false or a ringer gets hurt; the discipline is that only one hand is ever on a given rope at a time, enforced structurally, not by politeness.
- **Evidence:** `grep -n "claim\|double.dispatch\|race\|concurrent"` against the brief returns zero hits. Mycroft's shipped dispatch flow (`docs/plans/2026-03-12-mycroft-fleet-orchestrator-v01.md` Step 7, "Dispatch execution") names this hazard explicitly and answers it with a specific, cheap mechanism: "4. Compare-and-swap guard: check `assigned_at` before writing" plus a "Two-phase claim TTL" (90s to first heartbeat, then 45min) — i.e., a rope is only ever 'held' by one dispatcher, verified at write time, with a short TTL so an abandoned claim self-releases. Rimsky's Q5 is scoped only to the pre-spawn *conflict* check's runtime cost, not to whether Rimsky's own dispatch write path can race itself or a concurrent invocation.
- **Suggestion:** When Q5 is resolved, fold in one sentence answering whether Rimsky's dispatch write (claiming which repo/task combo is about to be fanned out) needs the same compare-and-swap + TTL guard Mycroft already built two doors down — not as new design, just as "does the mandated pre-spawn check also need to be atomic with the claim write, or can a dry-run and a claim interleave." This is a one-line addition to the Q5 verdict, not a new question — flagged P2 because interlock's file reservations may already close this at a different layer (worth confirming, not assuming).

## Verdict

Round-0's lenses converged hard on provenance/fabrication issues (the dispatch log doesn't exist, citations are misattributed, epic metadata is stale) and left the *operational* half of the ringing analogy — what happens to already-spawned agents when things go wrong — almost untouched. The brief's near-decided constraints (flat depth-1, pre-dispatch cost gate, telemetry-not-controller) are all pre-spawn concerns; nothing in the document answers the "bells are up, now what" question, and the one piece of shipped, adjacent prior art (Mycroft) already answers it twice (drain-stop, compare-and-swap claim guard) without the brief citing either mechanism as something Rimsky should inherit or deliberately decline.

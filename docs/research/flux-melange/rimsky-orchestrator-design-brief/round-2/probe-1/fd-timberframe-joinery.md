## Findings

### bzy-timber-not-yet-single-piece
- **Severity:** P1
- **Where:** §6 Collision map — `sylveste-bzy` (open, P2) — "a clean per-repo fan-out may require this cleanup first."
- **What:** The brief lists bzy as a soft maybe. Reading the actual timber (the bead text, not the drawing dimension): bzy says five interverse plugins — interfer, interhelm, intersight, interseed, intership — are **dual-tracked right now**: force-added into the monorepo AND independently published from their own repos, with only two of the five (interhelm, intercut) resolved via the cpd pilot. A master carpenter does not cut a joint into a log whose grain direction is still contested — and per-nested-repo fan-out (§4, the doc's own hardest correctness constraint) is exactly a claim about which repo is canonical per plugin. For the three still-dual-tracked plugins (interfer, intersight, interseed), Rimsky's fan-out has two candidate timbers per member and no rule yet for which one it's isolating. This is not "may require cleanup," it is "cannot correctly assign a worktree slot to these three plugins until the splice question is closed" — a precondition, not a nice-to-have, for the nested-repo rule to hold universally rather than for the two already-fixed cases.
- **Evidence:** `.beads/issues.jsonl` (Sylveste-bzy, open, P2): "five interverse dirs are force-tracked in the Sylveste monorepo... while each is ALSO an independent published plugin... Resolution: untrack the five... NOT done in the pilot to avoid a large unilateral untrack mid-goal." Only interhelm + intercut (2 of 5+1) were resolved (Sylveste-cpd, closed). Brief §6 lists bzy without flagging the 3-of-5 unresolved count against the nested-repo rule's universality.
- **Suggestion:** Add a §6 or §5-adjacent note: Rimsky's per-nested-repo fan-out is only correctness-complete for plugins with one resolved canonical repo. For interfer/intersight/interseed, either (a) gate those three out of Rimsky's fan-out eligibility until bzy closes, or (b) have Rimsky's pre-spawn check (Q5) detect dual-tracking and refuse to slot a worktree for a still-contested plugin — cheap, since the check already inspects repo state before spawning.

### lbkd-splice-has-a-known-defect
- **Severity:** P1
- **Where:** §5 Q1 — "lbkd is OPEN and unstarted — the answer determines sequencing."
- **What:** Q1 asks whether lbkd is a dependency, subsumed, or orthogonal, but frames the open question purely as one of *sequencing* (has it shipped yet). Reading the actual timber — `docs/plans/2026-03-19-sprint-v2-artifact-bus.md` — shows the plan already documents a **defect in the joint itself**, not just its unbuilt status: `bd set-state` uses `key=value` encoding, so an artifact path containing `=` breaks the write, and the plan's own Risk section calls this "low risk" only because "our paths don't contain `=`" today — an assumption about the CURRENT artifact corpus, not a guarantee about paths Rimsky's fan-out would generate (worktree-qualified paths, per-repo-namespaced artifact names, etc., are exactly the kind of path Rimsky would introduce). A tsugite splice cut to a defect you haven't inspected is cut to the wrong two timbers. If Q1 resolves toward (a) hard dependency or (b) subsumed — both of which make lbkd Rimsky's inter-stage channel for N parallel tasks — this defect becomes load-bearing under exactly the conditions (many concurrent, differently-shaped artifact paths) that make it likeliest to trigger.
- **Evidence:** `docs/plans/2026-03-19-sprint-v2-artifact-bus.md:106-109` (Risk section): "`bd set-state` uses `key=value` format — artifact paths with `=` in them would break. Mitigate: URL-encode or use a different separator. Low risk since our paths don't contain `=`." This is un-mitigated (mitigation is listed as a TODO, not done) and the plan's own dual-write design (Task 2, get-artifact tries ic first, bd second) means silent bd-path corruption wouldn't necessarily surface if ic is also active.
- **Suggestion:** Q1's answer should carry an explicit precondition, not just a sequencing verdict: if lbkd becomes Rimsky's channel (paths a) or (b)), the `=`-in-path mitigation (Task 2's TODO) must land before N-parallel Rimsky adopts it — otherwise Rimsky is the workload most likely to first strike the untested edge in a joint whose builder already flagged, then postponed, the defect.

### two-dispatch-logs-one-name
- **Severity:** P2
- **Where:** §3.3 ("Extend the EXISTING `/clavain:work` + `/flux-review` dispatch log...") and §5 Q2 ("Do not build a second fleet orchestrator by accident").
- **What:** §3.3 instructs Rimsky to extend "the EXISTING dispatch log" (singular, definite article) — but the actual timber shows there are two dispatch_log joints already standing in the codebase, cut for different loads. Mycroft/Autarch (`docs/plans/2026-03-12-mycroft-fleet-orchestrator-v01.md:67,210-216`) ships its OWN SQLite `dispatch_log` + `tier_state` + `tier_transitions` schema, purpose-built as a **tier-gated** log: T0 writes `shadow_suggest` entries, T1 writes approve/reject with reasons, and `mycroft overrides` already does pattern analysis over `dispatch_log.reason`. That is structurally the same joint Rimsky's Q4 controller-gate would need (a log that already distinguishes "observed only" from "escalated/acted," already supports reason-coded rejection). The brief's Q2 asks whether Rimsky duplicates Mycroft's *orchestration* layer, but doesn't ask the narrower, cheaper question: when Rimsky's telemetry (§3.3) needs a tier/escalation dimension later (Q4's gate condition), should it extend Mycroft's already-proven tier-gated dispatch_log schema, or grow its own gate logic bolted onto the plain `/clavain:work`+`/flux-review` log that has no tier concept today? Naming both "the dispatch log" invites cutting two same-species joints under one label.
- **Evidence:** Brief §3.3 says "Extend the EXISTING `/clavain:work` + `/flux-review` dispatch log (already records wall-time, task-sum, agent-count)." Mycroft plan lines 210-216, 228, 236, 330 describe a separate, schema-richer `dispatch_log` with tier semantics already built and tested (v0.1 shipped per the doc's own §2 substrate table row).
- **Suggestion:** When Q4's gate condition is eventually evaluated (non-trivial conflict rate observed), have that decision explicitly choose between (a) growing tier/escalation columns onto the plain dispatch log named in §3.3, or (b) routing Rimsky's escalation events into Mycroft's existing tier_state/tier_transitions tables via FleetView (Q2's "consumer" framing) — don't let two dispatch_log tables silently diverge because §3.3 and Mycroft's own doc both use the bare name "dispatch log" for different timbers.

## Verdict
Three P1/P2-grounded findings, all reading the timbers the brief cites (bzy's bead text, lbkd's own risk section, Mycroft's dispatch_log schema) rather than the brief's summary of them. The strongest is lbkd-splice-has-a-known-defect: Q1's framing is purely temporal (has lbkd shipped) when the actual blocking question is whether its one documented defect is load-bearing under Rimsky's usage pattern — a fit question the brief's own subsumption framing invites but doesn't ask.

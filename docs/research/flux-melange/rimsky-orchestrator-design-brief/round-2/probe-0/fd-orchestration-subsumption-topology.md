## Findings

### no-abort-vocabulary-confirmed
- **Severity:** P1
- **Where:** docs/brainstorms/2026-07-23-rimsky-orchestrator-design-brief.md §1 (framing), §5 Q4/Q6, §7 (completion shape)
- **What:** CONFIRMED. Grepping the brief for `kill|abort|cancel|drain|pause|stop` finds exactly one hit: line 71, "dynamic kill-rule controller" — deferred to P3, gated on telemetry. Zero occurrences of abort, cancel, drain, or pause anywhere else in the document, including §1's framing of what Rimsky "is," §4's plug-in points, §6's collision map, and §7's candidate completion shape. The brief specifies how N tasks get spawned (flat fan-out, cost gate, pre-spawn conflict check) and how their outcome gets measured (conflict-economics telemetry) but never how an operator stops an already-running fan-out short of letting every task finish or waiting for the not-yet-built kill-rule controller.
- **Evidence:** `grep -n "kill\|abort\|cancel\|drain\|pause\|stop" docs/brainstorms/2026-07-23-rimsky-orchestrator-design-brief.md` → single match at line 71. Cross-checked docs/guide-worktree-first-coordination.md and docs/plans/2026-03-19-sprint-v2-artifact-bus.md for the same terms — zero hits in either, confirming this is a hole in the whole substrate Rimsky consumes, not just the brief's prose. Meanwhile apps/Autarch/cmd/mycroft/main.go:230-247 ships `mycroft pause` (sets a paused flag via `d.LogPause()`, blocks new dispatch, lets in-flight agents finish) and `mycroft resume` (line ~249) as working Cobra subcommands backed by `Orchestrator.Pause()`/`Resume()`/`IsPaused()` in internal/mycroft/scheduler/orchestrator.go:69-76. The plan doc (docs/plans/2026-03-12-mycroft-fleet-orchestrator-v01.md:324-326) explicitly documents two distinct primitives: `mycroft pause` ("stop new dispatches") and `mycroft pause --drain` ("paused + send graceful-stop signal to in-flight agents") — matching the prior finding's description almost verbatim. The "stop new dispatch" half is real and shipped; see the companion finding below on `--drain` itself.
- **Suggestion:** N/A — this is the confirmation of the prior finding; see q6-scope-cut-silent-on-abort-safety for the actionable fix.

### q6-scope-cut-silent-on-abort-safety
- **Severity:** P1
- **Where:** docs/brainstorms/2026-07-23-rimsky-orchestrator-design-brief.md §5 Q6, §7
- **What:** Q6 asks whether Rimsky is one C4/C5 goal or decomposes into shippable-v1 (instrument + flat fan-out + cost gate) plus gated-v2 (controller), and "where are the internal gates so it can't stall as a half-built orchestrator." That question is entirely about *build-sequencing* gates. It never asks the orthogonal *operational-safety* question: once v1 ships and an operator has N tasks fanned out across worktrees, does v1 need a way to stop the fan-out cleanly (e.g., mid-run cost-gate breach discovered, or the operator realizes the parallelization choice was wrong) that is separate from the deferred controller? Conflating "no kill-rule controller in v1" with "no way to stop a running fan-out in v1" is exactly the second-fleet-orchestrator-adjacent risk this lens watches for — if the answer turns out to be "yes, v1 needs a manual stop," that requirement was never scoped, and it will get bolted on ad hoc later, or worse, an operator will `Ctrl-C` the orchestrating session and leave N worktrees and interlock reservations in an undefined state.
- **Evidence:** §5 Q6 text (lines 115-117): "Is it one goal, or does it decompose into a shippable v1 (instrument + flat fan-out + cost gate) and deferred v2 (controller, if earned)? Where are the internal gates so it can't stall as a half-built orchestrator?" — "gates" here means sequencing/build gates, confirmed by cross-reference to §3.3 (line 71-74) where "gated on telemetry" is used the same way. §7's candidate completion shape (lines 130-134) lists route.md gate, dispatch log telemetry, documented fan-out path, Q1/Q2 verdicts, and "controller explicitly deferred with its gate condition written down" — no line asks about mid-flight operator control. The dynamic kill-rule controller (§3.3) is a *policy* that decides when to kill based on conflict-rate evidence; a manual stop is a *mechanism* an operator invokes directly regardless of what the controller would decide — these are different concerns that the brief's single "kill-rule controller" vocabulary conflates by omission (the brief never distinguishes them because it never mentions the manual case at all).
- **Suggestion:** Add a Q6 sub-question (or a new §5 Q7) asking explicitly: "Does Rimsky v1 need an operator-invoked stop-fan-out primitive independent of the deferred kill-rule controller, and if so, does it stop-new-only (Mycroft's `pause` model) or attempt to signal in-flight tasks (Mycroft's `--drain` aspiration, which is itself unshipped — see companion finding)?" Given nested-repo worktree state and interlock reservations are the resources at risk mid-fan-out, the answer likely needs to be scoped into v1, not deferred with the controller.

### pause-resume-is-the-cheap-v1-primitive-and-its-unclaimed
- **Severity:** P2
- **Where:** docs/brainstorms/2026-07-23-rimsky-orchestrator-design-brief.md §2 (substrate table), §7 (completion shape)
- **What:** The brief's §2 table lists Mycroft only as "closest prior orchestrator" for the Q2 overlap question — it never inventories Mycroft's *specific shipped mechanisms* as candidate patterns to reuse. `mycroft pause`/`resume` is exactly the "stop new dispatch only" primitive that would satisfy a minimal v1 answer to the abort-safety gap above, and it is cheap: ~15 lines of orchestrator state (`paused bool` + two setters + one guard at scheduler/orchestrator.go:19,39,69-76) plus a DB-logged event for audit. If Rimsky's answer to Q2 is "different layer" (within-goal vs cross-session), that still doesn't preclude *pattern* reuse — the brief's own "consumer of Mycroft's FleetView" option (Q2c) suggests reuse is already on the table, just not for this specific mechanism.
- **Evidence:** apps/Autarch/internal/mycroft/scheduler/orchestrator.go:19 (`paused bool` field), lines 39-41 (dispatch loop checks `o.paused` before advancing), lines 69-76 (`Pause()`/`Resume()`/`IsPaused()`). apps/Autarch/cmd/mycroft/main.go:230-257 (Cobra commands wired to `LogPause()`/`LogResume()`). Brief §2 (lines 41-49) cites Mycroft only for "fleet monitor + T0/T1 suggest/approve dispatch," never for pause/resume specifically.
- **Suggestion:** In whichever doc resolves Q1/Q2/Q6 (bead verdict or charter), explicitly note whether Rimsky v1 adopts a pause/resume-equivalent (stop-new-dispatch-only, in-flight tasks finish) as its minimal abort-safety answer, scoped as part of shippable-v1 rather than bundled with the deferred controller.

### drain-flag-is-a-stub-worth-naming-in-mycroft-not-rimsky
- **Severity:** P3
- **Where:** apps/Autarch/cmd/mycroft/main.go:427 (flag registration); apps/Autarch/cmd/mycroft/main.go:230-247 (`pauseCmd.RunE`, no drain handling)
- **What:** The prior finding under test describes Mycroft as already shipping "a coordinated graceful-stop primitive (`pause --drain`)." That's true of the plan doc (docs/plans/2026-03-12-mycroft-fleet-orchestrator-v01.md:325) but only half-true of the shipped code: the `--drain` bool flag is registered on `pauseCmd` at main.go:427, but `pauseCmd`'s `RunE` (lines 233-247) never calls `cmd.Flags().GetBool("drain")` or branches on it — a full-repo grep for `drain|Drain` finds only that one registration line, no read site, no signal-dispatch codepath in the scheduler. So `mycroft pause --drain` today behaves identically to `mycroft pause`: new dispatch stops, in-flight agents are *not* actually signaled to checkpoint. This doesn't change the P1 finding's verdict (the "stop new dispatch only" primitive is real and shipped, which is already enough to show Rimsky's brief has a documented gap relative to adjacent prior art) — but citing `pause --drain` as evidence of a working graceful-stop mechanism overstates Mycroft's actual current capability by one increment.
- **Evidence:** `grep -n "drain\|Drain" -r apps/Autarch/internal/mycroft apps/Autarch/cmd/mycroft` → exactly one hit, the flag registration at main.go:427. No corresponding `GetBool("drain")` call exists in the file.
- **Suggestion:** When the round's synthesis cites Mycroft's `--drain` as prior art for Rimsky to follow, flag it as "designed, flag-stubbed, not functionally wired" rather than "shipped" — Rimsky should treat the drain *semantics* as validated design intent to borrow, not as a working implementation to copy-paste from.

## Verdict
CONFIRMED, with a sharpened evidentiary edge. The Rimsky brief genuinely contains zero abort/cancel/drain vocabulary outside the deferred kill-rule controller, and this gap is systemic across the adjacent worktree-contract and artifact-bus docs too — not brief-specific carelessness. Mycroft does ship the "stop new dispatch, let in-flight finish" half of the claimed prior art (`pause`/`resume`, fully wired), which is itself sufficient to prove the pattern exists and is cheap; but the "graceful-stop signal to in-flight agents" half (`--drain`) is a registered-but-unread flag, not a working mechanism, so the prior finding's characterization of Mycroft's drain primitive should be downgraded from "ships" to "specifies, partially implements." Q6's anti-abandonment framing should be amended to ask about operator-invoked mid-flight stop as a v1-scoping question, separate from the deferred kill-rule controller.

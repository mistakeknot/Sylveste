## Findings

### sentinel-is-a-clock-not-a-lease
- **Severity:** P1
- **Where:** `core/intercore/internal/sentinel/sentinel.go:32-60` (Store.Check); called via `intercore_sentinel_check_or_legacy` in `os/Clavain/hooks/auto-stop-actions.sh:135` for the goal-cadence tier itself
- **What:** The task brief asks me to score lease/heartbeat as a terminal-gate alternative. Intercore already has exactly one liveness-adjacent primitive in the codebase — `sentinel.Store.Check` — and it is NOT a lease. It is a monotonic throttle: `INSERT OR IGNORE` a row at `last_fired=0`, then an atomic `UPDATE ... WHERE unixepoch() - last_fired >= intervalSec` that either fires (updates the clock) or doesn't. There is no renewal call, no holder identity stored (only `name`+`scope_id`, not a session/administrator ID), and no way to distinguish "the goal is actively being tended by a live session" from "enough wall-clock time has passed since anyone last touched it." If a lease/heartbeat terminal-gate shape is designed by analogy to this existing primitive (the natural move — it's already wired into the goal-cadence path that fires next-goal), it will inherit throttle semantics: a session that dies mid-run leaves the sentinel clock exactly where a healthy idle session would, and both look identical to any observer. In waqf terms, this is a water-clock marking how long since the last visit to the orchard, not a deed recording who currently holds the keys — it can tell you "nobody has checked in for N minutes" but never "the trustee who checked in last is still alive and will check in again," which is the actual claim a lease/heartbeat model needs to make to distinguish transient session-close (administrator discharge, frequent, fine) from goal abandonment (endowment ownerless, rare, structural failure).
- **Evidence:** `sentinel.go:32-33` doc comment: "Check performs an atomic claim-if-eligible throttle check... When intervalSec is 0, the sentinel fires at most once per scope_id." No `Renew`, `Release`, or holder-identity field exists in the `Sentinel` struct (`Name`, `ScopeID`, `LastFired` only, lines 11-15). The one live caller (`auto-stop-actions.sh:135`) uses it to prevent duplicate next-goal firing within 60s of the same session — a debounce, not a succession mechanism.
- **Suggestion:** If a lease/heartbeat terminal-gate candidate advances past this probe round, name explicitly whether it reuses `sentinel` (and accept throttle semantics: expiry proves absence-of-recent-activity, never proves death) or requires a new primitive that stores a holder ID and supports renew/release — the difference determines whether "session B may or may not arrive" (the lens's stress scenario) is detectable as abandonment or just indistinguishable idle time.

### successor-proposal has no bound office
- **Severity:** P0
- **Where:** `docs/brainstorms/2026-07-18-goal-native-cycle-brainstorm.md` §Key Decisions item 7 ("goal-cadence Stop-hook tier reads the entity instead of regex-matching prose") and §Open Questions 'Terminal-gate shape' (the successor-proposal doctrine line)
- **What:** All three named terminal-gate candidates, and the ones this probe was asked to add, describe successor-proposal as a *step* — something that runs at a point in a sequence, or a consumer that subscribes to an event, or something a lease-expiry might trigger. None of them name a standing office that is accountable for the obligation existing at all, independent of any single session's execution path. Waqf law's answer to "who appoints the next mutawalli when the current one's tenure lapses" is never "whichever administrator happens to still be in the room when the term ends" — it is the nazir, a role that persists precisely because it is not the same actor whose departure creates the vacancy. Every candidate in the doc (two-layer ordered close, single-layer /goal-met, event-driven consumers, and this probe's lease/heartbeat and escrowed-close variants) locates the successor-proposal obligation inside the SAME execution path as the session that is closing — i.e., the discharging administrator is also the one who must, in the same breath, appoint their own successor. If that session dies, crashes, or is killed between "goal purpose fulfilled" and "next-goal fired" (a window this doc itself calls out via the goal-cadence Stop-hook's 60s throttle window and the coarse close-evidence gap already logged as settled), the obligation evaporates with no other party positioned to notice — there is no separate, persistently-scheduled check of the form "does every goal marked done/abandoned have a successor-proposal record, and if not, raise it" run by something OTHER than the terminal-closing session.
- **Evidence:** `next-goal.md` (the successor-proposal mechanism itself) is a Stop-hook-triggered, in-session command (`hooks/auto-stop-actions.sh:135-146`) — its only trigger is `SIGNALS == *goal-completed*` detected within the *same turn* that is closing. There is no batch/cron/kernel-level sweep in the repo (confirmed absent from `core/intercore/internal/sentinel` and the hooks directory) that audits Goals for "closed without a logged successor-proposal" after the fact. Compare to the doc's own settled-fact language: "goals span many runs/sessions; the successor-proposal doctrine... wants enforcement somewhere" (§Open Questions) — the doc already flags this as unresolved, but frames it as a sequencing choice among the three candidates rather than as a role-assignment problem. This finding reframes it: no candidate proposes a party whose JOB is to hold this obligation across administrator turnover, only a step order for the administrator currently present to try to discharge it before leaving.
- **Suggestion:** Name a standing successor-proposal auditor independent of the closing session — e.g., a kernel-level sweep (analogous to the existing `sentinel`-adjacent TTL cleanup pattern noted in `core/intercore/AGENTS.md:191-200` for operational-state pruning) that periodically scans Goals in a terminal-adjacent state (met/abandoned/dormant) for a missing successor-proposal record and raises it as a first-class defect, not merely a missed step in one session's sequence. This is the nazir office the doc is currently missing, and it is orthogonal to which of the terminal-gate shapes wins — every candidate needs it as a backstop.

### C1 self-administration collapses nazir and mutawalli
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-07-18-goal-native-cycle-brainstorm.md` §Key Decisions item 6 ("C1 = one confirming question, no melange")
- **What:** Item 6 stakes-routes ceremony depth by `classify-complexity`, exempting C1 goals from melange review entirely — the doc's own text: "Anti-goal: if the ritual taxes small goals, users route around it back to free text." This is the correct anti-ceremony instinct, but it has an unexamined second-order effect on the terminal side, not just the formation side: a C1 goal is also, structurally, the class most likely to be a short-lived, single-session, low-attention goal — exactly the profile most prone to silent abandonment (the session closes, nobody comes back, the goal is never formally dissolved). Yet C1 is precisely the tier that gets NO supervisory party (no melange, no nazir-equivalent) at formation, and the doc's terminal-gate discussion doesn't stakes-route the CLOSE side at all — it treats terminal-gate shape as a single global mechanism applied uniformly regardless of the C1-C5 tier that formed the goal. In waqf terms: a small waqf may lawfully be self-administered with the founder as sole trustee and no separate nazir, but jurists still required SOME minimal formality (a written stipulation, a dated deed) precisely because self-administered endowments were the ones jurists observed lapsing into de facto private property or abandonment over a generation, absent even that minimal external check. If C1 goals get lightweight formation AND whatever terminal-gate shape wins applies to them with the same lack of oversight, there is no jurist-equivalent anywhere in the C1 lifecycle who would ever notice a C1 goal going ownerless — it's invisible at both ends.
- **Evidence:** §Key Decisions item 6 stakes-routes only formation ceremony and review-gate choice ("Same metric routes review gates (flux-drive vs melange)"); no text stakes-routes terminal-gate mechanism strength by C1-C5. The doc's terminal-gate paragraph (§Open Questions) discusses (a)/(b)/(c) as globally-applicable shapes with no C-tier modulation mentioned.
- **Suggestion:** Ask explicitly, in the melange round this doc delegates terminal-gate shape to: should terminal-gate rigor be stakes-scaled symmetrically with formation ceremony (e.g., C1 goals get a cheap but MANDATORY dissolution record — even if it's just "goal auto-marked stale after N idle days, logged, no successor required" — while C4/C5 get the full ordered-close-with-verification), rather than either (i) one global mechanism for all tiers or (ii) accidentally exempting the cheapest tier from both ends of the trust lifecycle.

### charter shurut carry no amendment protocol
- **Severity:** P2 [t]
- **Where:** §What We're Building Pillar 1 (charter description: "the why, scope, acceptance criteria, verdicts on adjacent work") and Pillar 2 ("goals contain runs, carry the charter, accumulate close evidence")
- **What:** The charter's acceptance criteria are explicitly framed as founder-authored, machine-evaluable stipulations meant to bind every subsequent run ("a machine-evaluable completion condition... written so the Haiku evaluator can judge it"). Waqf shurut (the founder's conditions) are similarly meant to bind in perpetuity — but classical waqf doctrine still had to develop doctrine for what happens when a stipulation becomes impossible, contradictory, or is discovered to have been miswritten (this is part of what cy-près doctrine, already flagged elsewhere in this lens's brief, resolves for IMPOSSIBLE purposes — but amendment of a still-possible-but-flawed condition is a distinct problem cy-près doesn't fully cover). Nothing in the doc says whether a charter's acceptance criteria are ever editable after ratification by a run that discovers the original condition was underspecified (e.g., "tests exit 0" turns out to pass trivially against an empty test file) — is this a NEW charter (new Goal), a melange-gated amendment to the existing one, or silently patched by whichever run notices the gap, unilaterally, with no re-ratification at all?
- **Evidence:** No amendment/versioning language appears anywhere in Pillar 1, Pillar 2, or Key Decisions 1-7. "melange review of high-stakes charters" is described only as a pre-ratification gate (Pillar 1: "high-stakes charters get a flux-melange review before ratification"), never as a re-review trigger for post-ratification edits.
- **Suggestion:** Low cost now, worth one line in the charter schema design: an explicit `amendment` field or event type distinct from `close evidence`, with the same stakes-routing (C1-C5) applied to whether an amendment needs re-ratification — this is a taste/completeness flag, not a structural blocker, hence P2.

## Verdict
The doc's terminal-gate alternatives, including the ones this probe was asked to widen the search to, all locate the successor-proposal obligation inside the same execution path as the closing session rather than assigning it to a standing party independent of administrator turnover — this is the deepest gap a waqf-succession reading surfaces, and it's orthogonal to which of the three-plus-N candidate shapes wins. The codebase's one liveness primitive (`sentinel`) is a throttle clock, not a lease, which is a load-bearing distinction for anyone about to design a lease/heartbeat terminal-gate by analogy to it. The stakes-routing doctrine (C1-C5) currently modulates formation ceremony only, leaving the cheapest tier unsupervised at both ends of the goal lifecycle.

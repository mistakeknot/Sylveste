## Findings

### defaultchain-has-no-version-field
- **Severity:** P0
- **Where:** §Key Decisions item 5 ("Strategy diet via absorption... the kernel chain gains a goal-formation head instead of a `strategized` middle. This is a chain change, not a prompt edit — `strategized` is a kernel phase in DefaultChain.")
- **What:** Verified directly: `core/intercore/pkg/phase/phase.go:23-35` defines `DefaultChain` as `var DefaultChain = []string{Brainstorm, BrainstormReviewed, Strategized, Planned, Executing, Review, Polish, Reflect, Done}` — a package-level variable with zero versioning metadata (no `schema_version`, no chain-ID, no per-run pin beyond the existing `Phases []string` override field on `Run`, phase.go:200, whose doc comment says "nil = legacy chain"). `ResolveChain(r *Run)` (internal/phase/phase.go:178-183) falls back to this same mutable global for any run with `Phases == nil`. If `DefaultChain` is edited in place to insert a goal-formation head and drop/relocate `Strategized`, every existing run that is mid-`strategized` with `Phases == nil` (the common case — `Phases` is explicitly the *override* path) will have `ResolveChain` return the *new* chain on next evaluation. `ChainNextPhase` (internal/phase/phase.go:110-120) and `ChainIsValidTransition` (internal/phase/phase.go:122-135) both do linear lookups by phase *name* in whatever chain `ResolveChain` returns — a run sitting at `Strategized` when the new chain removes or renames that phase will either fail `ChainNextPhase`'s `"phase %q not found in chain"` error or silently jump indices if the name is reused with different neighbors.
- **Evidence:** `core/intercore/pkg/phase/phase.go:23-35` (DefaultChain — no version field); `core/intercore/internal/phase/phase.go:177-183` (`ResolveChain` — nil Phases falls through to the mutable global); `core/intercore/internal/phase/phase.go:109-120` (`ChainNextPhase` — name-based lookup, errors if phase absent from chain).
- **Suggestion:** Smallest viable fix: don't edit `DefaultChain` in place. Add a new named chain constant (e.g. `GoalNativeChain`) alongside the existing `DefaultChain`, and have run-creation code (wherever `Phases` is populated as nil today) start stamping an explicit `Phases` array for all *new* runs at the cutover point, leaving `DefaultChain` itself untouched so in-flight nil-`Phases` runs keep resolving to the old chain unchanged. This reuses the override mechanism that already exists (phase.go:200's doc comment literally anticipates "nil = legacy chain" as a distinct population) rather than requiring new versioning infrastructure.

### interphase-retirement-names-no-replacement-data-source
- **Severity:** P1
- **Where:** §Open Questions, "interphase retirement path" ("it ships statusline UX people see daily; retiring the phase authority without losing the display surface needs a consumer story")
- **What:** Verified interphase's actual mechanism: `interverse/interphase/README.md:11` states "Phase state is communicated to interline via sideband files at `~/.interband/interphase/bead/${session_id}.json`, so the statusline can show your current workflow phase without any direct coupling between the plugins." This is a concrete, named integration contract (a JSON sideband file keyed by session_id, consumed by a *third* plugin, interline) — not a vague "it has a UI." The doc's open question correctly flags the retirement risk but proposes no replacement writer for that file path. If the Goal-native design retires interphase's phase-tracking authority (`lib-phase.sh`) without something else writing to `~/.interband/interphase/bead/${session_id}.json`, interline's statusline goes stale or blank the moment interphase stops running, with no code change to interline itself.
- **Evidence:** `interverse/interphase/README.md:11` (sideband file path + interline as the decoupled consumer); `interverse/interphase/docs/vision.md:17,58` (repeats the sideband mechanism; explicitly notes "Render the statusline (that is interline)" is out of interphase's own scope, confirming a three-plugin chain: interphase writes → interline reads/renders); Clavain's own `CLAUDE.md` "Quick Commands" section lists interphase as a "Key companion: phase tracking, gates, discovery" alongside interline as "statusline renderer" — both are first-class, separately-versioned plugins, not sub-modules of Clavain.
- **Suggestion:** Scope the interphase retirement as an explicit consumer-migration bead: either (a) have the new Goal/kernel-chain-authority write the same sideband JSON shape to the same path (cutover is then invisible to interline, zero interline changes needed), or (b) if the shape changes, file a companion bead against interline to consume the new source, with an explicit cutover date so there's no window where neither writer is active. Do not scope retirement as "delete interphase" without one of these two paired changes.

### three-way-transition-owner-not-named
- **Severity:** P1
- **Where:** §Key Decisions item 4 ("Scope: all-in, gated inside one goal"); §Open Questions "Three-way transition-ownership cleanup"
- **What:** The doc names all three phase-sequencing owners with real specifics — `sprint.md` (prompt-level), `lib-sprint.sh` (1905 lines, confirmed via `wc -l`), and "clavain-cli Go port (~90 verbs, mid-migration)" — and states "the goal-native chain change lands on whichever of these is canonical; sequencing vs. the Go migration is open." But Key Decision 4 simultaneously declares scope "all-in, gated inside one goal... staged with internal gates," implying implementation is imminent, while the landing target is explicitly still unresolved. Verified `sprint.md` itself already routes phase-advance calls through `clavain-cli sprint-advance` (e.g. `commands/sprint.md:529` `clavain-cli sprint-advance "$CLAVAIN_BEAD_ID" "reflect"`), meaning the Go port is not a distant future target — it's already load-bearing in the current terminal-step (Step 10/reflect) path today. Landing the goal-formation-head chain change in bash (`lib-sprint.sh`, fastest to edit) while `clavain-cli` is "mid-migration" of the same phase-sequencing logic risks the Go port later re-deriving phase sequencing from a pre-change spec, per this lens's own P1 severity calibration.
- **Evidence:** `os/Clavain/hooks/lib-sprint.sh` (1905 lines, confirmed via `wc -l`); `os/Clavain/commands/sprint.md:529` (`clavain-cli sprint-advance` already called from the prompt layer, confirming Go-port entanglement is current, not hypothetical); doc §Open Questions final bullet (names the ambiguity but doesn't resolve it).
- **Suggestion:** Before implementation starts on the chain change, add one explicit line to the plan: "the goal-formation-head chain change lands in `clavain-cli` (Go) first since `sprint-advance` already round-trips through it; `lib-sprint.sh` and `sprint.md` are updated to call the new verb, not to reimplement phase logic locally." This matches the project's own stated direction (Go port is the migration target) and avoids the two-owners-diverge failure mode named in this lens's P1 calibration.

### stakes-metric-reused-across-two-decisions-without-cross-check
- **Severity:** P2
- **Where:** §Key Decisions item 6 ("Ceremony is stakes-routed via classify-complexity (C1–C5)... Same metric routes review gates (flux-drive vs melange)")
- **What:** `classify-complexity` (verified in `cmd/clavain-cli/complexity.go:52-115`) scores a single free-text `desc` string via keyword-list matching (trivialKeywords, researchKeywords, ambiguitySignals, simplicitySignals) into one 1-5 score. The doc reuses this *single score* to route two structurally different decisions: ritual ceremony depth (charter interview length + melange trigger) and review-gate choice (flux-drive vs melange) for the *runs inside* the goal. A goal could plausibly be C5 at formation time (broad, ambiguous scope → full ritual) while its individual runs, once well-scoped by the charter, are legitimately C1-C2 for review-gate purposes — or the reverse (a deceptively simple-sounding C1 charter whose execution run turns out gnarly). The doc doesn't say whether goal-level classify-complexity and run-level classify-complexity are the same call, re-evaluated, or inherited.
- **Evidence:** `os/Clavain/cmd/clavain-cli/complexity.go:52-115` (`classifyComplexity(desc string) int` — single string in, single score out, no context distinguishing "goal formation" vs "run review" call sites); `cmd/clavain-cli/complexity.go:227` (epic-with-no-children bump, `cmd/clavain-cli/complexity.go:237` bug-type cap — shows the function already special-cases call-site semantics via bead type, so a goal-vs-run distinction is a precedent-consistent extension, not a new pattern).
- **Suggestion:** State explicitly whether goal-formation classify-complexity is a one-time score stored on the Goal entity (charter-time), and whether run-level review-gate routing re-invokes classify-complexity per-run against the run's own scoped description rather than inheriting the goal's score verbatim — this is a one-line design clarification, not new code.

### bead-binding-optionality-not-checked-against-existing-gate-rules
- **Severity:** P2
- **Where:** §Key Decisions item 3 ("bead binding optional and stakes-scaled — epic for C4/C5 goals, single task bead or none for C1")
- **What:** `internal/phase/gate.go` has existing portfolio/child gate logic keyed on bead-linked run relationships — e.g. line 391-396 resolves `childChain := ResolveChain(child)` and indexes by `rule.phase` for children under a `ParentRunID`, and lines 418-428 pull `dq.GetUpstream`/`pq.GetChildren` for cross-run gate rules. This machinery assumes a run graph exists (parent/child via `ParentRunID`) — it doesn't strictly require a bead, but Key Decision 3's "or none for C1" case means a C1 goal's run(s) could have neither a bead *nor* necessarily a populated `ParentRunID`/`goal_id` gate-rule wiring, if `goal_id` containment (Pillar 2) and `ParentRunID` (existing portfolio field) end up as two parallel containment mechanisms rather than one. The doc doesn't clarify whether `goal_id` reuses `ParentRunID` or is a net-new column, which determines whether existing portfolio gate rules (`gate.go:391-453`) apply to goal-contained runs for free or need parallel new logic.
- **Evidence:** `core/intercore/internal/phase/gate.go:391-396,418-453` (existing parent/child gate-rule resolution via `ParentRunID`); doc §Key Decisions item 3 (`goal_id` on runs) vs. existing `ParentRunID *string` field (`internal/phase/phase.go:203`) — doc never states the relationship between these two fields.
- **Suggestion:** One-line clarification: is `goal_id` a rename/repurposing of `ParentRunID` for goal-scoped containment, or an additional column? If additional, `gate.go`'s existing portfolio-child gate rules (391-453) will need an explicit decision on whether they also traverse `goal_id`-siblings or remain `ParentRunID`-only — otherwise goal-contained runs silently don't get portfolio gate benefits that bead-epic-contained runs already have.

## Verdict
The single highest-confidence finding is concrete and verified in code: `DefaultChain` (`pkg/phase/phase.go:23-35`) has no version field and `ResolveChain` falls through to it for any run without an explicit `Phases` override, so an in-place edit for strategy-absorption is a P0 in-flight-compatibility hazard exactly as this lens's calibration predicts — but the fix is cheap (add a new named chain, stamp `Phases` explicitly on new runs, leave `DefaultChain` alone) since the override mechanism already exists. The interphase-retirement and three-way-ownership open questions are correctly flagged by the doc itself but currently lack the one-line resolution each needs before "staged with internal gates" scope can actually be staged.

## Findings

### no-charter-validation-checkpoint-against-evaluator-constraint
- **Severity:** P1
- **Where:** §What We're Building, Pillar 1, final sentence ("a machine-evaluable completion condition for Claude Code's built-in `/goal` command — written so the Haiku evaluator can judge it from surfaced output... ≤4000 chars, bounded with 'or stop after N turns' where appropriate")
- **What:** The doc states the constraint precisely (surfaced-output-only judging, Haiku evaluator, ≤4000 chars, bounded turns) but never describes a validation step in the ritual that actually checks a drafted condition *against* that constraint before the charter is ratified. The ritual's described mechanics are: research-first → single-question interviews → charter doc → melange review (high-stakes only). None of those four steps is described as "does this condition depend on state the Haiku evaluator can't see (test logs, bead DB queries, metrics, file contents not echoed into the transcript)?" A condition like "the caching layer correctly reduces redundant API calls" would pass through research-first (agent can derive this is a real goal), the single-question interview (user confirms it matters), and — for C1-C3 goals — skip melange entirely (only C4/C5 gets melange per Key Decision 6), reaching ratification with zero mechanical check against the evaluator constraint the whole Pillar 1 design exists to satisfy.
- **Evidence:** doc line 13 (states the constraint: "judges only surfaced output," "≤4000 chars," "or stop after N turns"); doc line 40 (Key Decision 6: only C4/C5 gets melange — meaning C1-C3 charters, i.e. most goals by the doc's own stakes-scaling logic, never get *any* review pass, melange or otherwise, on the condition text before ratification).
- **Suggestion:** Add a fifth, universal (not stakes-scaled) micro-step to the ritual: a cheap mechanical/scripted check — e.g. a linter pass that flags condition text referencing anything not producible as conversational output (grep for "test," "metric," "log," "database," "coverage" combined with a check for whether the charter also stages a step that echoes that evidence into the transcript). This is not a new agent dispatch, just a validation gate before the condition is written to the entity — proportionate to a C1 goal, unlike a melange pass.

### recommended-option-first-has-no-counter-anchoring-mechanism
- **Severity:** P1
- **Where:** §What We're Building, Pillar 1 ("single-question AskUserQuestion interviews (one at a time, recommended option first)")
- **What:** The doc's own rationale for the ritual is that it "maximizes comparative advantage: the user holds intent, stakes, taste... the agent holds research breadth... candidate enumeration" (line 11) — i.e., the design's entire premise is that the user's judgment, not the agent's prior, should steer goal selection. But "recommended option first" is a well-documented anchoring pattern: once a user sees the agent's top pick framed as the default, later options are evaluated relative to it rather than independently. The doc has zero mechanism to detect if this design property is actually working as intended over time (e.g., is the user accepting the first-listed option 95% of the time, which would mean the ritual has degraded into rubber-stamping research rather than genuine steering) versus failing (comparative-advantage premise not actually realized). This is a design property with no closed feedback loop, which matters because the doc elsewhere shows real interest in closing feedback loops — see `feedback_next_goal_same_project.md`-style discipline docs and `capability-routing doctrine` in Sylveste's own AGENTS.md conventions, which this repo already applies to other agent-routing decisions (Interspect calibration, e.g. `interspect:calibrate-audit`).
- **Evidence:** doc line 11 ("the user holds intent, stakes, taste... go/no-go authority" — stated premise); doc line 13 ("recommended option first" — stated mechanic); repo convention precedent: this project already tracks acceptance-rate-style drift elsewhere (`interspect:calibrate-audit` "compare current ranking vs a snapshot from N days ago, flag drift" — the same drift-detection pattern this finding recommends is already a first-class pattern in the codebase, just not applied here).
- **Suggestion:** Reuse the existing interspect-style drift-detection pattern rather than inventing new mechanism: log (agent's first-listed option, user's chosen option) pairs from ritual interviews as evidence, and add a periodic audit (interspect already has the audit primitive) that flags if first-option acceptance rate exceeds some threshold (e.g. >90% over N sessions) as a signal the ritual's single-question ordering may be anchoring rather than eliciting. This is metrics-only, not a UX redesign.

### classify-complexity-conflates-effort-with-spec-risk-for-ceremony-routing
- **Severity:** P2
- **Where:** §Key Decisions item 6 ("Ceremony is stakes-routed via classify-complexity (C1–C5): C1 = one confirming question, no melange")
- **What:** Verified `classifyComplexity` (`cmd/clavain-cli/complexity.go:52-115`) scores purely from text-keyword matching on the goal/bead description: `trivialKeywords` trigger complexity=1 on short descriptions, `researchKeywords` push toward complexity=5, `ambiguitySignals`/`simplicitySignals` nudge the score ±1. This is a linguistic-effort/ambiguity heuristic operating on how the description is *worded*, not a measure of blast radius, reversibility, or specification risk. A goal phrased tersely and confidently ("delete the deprecated auth migration table") would score low (short, no research/ambiguity keywords, high simplicity-signal density) and route to C1's "one confirming question, no melange" — even though the actual risk (irreversible data loss, auth surface) is high. The doc reuses this same score to route review-gate choice too (item 6, "Same metric routes review gates"), doubling the exposure of one effort-proxy metric into two stakes-sensitive decisions.
- **Evidence:** `os/Clavain/cmd/clavain-cli/complexity.go:10-30` (keyword-list definitions — `trivialKeywords`, `researchKeywords`, `ambiguitySignals`, `simplicitySignals` — all operate on description text, none reference bead type risk, file paths touched, or reversibility); `complexity.go:227-237` (existing special-cases: epic-with-no-children bumps complexity, bug-type caps at 3 — shows the function already has precedent for context-aware overrides, meaning a "high blast-radius keyword list" bump would be a consistent, small extension).
- **Suggestion:** Don't build a new risk metric. Extend `classifyComplexity`'s existing override pattern (it already has `tryComplexityOverride` for manual bead-state overrides, `complexity.go:249`) with a small blast-radius keyword bump (e.g. "delete," "migrate," "drop table," "auth," "prod," "irreversible" → +1 or +2, similar weight to the existing `ambiguitySignals` bump) — reuses the existing scoring shape rather than introducing a second parallel metric that the ritual would then need to reconcile against classify-complexity.

### next-goal-seeded-charters-inherit-derivability-boundary-violation
- **Severity:** P2
- **Where:** §Key Decisions item 7 ("Migration of the informal flow: ... next-goal's ranked candidates become draft charters (seeded, not blank-page)")
- **What:** `next-goal.md`'s own ranking (verified: `commands/next-goal.md` Step 2, lines 87-107) is explicitly a *leverage* ranking — `dependent_count`, `priority`, `issue_type`, momentum/proximity to just-shipped work, and `remontoire-promotion` provenance. None of these ranking signals speak to whether the candidate is well-specified, has a derivable completion condition, or has known unknowns the research-first step should surface. Seeding a charter from a `bd ready`-ranked candidate means the ritual's research-first step inherits a *leverage-optimized* starting point, not a *specification-quality*-optimized one — the doc doesn't say whether research-first re-derives from scratch (treating the seed as just a title suggestion) or treats the seed's existing bead description as already-derived context the agent shouldn't re-ask about, which risks skipping genuine derivability gaps that a cold-start charter would have caught via the single-question interview.
- **Evidence:** `os/Clavain/commands/next-goal.md:87-107` (Step 2 ranking signals: `dependent_count`, `priority`, `issue_type`, momentum/proximity, `remontoire-promotion` — all leverage/momentum signals, zero specification-quality or derivability signals); doc §Key Decisions item 7 (states seeding without specifying the research-first re-derivation boundary).
- **Suggestion:** State explicitly in the ritual design that a seeded draft charter still runs the *full* research-first pass against the seed bead (treating its title/description as one more research input, not a shortcut past derivation) — this is a one-sentence clarification in the ritual's entry-point description, not new mechanism, but it closes the gap between "seeded" and "the agent skips research because next-goal already ranked it."

### melange-review-target-ambiguous-doc-vs-fields
- **Severity:** P3 [t]
- **Where:** §Open Questions, "Charter storage shape" ("intercore entity fields vs. companion doc file... and what the melange reviews (the doc) vs. what the kernel gates on (the fields)")
- **What:** The doc's own open question flags this ambiguity, so this is a minor reinforcement rather than a new discovery: melange (verified via `commands/brainstorm.md:146` and `commands/plan-review.md:13-19`) is described project-wide as a document/design review mechanism ("derive the 2-3 proposed approaches from its surfaced findings," "find what makes this plan fail and what it's missing") — it reviews prose for gaps, risk, and disagreement. If "the charter" that gets melange-reviewed is the human-readable doc, that doesn't mechanically validate the machine-evaluable condition text (a structured, character-bounded string) the way a targeted linter would (see the first finding above) — melange is well-suited to catching "this charter's scope is wrong" but not well-suited to catching "this specific condition string references state the Haiku evaluator can't see." The doc's own open question already names this tension; flagging here only to make explicit that the two review mechanisms (melange for prose quality, a mechanical check for evaluator-constraint fit) are not substitutes for each other and both are needed.
- **Evidence:** `os/Clavain/commands/brainstorm.md:146` (melange's actual use pattern — "derive the 2-3 proposed approaches... rather than inventing them inline"); `os/Clavain/commands/plan-review.md:13,19` (melange for "what makes this plan fail and what it's missing" — a gap/risk-hunt frame, not a structured-field validator).
- **Suggestion:** When resolving the open "Charter storage shape" question, explicitly pair it with a statement that melange targets the charter doc/prose (scope, rationale, risk) while a separate mechanical check (per the first finding) targets the condition field — don't let "melange reviews high-stakes charters" be read as covering both jobs.

## Verdict
The two P1s are the load-bearing gaps: the ritual specifies the evaluator constraint precisely (surfaced-output-only, ≤4000 chars) but has no validation step that actually checks a drafted condition against it, and the "recommended option first" mechanic runs directly against the ritual's own comparative-advantage premise with no drift-detection to confirm it isn't quietly anchoring users toward the agent's prior. Both are cheap to close (a mechanical linter-style check; reuse of the project's existing interspect drift-audit pattern) rather than requiring ritual redesign.

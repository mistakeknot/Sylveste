## Findings

### no-fencing-on-two-layer-close
- **Severity:** P0
- **Where:** §Open Questions, "Terminal-gate shape," candidate (a) — two-layer ordered close
- **What:** Candidate (a) proposes "intercore goal close is a kernel-gated ordered sequence verify-against-charter → reflect + compound → next-goal successor proposal, stakes-scaled, evidence on the entity." Nothing in the doc names what prevents two sessions attached to the same goal (`goal_id` on runs, per Key Decision 3) from each independently reaching their own local completion condition and each kernel-gating their own copy of the terminal sequence. `internal/phase/gate.go`'s `evaluateGate` (line 146) and `EvaluateGate` (line 563) operate per-run against `ResolveChain(run)` — there is no cross-run mutex primitive visible in `internal/phase/phase.go`'s `Run` struct (no `lock_holder`, `lease_expires_at`, or `fencing_token` field) that a goal-level close could reuse. `ParentRunID` (phase.go:203) links a child run to a parent but confers no exclusivity.
- **Evidence:** `core/intercore/internal/phase/phase.go:186-208` (Run struct — no lock/lease fields); `core/intercore/internal/phase/gate.go:146,563` (gate evaluation is per-run, no cross-run coordination primitive); doc §Key Decisions item 3 ("Goal → runs directly (`goal_id` on runs)") establishes the 1-goal-to-many-runs shape that makes concurrent closers possible.
- **Suggestion:** Name the concurrency-control primitive explicitly before scoring candidate (a) further — e.g., a `closing_run_id` + `closed_at IS NULL` compare-and-swap column on the Goal entity (single UPDATE...RETURNING as a fencing token, consistent with the project's own "CTE wrapping UPDATE...RETURNING is not supported" constraint noted in intercore's CLAUDE.md — so this must be a direct UPDATE with row-count check, not a CTE). Smallest viable fix: one column + one guarded UPDATE, not a new locking subsystem.

### no-per-step-checkpoint-on-goal-entity
- **Severity:** P0
- **Where:** §Open Questions, "Terminal-gate shape," candidate (a); §What We're Building Pillar 2 ("goals... accumulate close evidence")
- **What:** The doc says the Goal entity "accumulates close evidence" but never specifies that evidence is per-step. If the ordered sequence (verify → reflect+compound → successor) is a single logical operation with only a coarse status, a crash after reflect but before successor-proposal leaves no state distinguishing "goal fully closed" from "goal closed except successor-proposal" — exactly the sprint-level pattern the codebase already has a known bug in: `sprint.md` Step 9's own comment documents that Step 7 and Step 9 both pass `"shipping"` as `currentPhase` to `recordPhaseTokens`, causing silent double-recording under one key (a "known calibration quirk," Sylveste-84sv partial fix). That is a live precedent for exactly this failure class (coarse/shared state key masking a partial multi-step operation) inside this same codebase, not a hypothetical.
- **Evidence:** `os/Clavain/commands/sprint.md:463` ("Note: This advances `shipping → reflect`... Both pass `"shipping"` as `currentPhase` which causes `recordPhaseTokens` to double-record... known calibration quirk (Sylveste-84sv partial fix)"); doc §Open Questions terminal-gate paragraph states only "evidence on the entity" with no per-step schema.
- **Suggestion:** Require the terminal-sequence design to specify a per-step field set on the Goal entity (e.g. `verified_at`, `reflected_at`, `compounded_at`, `successor_proposed_at`, each nullable timestamp) rather than one `closed_at`/`status` bit — a resumer can then run only the missing suffix instead of re-running or silently skipping. This is the direct fix for the Sylveste-84sv-class bug at goal scope before it's inherited.

### session-close-vs-goal-close-cardinality-unresolved
- **Severity:** P1
- **Where:** §What We're Building Pillar 2; §Open Questions "Terminal-gate shape" ("sessions close often, goals span many runs/sessions")
- **What:** `/goal`'s Haiku evaluator is explicitly session-scoped: "cleared on met, restored on resume" (doc line 23). A goal with `goal_id`-linked runs (Key Decision 3) may have N sessions attached, each with its own independently-evaluated `/goal-met` condition instance (since the condition text and evaluator state are per-session per the built-in's own documented behavior). The doc never states whether the *first* session to hit local "met" authoritatively closes the intercore Goal, whether ALL attached sessions must independently hit "met," or whether goal-level closure is a distinct condition evaluated separately from any individual session's local condition. This is a cardinality question, not just a concurrency one — even with perfect fencing (see P0 above), the design doesn't say *what* triggers the fencing attempt.
- **Evidence:** doc line 23 (`/goal` "cleared on met, restored on resume" — session-scoped); doc §Key Decisions item 3 (`goal_id` on runs — one goal, many runs); doc §Open Questions terminal-gate paragraph (acknowledges "sessions close often" but doesn't resolve the trigger question).
- **Suggestion:** Add one explicit rule to the charter/entity design: does the *first* session-level `/goal-met` for a goal-linked session attempt the intercore-level close (treating it as "this session believes the goal is done, attempt terminal sequence," with the fencing mechanism from the P0 finding arbitrating), or is there a separate goal-level completion condition independent of any single session's? Either is workable; the doc currently specifies neither.

### event-driven-shape-has-no-doctrine-owner
- **Severity:** P2
- **Where:** §Open Questions, "Terminal-gate shape," candidate (c) — event-driven, "unordered, individually optional"
- **What:** Candidate (c)'s defining property ("individually optional" consumers) is structurally incompatible with a hard requirement like the successor-proposal doctrine ("never leave a finished goal without a proposed successor" — user's own durable rule, not present anywhere in Clavain's hook code per repo search). If successor-proposal is just one more optional consumer of a goal-close event, there is no code path that fails loudly when it doesn't fire — it degrades to "usually happens," which is the doc's own stated worry ("the successor-proposal doctrine needs enforcement somewhere," line 45) restated as an architectural property of candidate (c) rather than a gap to close.
- **Evidence:** doc line 45 (candidate (c) definition: "unordered, individually optional"); repo-wide grep for "never leave a finished goal" / successor-doctrine enforcement in `os/Clavain/hooks/*.sh` and `commands/*.md` returns no hits — the doctrine currently lives only in user-level CLAUDE.md/memory, confirming it has no code-level enforcement today either, so candidate (c) would perpetuate rather than fix the status quo gap.
- **Suggestion:** If candidate (c) is chosen or scored competitively, split successor-proposal out as a **mandatory** consumer (not "individually optional" like the rest) — i.e., the event-driven shape needs a two-tier consumer model (required vs. optional) rather than uniform optionality, which is effectively a hybrid with candidate (a)'s ordering for at least one step.

## Verdict
The doc correctly identifies the terminal-gate shape as the central open question and correctly flags the tension between session-scoped `/goal` and goal-scoped closure, but stops short of naming any concurrency-control primitive or per-step checkpoint schema — both are P0-grade gaps given the doc's own admission that "sessions close often." The requested alternative shapes (lease/heartbeat, escrowed-async-verify, successor-as-obligation) are not yet present in the doc text at all and need to be scored, not just gestured at, before melange can adjudicate.

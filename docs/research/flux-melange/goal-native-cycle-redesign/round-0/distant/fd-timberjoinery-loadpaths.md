## Findings

### session-scoped-sentinel-is-a-single-shearing-fastener
- **Severity:** P1
- **Where:** `os/Clavain/hooks/auto-stop-actions.sh:135-146` calling `intercore_sentinel_check_or_legacy "goal_cadence_throttle" "$SESSION_ID" 60` (function defined `os/Clavain/hooks/lib-intercore.sh:63-81`)
- **What:** The entire goal-cadence enforcement mechanism — the only load path that currently fires the next-goal/successor-proposal instruction — is scoped to `$SESSION_ID` with a 60-second interval, and is fail-open (`intercore_available` false → `return 0`, i.e. silently allow/skip). This is a single fastener, not a joint: it has no goal identity in its key at all today. The doc's Key Decision 7 ("goal-cadence Stop-hook tier reads the entity instead of regex-matching prose") swaps the *trigger* (regex → entity lookup) but the surrounding member — a session-keyed, fail-open, 60s-interval sentinel — is untouched by that plan.
- **Evidence:** Read `hooks/lib-intercore.sh:67-81`: `intercore_sentinel_check_or_legacy` returns `0` (allowed/fail-open) whenever `intercore_available` is false, and returns `0`/`1` based on `ic sentinel check <name> <scope_id> --interval=<interval>` otherwise. The scope_id passed for goal-cadence is literally `"$SESSION_ID"` (`auto-stop-actions.sh:142`), and the doc-cited `lib-signals.sh:84`'s comment even says the signal is "weight 0 — structural trigger" fired independently, i.e. this is already known to be a special, singular path.
- **Suggestion:** Trace the concrete load path: goal minted → runs attach → session A closes (sentinel scope=`session-A`, fires or is throttled) → session B resumes the same goal minutes later (sentinel scope=`session-B`, fresh — no memory of A's throttle state) → session B closes again. If two sessions close inside the same 60s window under different `$SESSION_ID`s, the throttle does nothing to prevent duplicate next-goal fires; if intercore is briefly unavailable during the *only* session-close that happens to correspond to true goal completion, the obligation silently fails open and no successor is ever proposed. Before landing "Goal reads the entity", re-key the sentinel scope to `goal_id` (or a goal_id+session_id compound) so the throttle's un-reversible failure mode (fail-open silently drops the obligation) is at minimum scoped to the entity whose lifetime the obligation is supposed to span, not the session's.

### existing-lock-coordination-primitive-omitted-from-lease-heartbeat-search
- **Severity:** P1
- **Where:** `core/intercore/internal/lock/lock.go:1-50`, `core/intercore/cmd/ic/lock.go:17-36` (`ic lock acquire/release/list/stale/clean`), and the separate `ic coordination reserve/release/check/list/sweep/transfer` family (`cmd/ic/coordination.go`)
- **What:** The task explicitly asks to "surface and score terminal-gate shapes BEYOND the three candidates... e.g. lease/heartbeat models." intercore already ships exactly this joinery pattern — a filesystem-based lock with `Owner`, `PID`, `Host`, `Created`, a `DefaultStaleAge` (5s) for the raw mutex, plus a separate `stale`/`clean` sweep subcommand family — and a second, apparently goal-adjacent `coordination reserve/release/check/list/sweep/transfer` verb set. Neither is mentioned anywhere in the brainstorm's terminal-gate discussion. This is the single closest piece of load-bearing precedent for a lease/heartbeat terminal-gate shape (an escrowed "goal is being closed by session X, expires at T, renewable" record) and evaluating alternatives without citing it risks re-cutting a joint the frame already has.
- **Evidence:** `internal/lock/lock.go:15-19` (`DefaultStaleAge = 5 * time.Second`, `DefaultMaxWait`, `DefaultRetryWait`) and `cmd/ic/lock.go:19` (`stale`, `clean` subcommands) show a working stale-detection + reap cycle already exists at second-granularity; `coordination.go` shows a second, separate `reserve/transfer/sweep` vocabulary that is closer in shape (transfer = a lease can move owners) to what a goal-scale "who currently owns closing this goal" lease would need.
- **Suggestion:** Before scoring a novel lease/heartbeat terminal-gate shape from scratch, spend one research pass asking whether `ic coordination reserve <goal_id> --owner=<session_id> --ttl=<goal-scale-duration>` (goal-scale TTL, not the 5s lock default) is a viable *extension* of the existing coordination primitive rather than a new subsystem — reuse the existing `transfer` verb for "goal handed to a new session mid-run," and the existing `sweep` verb for reaping abandoned goal-close attempts. If it's rejected, say why explicitly (e.g. "coordination is file/second scale, goals need DB/day scale") rather than silently not considering it.

### interphase-and-kernel-chain-are-two-incompatible-phase-vocabularies
- **Severity:** P1
- **Where:** `interverse/interphase/docs/interphase-vision.md:8-10` (8-step: brainstorm, brainstorm-reviewed, strategized, planned, plan-reviewed, executing, shipping, done) vs. `core/intercore/pkg/phase/phase.go:22-33` (`DefaultChain`, 9-step: Brainstorm, BrainstormReviewed, Strategized, Planned, Executing, Review, Polish, Reflect, Done)
- **What:** The doc frames interphase retirement as swapping out one "load-bearing member people see daily (statusline)" while "keeping the display." But interphase isn't gating the same chain the kernel gates — it has its own 8-phase vocabulary (no `review`/`polish`/`reflect` split; has `plan-reviewed` where the kernel doesn't) written to bead state (`bd`) plus a sideband JSON contract (`~/.interband/interphase/bead/${session_id}.json`) that interline statusline reads. interphase also has its own fail-open/fail-closed gate semantics (`CLAVAIN_GATE_FAIL_CLOSED`, `CLAVAIN_SKIP_GATE`) that are bead-scoped, not run-scoped or goal-scoped. "Retire interphase, keep the display" requires deciding whose phase vocabulary the display now reflects — the kernel chain (run-scoped, may not exist for a bead not yet run-attached) or the new Goal entity (goal-scoped, doesn't map 1:1 onto bead phases either) — and the doc's open question treats this as a "consumer story" problem when it's actually a vocabulary-reconciliation problem first.
- **Evidence:** interphase's own CLAUDE.md: "Libraries are sourced by consuming plugins... via shim delegation" and "Legacy mode is fail-safe/fail-open... Strict mode is opt-in and fail-closed for hard-tier." This is bead-keyed strict/lenient policy independent of intercore's run-keyed `GateRules map[string][]SpecGateRule` (`internal/phase/phase.go:207`). Two independent gate-policy engines currently coexist; collapsing one into "just a display" doesn't remove the second policy engine's authority over what actually gets recorded to `bd state`.
- **Suggestion:** Before retiring interphase, name explicitly which entity (bead / run / goal) owns phase-of-record once interphase's gate authority is withdrawn, and confirm `_gate_update_statusline()`'s sideband writer is re-pointed at that entity's transitions rather than left to silently stop firing (a withdrawn joint that leaves the visible display frozen at its last state, rather than reversibly removed, reads as a glued joint, not a floating one).

### strategy-phase-0.5-reconciliation-logic-has-no-named-landing-spot-in-the-ritual
- **Severity:** P2
- **Where:** `os/Clavain/commands/strategy.md:16,26,86-88,209-228` (Phase 0.5: Shipped-State Reconciliation, subsume/supersede/orthogonal verdicts) vs. brainstorm Key Decision 5 ("strategy's real jobs... migrate into the ritual's research phase")
- **What:** Phase 0.5 is not a loose "job" of strategy — it is a named, gated phase with its own checklist item, its own artifact (`artifact_reconciliation:`), and canonical precedent (`sylveste-9gn9`, cited in strategy.md itself, cut ~40% of a planned epic via a subsume verdict). The brainstorm's own Open Questions section treats sylveste-lbkd/sylveste-3kol reconciliation as something "strategy Phase 0.5 enforces... as a hard gate downstream" — but Key Decision 5 says strategy (and by extension Phase 0.5) is being diet-ed away, with its verdict logic "migrating into the ritual's research phase." These two statements aren't reconciled: does the ritual's research phase re-implement Phase 0.5's hard-gate enforcement (blocking ratification on an unresolved subsume verdict), or does it only surface the verdict as information? If only the latter, the "hard gate" downstream is lost when strategized is collapsed.
- **Evidence:** `strategy.md:88`: "Skipping this is how parallel implementations and redundant rebuilds of sunk work happen" — Phase 0.5 exists because of a specific, named prior failure. The doc's own Open Question #2 asks for "an evidence-based verdict" on lbkd/3kol via "strategy Phase 0.5" as if that phase still exists as the enforcement mechanism, while Key Decision 5 says it's absorbed away.
- **Suggestion:** State explicitly in the ritual design which member carries Phase 0.5's *hard-gate* property (not just its verdict-generation logic) forward — e.g., "the charter cannot be ratified while an unresolved subsume/supersede verdict exists on an adjacent open tracker" as a melange-review precondition — or accept and document that the hard gate is being softened to advisory as part of the diet.

### two-strikes-escalation-ladder-not-considered-as-a-terminal-gate-precedent
- **Severity:** P3
- **Where:** `core/intercore/internal/dispatch/escalate.go:34-52` (`DefaultEscalationPolicy`: `StrikesPerRung: 2`, `MaxEscalations: 2`, `Ladder: []string{"sonnet", "opus", "fable"}`)
- **What:** This finding is offered as a design-taste note, not a defect: the shipped two-strikes ladder is a clean precedent for "retry N times at this rung, then escalate, cap total escalations" — structurally similar to what an escrowed-close-with-async-verify terminal gate needs (verify-against-charter fails → retry N → escalate to a higher-stakes reviewer/melange rather than looping cheap retries forever). Citing it by name would let the terminal-gate scoring section reuse a vetted vocabulary (rung, strike, escalation cap) instead of inventing new terms for the same shape.
- **Evidence:** `escalate.go:39-49` doc comment: "two strikes at the base tier, then one attempt per higher rung" with an explicit guard field `MaxEscalations` "vs oscillation" — this guard-against-oscillation concern is exactly the failure mode an escrowed-verify terminal gate must avoid (repeatedly bouncing a goal between "pending verify" and "reopened").
- **Suggestion:** When scoring the escrowed-close-with-async-verify candidate, reference `DefaultEscalationPolicy`'s shape (strikes-per-rung, max-escalations-total) as the naming/parameter convention to reuse, rather than a from-scratch retry policy. [t]

## Verdict
The design's load paths concentrate force on a session-scoped, fail-open sentinel that has no memory across the many session-closes a goal is defined to span — this is the P1 core finding, and it directly informs the terminal-gate scoring the user prioritized. Two real, existing reversible-joint precedents (the `ic lock`/`ic coordination` stale/sweep/transfer primitives, and the escalate.go two-strikes ladder) are available in-repo and unused in the doc's exploration of lease/heartbeat and escrow shapes; citing and either adopting-or-explicitly-rejecting them would ground the melange review in load-bearing fact rather than de novo design. The interphase-retirement and strategy-Phase-0.5-absorption seams both have real vocabulary/enforcement mismatches (8-step vs 9-step chains; hard-gate vs advisory verdict) that the doc's "consumer story" and "chain change" framing understate.

## Findings

### fail-open-sentinel-resuspends-the-successor-obligation-on-every-flush
- **Severity:** P1
- **Where:** `os/Clavain/hooks/lib-intercore.sh:63-81` (`intercore_sentinel_check_or_legacy`), consumed at `os/Clavain/hooks/auto-stop-actions.sh:135-146`
- **What:** The successor-proposal doctrine ("never leave a finished goal without a proposed successor") is the one obligation the doc explicitly says "needs enforcement somewhere." Today's *entire* enforcement path is a single sentinel check that fails open: `if ! intercore_available; then return 0` — i.e., if `ic` is briefly down, unreachable, or mid-migration (the doc's own "clavain-cli Go port mid-migration" open question) at the exact moment a goal-completing session closes, the next-goal instruction never fires and no residence-time check catches the loss. This is a deposition event with zero consolidation guarantee: the sediment (the obligation) is created and immediately flushed if the current (infra availability) happens to be running fast at that instant.
- **Evidence:** `lib-intercore.sh:74-76`: "NOTE: ic is now required. If unavailable, returns 0 (fail-open: allow the action)." comment on `intercore_sentinel_check_or_legacy`. The doc's own research section flags "clavain-cli Go port mid-migration" as an open transition-ownership risk — meaning the exact window where `ic`/`intercore` availability is least certain (mid-migration) is also the window where this obligation is least likely to be honored.
- **Suggestion:** Reason in rates: state the goal-cadence sentinel's deposition rate (once per goal-completing session-close), its residence time under the current design (zero — a single missed check and the obligation is gone with no retry), and add a durable, goal-scoped "successor pending" flag written to the Goal entity itself at formation-of-completion time, checked by an independent slow-settling sweep (e.g., a periodic `next-goal` audit over `ic goal list --status=done --successor=none`) rather than relying solely on the fast, fail-open Stop-hook current.

### two-layer-candidate-has-no-stated-settling-time-for-slow-materials
- **Severity:** P1
- **Where:** Doc §Open Questions, Terminal-gate shape candidate (a): "kernel-gated ordered sequence verify-against-charter → reflect + compound → next-goal successor proposal"; cross-referenced against `os/Clavain/commands/sprint.md:451-483` (Step 9: Reflect) and `os/Clavain/hooks/auto-stop-actions.sh:135-166` (goal-cadence tier fires ahead of compound tier, weight≥4 gate)
- **What:** `sprint.md` shows reflect is not instantaneous: Step 10 explicitly gates on a reflect artifact existing and having a minimum "3 substantive body lines" (`sprint.md:481-483`), erroring out ("ERROR: Step 10 requires a reflect artifact. Run /reflect first.") if it hasn't consolidated yet. Candidate (a) describes this as one link in a synchronous "ordered sequence," but the sprint machinery it's built on top of already treats reflect as a slow-settling material that can legitimately not be ready yet and must block downstream. The doc doesn't say what a kernel-gated terminal sequence does when reflect/compound haven't consolidated at the moment the goal-closing session ends — does the gate hold the session open (bad: sessions close often, that's the whole premise), does it degrade to "mark pending, close anyway" (then who resweeps it — same gap as the successor-obligation finding above), or does it force reflect to run synchronously inside the closing turn (risking exactly the "instantaneous deposition" failure mode this lens flags)?
- **Evidence:** `sprint.md:459`: "If resolve has no blocking findings... resolve and reflect can run in parallel... Sprint waits for both artifacts before advancing" — i.e. the existing kernel already has precedent for *waiting* (residence time) rather than forcing instant deposition, but that precedent is a synchronous same-session wait, not a cross-session one. Candidate (a) needs to say whether goal-close reflect/compound reuse that same-session wait pattern (won't work — goal spans many sessions, reflect belongs to whichever session is closing) or introduce an async consolidation record.
- **Suggestion:** For terminal-gate scoring, name each material's settling time explicitly: verify-against-charter (fast — can be evaluated from surfaced output per the `/goal` Haiku-evaluator constraint the doc itself cites), reflect+compound (slow — gated on artifact minimum-content checks today), successor-proposal (fast to *propose*, but the doc's own doctrine wants it non-skippable). A shape that treats all three as one ordered synchronous chain will either stall session close (violates "sessions close often") or silently skip the slow ones (recreates the ghost-channel risk already present in today's independent-trigger design, which the doc itself criticizes as "four independent triggers").

### interphase-sideband-is-a-second-uncoordinated-tidal-regime
- **Severity:** P1
- **Where:** `interverse/interphase/docs/interphase-vision.md:14-17` ("Gate state is written as structured sideband to `~/.interband/interphase/bead/${session_id}.json`... with no direct coupling between the two plugins") vs. proposed Goal entity persistence (intercore DB) and kernel `GateRules` (`core/intercore/internal/phase/phase.go:207`)
- **What:** There are, today, at least three independent deposition clocks writing phase-adjacent sediment: (1) the kernel chain's `PhaseEvent` audit log inside intercore's own DB (durable, consolidated), (2) interphase's bead-state + JSONL telemetry writes plus its statusline sideband file (bead-scoped, file-based, explicitly "no direct coupling"), and (3) the proposed Goal entity's own close-evidence accumulation. The doc frames interphase retirement as swapping a display member, but the sedimentology question is sharper: interphase's design principle #1 is "Transitions are receipts, not cursor state... If it didn't produce a receipt, it didn't happen" — this is itself a consolidation guarantee (interphase's docs claim durability). Withdrawing interphase without an explicit migration of *that specific guarantee* onto the Goal entity's evidence model risks a regression: today's bead-phase receipts are durable-by-design; a goal-scoped record that only writes evidence on the (fail-open, session-scoped, per finding 1) goal-cadence path is durable-by-accident.
- **Evidence:** interphase's own CLAUDE.md: "Legacy mode is fail-safe/fail-open for dependency errors... Strict mode is opt-in and fail-closed for hard-tier." — interphase already made a deliberate settling-time choice (strict mode for P0/P1 beads) that the goal-native redesign's fail-open sentinel does not yet have an equivalent for at goal scale.
- **Suggestion:** Before retiring interphase, name which of its three consolidation guarantees (bead-state receipt, JSONL telemetry line, sideband display payload) the Goal entity inherits and via what event, and confirm at least one of them is fail-closed for high-stakes (C4/C5) goals — mirroring interphase's own `CLAVAIN_GATE_FAIL_CLOSED` precedent — rather than uniformly fail-open like the current goal-cadence sentinel.

### ghost-goal-risk-not-enumerated-for-the-abandoned-mid-ritual-charter
- **Severity:** P2
- **Where:** Doc §What We're Building, Pillar 1 (research-first → single-question interviews → charter → melange review for high-stakes charters); no corresponding entry in §Open Questions
- **What:** The doc enumerates ghost-channel risk at the *back* end (successor-proposal doctrine, terminal-gate shapes) in detail, but not at the *front* end. A high-stakes (C4/C5) charter formation explicitly routes through melange review before ratification — a multi-turn, potentially multi-session deposition process. If the session forming the charter ends (context flush) before melange review completes and the entity is minted, what happens to the partially-formed charter? Is it itself a durable, resumable deposit (a draft Goal row with `status=forming`), or does it live only in session transcript / a companion doc that resuspends on close, forcing the next session to re-run the whole comparative-advantage interview from scratch? This is the same class of risk the doc already takes seriously for terminal close, unaddressed for terminal *open*.
- **Evidence:** Key Decision 2 describes the ritual mechanics but the doc's Open Questions "Charter storage shape" question asks only about the *final* storage split (entity fields vs. companion doc vs. both) — not about the in-flight, pre-ratification state. Rationale section frames goal quality as "the highest-leverage variable in the cycle," which argues the formation process itself deserves the same settling-time rigor as closure.
- **Suggestion:** Add an explicit "draft charter" deposit state to the Charter storage design — even a lightweight one (companion doc path recorded against the initiating session/bead) — so a C4/C5 ritual interrupted mid-melange-review has a resumable sediment layer rather than fully resuspending on the next session's flush tide.

### behavioral-memory-subsidence-cadence-not-matched-to-ritual-cadence
- **Severity:** P3
- **Where:** Doc Rationale paragraph: "institutionalizes what currently exists only as behavioral memory ('propose ambitious goals', 'finish design calls before executing', 'next-goal freshness check')" — cross-referenced against `/Users/sma/.claude/projects/-Users-sma-projects/memory/MEMORY.md` feedback entries of the same names
- **What:** Offered as a design-taste observation: these three behavioral rules currently live in auto-memory (an accreting, user-correction-driven substrate that can gain new nuance or be superseded at any time via feedback capture) and the doc proposes freezing versions of them into the ritual's structure. Once institutionalized, does the ritual's hard-coded form re-read auto-memory at each ritual invocation (keeping the two substrates synchronized, deposition rate = ritual-invocation rate) or does it fork a point-in-time snapshot (deposition rate = zero after ship, and the two copies begin to diverge the next time an auto-memory feedback file like `feedback_ambitious_goals.md` is corrected)? Not flagged as P1/P2 because divergence here degrades quality slowly rather than causing acute loss, but worth naming explicitly given the design otherwise cares about exactly this kind of substrate-consolidation mismatch.
- **Evidence:** `feedback_next_goal_freshness_check.md` and `feedback_ambitious_goals.md` are both named as *currently live, correctable* memory files in the user's MEMORY.md index — i.e., they are demonstrably still an accreting substrate, not settled doctrine, at the time this brainstorm is being reviewed.
- **Suggestion:** State in the ritual design whether hard-coded ritual steps derived from behavioral memory are meant to be periodically re-synced from the memory substrate (e.g., as part of a doc-drift/interwatch pass) or intentionally forked at design time; either is defensible, but leaving it unstated risks silent doctrine drift between the two. ## Verdict
The redesign's single highest-leverage settling failure is structural: the one mechanism enforcing the successor-proposal doctrine is a fail-open, session-scoped sentinel with zero residence time, so an ordinary infra hiccup (plausible given the doc's own "clavain-cli Go port mid-migration" caveat) silently erodes the exact obligation the doc says most needs enforcement. The terminal-gate candidates need explicit per-material settling times (verify is fast, reflect/compound are demonstrably slow per the existing sprint.md gate), and the interphase-retirement plan should name which of interphase's own consolidation guarantees (receipts over cursor state, fail-closed for hard-tier) the Goal entity inherits rather than treating retirement as a pure display swap.

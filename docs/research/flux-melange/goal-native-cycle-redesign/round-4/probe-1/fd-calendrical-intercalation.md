## Findings

### entity-read-still-fast-clock-triggered
- **Severity:** P1
- **Where:** docs/brainstorms/2026-07-18-goal-native-cycle-brainstorm.md §Key Decisions item 7 (line 41); §What We're Building Pillar 2 (line 15); mechanism today: os/Clavain/hooks/lib-signals.sh:19-25 (`goal-completed` signal def), lib-signals.sh:83 (`grep -iq '/goal\b.*\(complet\|done\|shipped\|landed\)\|...'`), os/Clavain/hooks/auto-stop-actions.sh:140-146 (goal-cadence tier keyed on `$SIGNALS == *"goal-completed"*`)
- **What:** The doc's own migration decision says the goal-cadence Stop-hook tier will read the Goal entity "instead of regex-matching prose" — correctly diagnosing that a text-pattern match is the wrong oracle. But this only swaps the OBJECT being consulted (entity fields vs. transcript text); it does not swap the CLOCK that triggers the consultation. As written, the entity-read still only happens when a session's Stop hook fires and that session's own transcript happens to trip whatever new detector replaces the `grep -iq` — i.e., the fast, per-session-close cadence remains the sole occasion for re-observation. A calendar reform that renames what you're looking at without changing when you look is not re-anchoring; it's the same computed-from-start-count hazard wearing a better sensor. If no session touching that Goal closes with goal-shaped language for an entire season, the entity is never re-read by anything, regardless of how faithful the entity's own fields are.
- **Evidence:** lib-signals.sh:19-25 documents `goal-completed` as "weight 0 by design: this is a STRUCTURAL trigger... not meant to add to the compound/drift weight ladder" — i.e., it is explicitly NOT continuously monitored the way weighted signals are; it only fires opportunistically inside whichever session's Stop hook happens to run the regex. auto-stop-actions.sh:140-146 shows the goal-cadence tier is nested entirely inside a per-session Stop-hook invocation (`$SESSION_ID`-scoped sentinel at line 142) — there is no separate, session-independent scheduler that ever asks "has any Goal gone quiet." The doc's Key Decision 7 fix targets the oracle (prose → entity) but the surrounding trigger architecture (Stop hook, per-session, opportunistic) is untouched by that decision, and none of the three terminal-gate candidates in §Open Questions add an independent trigger either — all three (two-layer close, single-layer /goal-met, event-driven consumers) are still occasioned by *some session's* local completion event, not by a standing scheduler re-observing the Goal.
- **Suggestion:** Name explicitly, in the terminal-gate decision, what re-observes Goal entities that no attached session ever closes cleanly — e.g., a `bd doctor`-style periodic sweep, or a check folded into `/clavain:next-goal` itself when invoked standalone (already "safe and encouraged to invoke manually" per next-goal.md:20-21) that also audits OTHER open Goals for staleness, not just proposes a successor to the one just closed. This is the smallest viable fix: piggyback the sweep on an existing manually-invocable command rather than building new scheduling infrastructure.

### no-epact-on-goal-entity
- **Severity:** P1
- **Where:** docs/brainstorms/2026-07-18-goal-native-cycle-brainstorm.md §Key Decisions items 1-3 (lines 35-37); §What We're Building Pillar 2 (line 15, "goals contain runs, carry the charter, accumulate close evidence"); current code has no analog — core/intercore/internal/phase/phase.go:186-208 (`Run` struct has no `GoalID`, no staleness/last-advanced field)
- **What:** The doc specifies what the Goal entity CONTAINS (charter, scope, acceptance criteria, adjacent-work verdicts, close evidence) but never a standing number whose sole job is to make drift legible: something like "sessions since a run last advanced this Goal" or "runs owed vs. runs observed this cycle." A calendar keeper without a carried epact can be handed a perfectly reconciled calendar today and have no way to tell, six months from now, whether it has quietly slipped — the keeper has to re-derive drift from first principles every time, which nobody does under routine load. Every terminal-gate candidate in §Open Questions (two-layer, single-layer, event-driven) is described purely as a triggered ACTION sequence; none of them specify a passively-readable STATE field on the Goal that would let a human or a sweep (see the epact-detection suggestion above) answer "is this Goal actually dormant?" without replaying its full run history.
- **Evidence:** §Key Decisions item 1 defines the Goal ontology choice (new entity vs. parent-run vs. label) but not its schema beyond "contains runs." §Pillar 2 lists three retained artifacts (charter, runs, close evidence) — all either write-once or accumulate-on-close, none of which is a live/updated counter a dormancy-sweep could cheaply query. Compare to intercore's own `sentinel.Store` (core/intercore/internal/sentinel/sentinel.go:12-16), which DOES carry exactly this kind of epact — `last_fired` per (name, scope_id) — precisely so throttle staleness is a single-column read rather than a derived computation; the Goal entity design as currently sketched has no equivalent for goal-level staleness.
- **Suggestion:** Add one field to the eventual `ic goal` schema — `last_run_advanced_at` (or equivalent) updated whenever any attached run makes chain-transition progress — so "is this Goal drifting?" becomes a single comparison (`now - last_run_advanced_at > threshold`) rather than a query needing to reconstruct history from the runs table. This is additive to the existing Key Decision 1-3 schema sketch, not a redesign of it.

### weight-zero-signal-is-the-observed-phenomenon
- **Severity:** P2
- **Where:** os/Clavain/hooks/lib-signals.sh:19-25 (signal weight table — `goal-completed (weight 0)` is the sole zero-weight, "structural trigger" signal among commit/resolution/investigation/bead-closed/recovery/version-bump, all weighted 1-2); lib-signals.sh:83 (the regex itself)
- **What:** Every other signal in the waterfall (commit, resolution, bead-closed, etc.) contributes to a WEIGHT that other tiers (compound, drift-check) compare against a threshold — i.e., those corrections require accumulated corroborating evidence before firing. `goal-completed` alone is wired to fire the single highest-priority tier (goal-cadence, which "short-circuits the rest of the waterfall" per auto-stop-actions.sh:121-123) off ONE unweighted regex match, with no corroboration requirement at all. In calendrical terms: every other correction requires the astronomer-priest to see multiple confirming omens before declaring the intercalary month; the goal-completion correction fires off a single sighting, unconfirmed, and top-priority. This is consistent with the doc's stated intent (goal-completion should always short-circuit), but it means the entire redesign's terminal-gate machinery inherits a single point of unweighted, unconfirmed textual triggering at its root, regardless of which terminal-gate shape (a/b/c or a new one) sits downstream of it.
- **Evidence:** lib-signals.sh:19-25's own comment: "Weight 0 by design: this is a STRUCTURAL trigger... not meant to add to the compound/drift weight ladder." auto-stop-actions.sh:120-123 confirms goal-cadence "takes top priority and short-circuits the rest of the waterfall" specifically because it's treated as a structural requirement, not a corroborated signal.
- **Suggestion:** Not urgent to fix (the doc's Key Decision 7 already plans to replace prose-regex with entity-reads, which subsumes this concern) — but worth naming explicitly in the terminal-gate write-up as the reason the entity-read migration matters beyond precision: it also upgrades the trigger from single-sighting to corroborated-by-durable-state.

## Verdict
The doc has already named its own fix direction for the two-clock problem (Key Decision 7: read the entity, not the prose) but has not yet designed the SCHEDULE that fix runs on, nor given the Goal entity a standing counter that would make drift detectable independent of any session's willingness to look. Both gaps are additive, small-diff fixes to the existing schema and command surface, not architecture changes — but without them, the "reads the entity" migration inherits the same fast-clock-only triggering it was meant to escape.

## Findings

### sentinel-not-lock-adjudication-holds
- **Severity**: P1
- **Where**: docs/brainstorms/2026-07-18-goal-native-cycle-brainstorm.md §Open Questions 'Terminal-gate shape' (line 45); core/intercore/internal/sentinel/sentinel.go:32-85; core/intercore/internal/lock/lock.go:29-51,104-184
- **What**: This is not an irreducible taste call — it is adjudicable from the code, and finding (1) is the one that holds. Finding (2)'s claim that intercore "already contains two tested, durable single-point-of-no-return primitives" that "are mechanistically the lease/heartbeat model" conflates two structurally different mechanisms under one label. Verified directly:
  - `sentinel.Store.Check` (sentinel.go:35-85) is a DB-transactional atomic *throttle*: it claims a fire-once-per-interval slot with `INSERT OR IGNORE` + conditional `UPDATE ... RETURNING`, inside one SQLite transaction. It has no `Owner`/`PID`/`Host` fields (contrast `lock.Lock` at lock.go:30-37), no `Release` call, no concept of a holder that can be checked for liveness or ownership. Once claimed, a sentinel just sits until it ages out via `Prune`/auto-prune (sentinel.go:76-79, 118-128) — there is no "am I still the one working on this" semantics at all. That is not a lease; it is a rate-limit gate.
  - `lock.Manager` (lock.go:29-51) genuinely has lease shape: `Owner`/`PID`/`Host` metadata written at acquire (lock.go:284-310), `Release` that enforces `ErrNotOwner` when the caller isn't the recorded owner (lock.go:175-177), and staleness recovery via `tryBreakStale` + `pidAlive` liveness checking (lock.go:259-282, 329-352) — the actual heartbeat/lease primitive PRIORITY-1 is asking to be surfaced.
  - Grounding the mechanism risk: the one call site wired into the goal-cadence Stop-hook path (os/Clavain/hooks/auto-stop-actions.sh:142, `intercore_sentinel_check_or_legacy "goal_cadence_throttle" "$SESSION_ID" 60`) uses **sentinel**, not lock.Manager — a session-scoped, 60-second interval throttle that fires an instruction to run `/clavain:next-goal`, not a multi-step transactional gate around a close sequence. So (2)'s framing — "two primitives, both mechanistically the lease model, already durable and tested for this purpose" — overstates sentinel's fitness and, by bundling it with lock.Manager under one description, risks a design that reaches for the already-wired-in but wrong primitive (sentinel) by analogy, exactly the risk (1) names.
  - Where (2) still has a point: the terminal-gate open question (line 45) does propose lease/heartbeat as if from a blank slate, and lock.Manager is a real, tested, durable primitive of exactly that shape sitting unreferenced in the same repo. (2)'s underlying observation — "the doc didn't survey what already exists before inventing" — is correct and worth keeping. What doesn't survive is the claim that *both* primitives are equally lease-shaped and equally ready to reuse.
- **Evidence**: sentinel.go:12-16 (`Sentinel` struct: `Name`, `ScopeID`, `LastFired` — no owner/PID/host), sentinel.go:32-34 (doc comment: "atomic claim-if-eligible throttle check"), sentinel.go:87-96 (`Reset`, not `Release` — no ownership check); lock.go:30-37 (`Lock` struct has `Owner`/`PID`/`Host`/`Created`), lock.go:153-184 (`Release` checks `meta.Owner != owner` → `ErrNotOwner`), lock.go:259-282 (`Clean` + `pidAlive` liveness), lock.go:325-352 (`tryBreakStale`); os/Clavain/hooks/auto-stop-actions.sh:142 (sentinel call site, keyed by `SESSION_ID`, 60s interval).
- **Suggestion**: When drafting the lease/heartbeat terminal-gate candidate for melange, cite `lock.Manager` specifically (not "sentinel/lock" as an interchangeable pair) as the closest existing primitive, and treat its 5s `DefaultStaleAge` + no-fencing-token gap (already flagged in a separate settled fact) as the concrete adaptation problem to solve — not a reason to reinvent from zero, and not a reason to assume it's plug-and-play either.

### neither-primitive-clears-fencing-bar
- **Severity**: P2
- **Where**: docs/brainstorms/2026-07-18-goal-native-cycle-brainstorm.md §Open Questions 'Terminal-gate shape' (line 45); core/intercore/internal/lock/lock.go:15-20,325-352
- **What**: The adjudication above resolves which primitive is lease-shaped, but it exposes a sharper point neither original finding states outright: even the correct primitive (lock.Manager) does not clear the bar the terminal-gate actually needs. A terminal-gate close sequence is explicitly multi-step and spans LLM calls (per the doc's own candidate (a): verify-against-charter → reflect+compound → next-goal proposal). `lock.Manager` has no fencing/generation token (already a settled fact) and only a 5-second `DefaultStaleAge` (lock.go:17) — sized for short filesystem-lock hold times, not for a sequence that could plausibly run tens of seconds to minutes across model calls. So "reference lock.Manager instead of sentinel" is necessary corrective guidance but not sufficient: a naive `Acquire`-at-start/`Release`-at-end wrap of the existing primitive would either time out mid-sequence on legitimate slow calls (spurious stale-break by a second contender) or require raising `StaleAge` so high that genuine crash recovery becomes slow — the fencing-token gap has to be designed in, not inherited by pointing at the right file.
- **Evidence**: lock.go:17 (`DefaultStaleAge = 5 * time.Second`); lock.go:106-151 (`Acquire` — single spin-wait acquire, no session/step handle returned for incremental renewal); lock.go:329-352 (`tryBreakStale` — breaks on elapsed time alone, no generation check against the sequence's current step).
- **Suggestion**: Treat "adapt lock.Manager" as a starting point that still needs (a) a fencing/generation token minted at acquire and checked before each step's write, and (b) either a heartbeat-renewal call between steps or a staleness window sized to the slowest realistic close sequence — spell this out as a requirement in the melange brief for the lease/heartbeat candidate rather than letting "already exists" read as "already sufficient."

## Verdict
Finding (1) holds: sentinel and lock.Manager are not mechanistically equivalent, and (2)'s bundling of them as an interchangeable "lease/heartbeat" pair overstates sentinel's fitness and risks aby-analogy design reaching for the wrong (already-wired) primitive. This is a fact-checkable code question, not taste. (2)'s narrower point — that a real, tested, durable lease primitive already exists in-repo and the terminal-gate open question didn't reference it — survives and should carry forward into the melange candidate list, with the caveat (new insight above) that lock.Manager itself still needs a fencing token and a longer/renewable staleness model before it's usable as the terminal-gate's lock, not just relabeled and pointed at.

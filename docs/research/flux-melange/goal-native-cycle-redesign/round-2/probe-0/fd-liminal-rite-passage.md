## Findings

### durable-primitives-unconsulted
- **Severity:** P1
- **Where:** `core/intercore/internal/sentinel/sentinel.go:32-50` (`Store.Check`, atomic claim-if-eligible via `BeginTx` + conditional `UPDATE...RETURNING`); `core/intercore/internal/lock/lock.go:15-20,47-51,233-254` (`Manager`, `DefaultStaleAge`, `Stale()` ghost-lock detection by `owner.json` mtime, `Clean()` dead-PID reaping); `os/Clavain/hooks/auto-stop-actions.sh:142` (`intercore_sentinel_check_or_legacy "goal_cadence_throttle" ...`) — the hook layer already calls the sentinel primitive today, for a different gate.
- **What:** The master's craft is knowing that a valid rite needs exactly one *irreversible* threshold-crossing act, witnessed and durable — not a courtesy check performed by whichever officiant happens to still be present. Intercore already contains two mechanisms built for exactly this shape: `sentinel.Store.Check` is a DB-transactional, single-writer, atomic "has this fired yet" claim that survives session death because it lives in the database, not in the closing session's memory. `lock.Manager` is a lease with an explicit staleness window (`DefaultStaleAge = 5s`, extendable) and ghost-lock/dead-PID reaping — literally the "lease/heartbeat model" the probe's PRIORITY-1 asked to be surfaced and scored. Yet the terminal-gate open question (line 45) proposes three candidates from scratch (two-layer ordered close, single-layer /goal-met, event-driven consumers) and none of them is framed as "sentinel-gated" or "lease-held." The auto-stop-actions.sh hook *already* calls `intercore_sentinel_check_or_legacy` for the unrelated goal-cadence-throttle purpose one line above the code cited in the settled facts (line 142 vs. the settled-fact citation at 135-146) — the primitive is one hop away from the exact mechanism the design needs and isn't being reused.
- **Evidence:** `sentinel.go:35` doc comment: "atomic claim-if-eligible throttle check... fires at most once per scope_id" — this is precisely a single point-of-no-return primitive, durable in SQLite, immune to the closing session dying mid-sequence (settled fact: "the obligation evaporates with nothing else positioned to notice"). `lock.go:29-37` `Lock{Owner, PID, Host, Created}` + `Stale()`/`Clean()` at lines 233-254 is a working lease-with-heartbeat implementation already exercised by `TestGhostLockCleanup` (`lock_test.go:261`).
- **Suggestion:** Score a fourth terminal-gate candidate explicitly: "sentinel-claimed close" — a goal's terminal sequence is gated by a `sentinel.Store.Check("goal_close", goal_id, 0)` claim (fires exactly once, durable in the intercore DB, survives session death) combined with a `lock.Manager`-style lease held by whichever session is *mid*-sequence (so a dead session's stale lease can be detected and the sequence resumed or explicitly re-opened by a successor session, rather than silently vanishing). This reuses two already-tested primitives instead of inventing goal-close semantics from zero, and it is the only candidate shape that gives the successor-proposal obligation a durable home independent of any one session's survival.

### witnessing-is-self-attestation
- **Severity:** P1
- **Where:** doc §What We're Building Pillar 1, line 13 ("the Haiku evaluator can judge it from surfaced output"); §Key Decisions item 6, line 40 (stakes-routed melange, C1 = "one confirming question, no melange"); settled fact re: C2/C3 melange-coverage gap.
- **What:** A rite of passage is only complete once it is *witnessed* — recognized by a party other than the candidate undergoing the passage, such that the community thereafter treats the status as changed. In this design, the only entity that confirms a goal's terminal condition was met is the same Haiku evaluator that has been silently judging the loop's own surfaced output the entire time — and per the settled fact, for C1-C3 goals (the likely majority tier) there is no melange pass and no other check at all. The "witness" and the "candidate" are functionally the same process. This is structurally different from — and weaker than — the ritual's own *entry* design, which explicitly requires a second party (research-first agent + user with go/no-go authority) before a charter is ratified. The exit rite has quietly dropped the second-party requirement that the entry rite insists on.
- **Evidence:** Line 13 states the evaluator "judge[s] it from surfaced output ('tests exit 0, bead closed with evidence', never 'the feature is good')" — this is a self-report constraint, not a witness constraint: the evaluator reads what the same loop wrote, using criteria the same loop (or its ritual-drafted charter) supplied. Key Decision 6 confirms C1/C2/C3 (no melange) get no second check at all on whether the condition that fires the evaluator was itself sound (this compounds the already-identified "sole trigger for kernel-gated close" gap, but from the witnessing angle rather than the validation angle).
- **Suggestion:** Define a minimum witness requirement independent of melange stakes-routing: even at C1, something outside the evaluating session's own turn-loop (a sentinel claim visible to `bd`/`ic` state, a required human ack surfaced in the next-goal block, or a cross-session `ic goal show` check) must register that the close happened, before the successor-proposal step is allowed to fire. Melange can remain stakes-scaled for *charter quality*; the witnessing act for *close completion* should not be optional at any tier, because an un-witnessed close is indistinguishable from a close that never happened to any party outside the dead session.

### charter-storage-liminal-split
- **Severity:** P2
- **Where:** doc §Open Questions, line 48 ("Charter storage shape: intercore entity fields vs. companion doc file... vs. both — and what the melange reviews (the doc) vs. what the kernel gates on (the fields)").
- **What:** If the charter is ratified as a doc (melange-reviewed) but the kernel gates on separately-stored entity fields, the formation rite has two witnessed artifacts with no stated rule for which one is authoritative or how they stay synchronized. A rite with two independent, unsynchronized attestation records is worse than one with none: it creates a scenario where the doc says "ratified" and the fields say something else (stale, hand-edited, or never populated from the doc), and nothing in the design says which the successor session should trust. This is the formation-side mirror of the terminal-gate's already-flagged fragmentation.
- **Evidence:** Line 48 states the split explicitly as an open question but proposes no reconciliation mechanism, not even "fields are derived from the doc at ratification time and doc edits after that point require re-ratification."
- **Suggestion:** Decide now, not later: the entity fields should be a generated projection of the ratified doc (one-way, doc → fields, at the moment melange approval fires), with no independent field-editing path — this makes the doc the single point of no return for formation and the fields a pure witness-record, closing the two-artifact liminal gap before it's built.

### subsumption-verdict-has-no-reincorporation-act
- **Severity:** P2
- **Where:** doc §Open Questions, 'Adjacent open trackers' (sylveste-lbkd, sylveste-3kol) and §Why This Approach line 29 ("interphase is a second, parallel bead-scoped phase system... competing with the kernel chain").
- **What:** "Subsume/supersede/orthogonal" is framed purely as a verdict to be reached ("Needs an evidence-based verdict") — but a verdict is a judgment, not a status transition. The rite-of-passage question is: once the verdict is "subsumed," what concrete, witnessed act changes sylveste-lbkd's own status from live-tracker to subsumed-tracker? Is its bead closed? Relabeled? Does a pointer get written into it referencing the goal-native design? If the verdict is reached in this brainstorm/melange but no bead/doc mutation enacts it, sylveste-lbkd remains, in every system that reads it, a live independent tracker — a zombie status exactly of the shape the lens is built to flag (asserted-not-executed).
- **Evidence:** The doc's own language treats this as a research/evidence question ("Needs an evidence-based verdict; strategy Phase 0.5 enforces it as a hard gate downstream") — "enforces it as a hard gate downstream" describes a future gate blocking on the verdict's existence, not an act that updates sylveste-lbkd/sylveste-3kol's own record. No file/bead mutation is named.
- **Suggestion:** When the melange verdict lands, require it to write back to the adjacent tracker itself (bead status + a note field, or equivalent) in the same pass that ratifies the goal-native charter — not as a downstream gate that merely checks the verdict exists, but as the act that makes the verdict binding on any future reader of sylveste-lbkd/sylveste-3kol.

## Verdict
The strongest new finding is structural, not decorative: intercore already ships two tested, durable point-of-no-return primitives (`sentinel.Store.Check`, `lock.Manager`'s lease/staleness pair) that are mechanistically exactly what PRIORITY-1's lease/heartbeat ask is looking for, and the terminal-gate discussion never connects to either — the design is reinventing a solved problem from a blank page. The witnessing gap (self-attestation by the same evaluator that ran the loop) is the lens's second load-bearing finding: the formation rite requires a second party, the close rite quietly doesn't.

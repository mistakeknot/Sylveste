## Findings

### lock-manager-has-no-fence-so-stale-break-double-witnesses
- **Severity:** P0
- **Where:** `core/intercore/internal/lock/lock.go:106-153` (`Acquire`, `Release`), `core/intercore/internal/lock/lock.go:329-351` (`tryBreakStale`), `core/intercore/internal/lock/lock.go:17` (`DefaultStaleAge = 5 * time.Second`)
- **What:** The prior round already established (settled fact) that `lock.Manager` is mechanistically the lease/heartbeat model PRIORITY-1 asked to be surfaced. This finding is the fused layer neither parent alone reaches: examining the primitive's actual code shows it has no fencing token at all, and its default staleness window is implausibly short for the rite it would need to guard. `Acquire` returns `error`, not an opaque generation/fence value — the caller has nothing to attach to writes that would let a later party reject them as stale. `tryBreakStale` decides staleness purely from `owner.json`'s `Created` timestamp vs. `StaleAge` (5s default) and, once broken, a second `Acquire` succeeds with a plain `os.Mkdir` — no compare-and-swap against the first holder's generation, because there is no generation. Transactionally (parent 1's ground): this is exactly the "fencing/single-writer designation makes the crossing serializable but ERASES the witness" trap — the break-and-reacquire *looks* serializable (only one `Mkdir` wins at a time) but nothing stops the ORIGINAL holder, now falsely presumed dead, from finishing its own writes (reflect doc, compound entry, successor proposal) after the second holder has already done the same and released. Ritually (parent 2's ground): both completions are independently, fully witnessed — each writes durable artifacts that the rest of the system (next-goal, statusline, sibling sessions) will treat as the real reincorporation, because nothing in the artifact trail distinguishes a fence-honored close from a stale-broken one. Neither parent's solo analysis reaches this: pure transaction analysis would say "add a fencing token" as generic advice without knowing intercore's specific candidate primitive already lacks one; pure rite analysis has no way to know `StaleAge` is 5 seconds against a sequence that necessarily involves multiple LLM calls (verify-against-charter, reflect+compound drafting, successor-proposal drafting) each easily exceeding 5s of wall-clock gap between the lock's `Created` write and the next filesystem touch.
- **Evidence:** `lock.go:17` `DefaultStaleAge = 5 * time.Second`; `lock.go:106-135` `Acquire`'s retry loop calls `m.tryBreakStale(ld)` on any `os.Mkdir` collision and immediately retries `Mkdir` on success — no fence value threaded through; `lock.go:154+` `Release` takes `owner string` and (per the function's own doc comment) "verif[ies] the caller is the owner" by string match, not by a token minted at acquire time; `lock.go:329-351` `tryBreakStale` reads only `meta.Created` (an `int64` unix timestamp) to decide staleness — there is no `Generation`/`Fence`/`Epoch` field anywhere in `ownerMeta` (lock.go:38-43, confirmed no such field exists in the earlier read of lines 1-60).
- **Suggestion:** If a future round adopts `lock.Manager` (or its successor) as the terminal-gate's concurrency primitive, add a monotonic fence/generation counter returned from `Acquire` and threaded through every terminal-sequence write (reflect doc, compound entry, successor proposal), with each write rejected if the current fence no longer matches; also raise `StaleAge` for goal-close specifically to something bounded by the sequence's expected LLM-call latency, not the 5s default tuned for the throttle use case it currently serves.

### sentinel-is-a-boolean-throttle-not-a-step-ledger-so-reuse-would-still-strand-mid-rite
- **Severity:** P1
- **Where:** `core/intercore/internal/sentinel/sentinel.go:11-16` (`Sentinel` struct: `Name`, `ScopeID`, `LastFired` — three fields, no step/ordinal), `sentinel.go:34-60` (`Check`, single atomic `UPDATE...RETURNING` against one `last_fired` column), `os/Clavain/hooks/lib-intercore.sh:67` and `auto-stop-actions.sh:142` (existing call is scoped by `SESSION_ID`, not by goal ID)
- **What:** The settled facts correctly identify that intercore already has durable, tested single-point-of-no-return primitives and that the terminal-gate open question doesn't reference either. This finding goes one layer further, into fused territory: even granting that gap gets closed by wiring in `sentinel.Store.Check`, the primitive as it actually exists cannot alone satisfy what the rite frame requires. `Sentinel` has exactly one temporal field (`LastFired int64`) and `Check`'s atomic update is a single boolean claim ("has this fired within `intervalSec`") — there is no column or API for "which of N ordered steps has completed." Transactionally, reusing it for goal-close gives you idempotent claim-or-throttle on the *decision to start* the terminal sequence, but nothing checkpoints progress *through* it — the exact per-step-checkpoint gap parent 1 flags in isolation. Ritually, a sequence with only a start-gate and no step ledger means an interrupted rite (process dies after reflect, before successor-proposal) leaves no record of which threshold was crossed — the liminal residue parent 2 flags in isolation. The fused-only insight is that these are the SAME missing column: a naive "just reuse sentinel" fix (the transaction parent's natural instinct once it learns the primitive exists) satisfies neither parent's actual requirement, because the primitive that answers "did this already start" cannot also answer "how far did it get" or "was it witnessed as complete" without a schema change parent 1 alone wouldn't necessarily insist on (sentinels are fire-once-per-interval throttles by design, not resumable-workflow state machines) and parent 2 alone has no visibility into (it doesn't read Go source to know `Sentinel` has no step field). Additionally, the one place sentinel is wired today is scoped by `SESSION_ID` (auto-stop-actions.sh:142, "goal_cadence_throttle" keyed to the closing session), not by goal ID — so even the existing call pattern, if copy-pasted for goal-close, would scope the claim to the wrong entity and fail to prevent two *different* sessions attached to the same goal from each passing their own session-scoped sentinel check.
- **Evidence:** `sentinel.go:11-16` struct definition (three fields, confirmed via direct read); `sentinel.go:34-60` `Check` signature `(ctx, name, scopeID string, intervalSec int) (bool, error)` — returns only `bool`, no step/progress value; `auto-stop-actions.sh:142` `intercore_sentinel_check_or_legacy "goal_cadence_throttle" "$SESSION_ID" 60` — second positional arg is `$SESSION_ID`, confirming session-scoping of the existing call site.
- **Suggestion:** If sentinel is extended for goal-close, its scope_id must be the Goal ID (not session ID) to get correct cross-session mutual exclusion, and a companion per-step evidence column (or a small ordered table keyed goal_id+step_name+completed_at) is needed alongside it — sentinel alone answers "started," not "how far" or "witnessed-complete."

### obligation-object-inherits-the-same-unfenced-witness-gap
- **Severity:** P1
- **Where:** §Open Questions 'Terminal-gate shape' (line 45, the successor-proposal-doctrine-needs-enforcement-somewhere framing); `core/intercore/internal/lock/lock.go:106-153`; `os/Clavain/commands/next-goal.md:13-21`
- **What:** PRIORITY-1 asks this probe to surface shapes including "successor-proposal as a separate obligation object" as a candidate escape from the settled standing-party gap. Taken alone, the transaction parent would likely score this favorably (an obligation record is a natural place to put a durable, queryable "is this discharged yet" flag, decoupled from the session that created it). Taken alone, the rite parent would likely also score it favorably (a named object gives the mandatory reincorporation act — the doctrine's "never leave a finished goal without a proposed successor" — its own witnessed existence, independent of whether the rest of the terminal sequence completed). The fused-only defect is that BOTH of those endorsements silently assume the obligation object's own CREATION is itself a fenced, single-witness act — and nothing in the doc, nor in intercore's existing primitives as verified above, guarantees that. If two sessions attached to the same goal both reach a terminal condition near-simultaneously (the doc's own stated tension), and each independently creates an "obligation: propose successor for Goal X" record because there is no fence on the CREATE step, the design has traded one double-witness defect (two closes) for an isomorphic one (two obligations, each independently visible to next-goal's candidate-ranking machinery, each capable of seeding a different successor). The obligation-object shape does not dissolve the fencing requirement PRIORITY-1's other candidates need — it relocates it one level down, onto a new object, without inheriting a mechanism to enforce it. This is intersection-only: the transaction parent alone would ask "is create-obligation idempotent" as a generic question without connecting it to the rite parent's specific doctrine language ("never leave... without a proposed successor" as the mandatory reincorporation act); the rite parent alone would ask "is the obligation witnessed" without the transaction parent's concrete vocabulary (idempotency key, fencing token) for what "witnessed exactly once" requires mechanically.
- **Evidence:** §Open Questions line 45 names "successor-proposal as a separate obligation object" only as a phrase to be scored, with no described creation mechanics; `next-goal.md:13-21` establishes the doctrine's enforcement point (the Stop-hook's `goal-completed` signal) is itself per-session (fires per completion message), reinforcing that any naive per-session obligation-create call would double-fire under the doc's own stated "sessions close often, goals span many runs" tension; `lock.go:106-153` (see finding 1) confirms the one candidate fencing primitive in the repo has no generation token to offer a new object type either.
- **Suggestion:** When scoring the obligation-object shape against the other terminal-gate candidates, score its CREATE path on the same fencing criteria being applied to the close path itself — an obligation object is not a fix for the missing standing party unless its own creation is proven single-witness (e.g., a UNIQUE constraint on goal_id in an `obligations` table, functioning as the fence sentinel and lock.Manager both currently lack).

## Verdict
The two parent lenses converge on a gap neither would fully surface alone: intercore's one candidate concurrency primitive with staleness detection (`lock.Manager`) has no fencing/generation token, so a stale-lock break during a necessarily-slow, multi-LLM-call terminal sequence produces two independently and fully witnessed reincorporations of one Goal with no way to tell which is canonical — and this defect propagates unchanged into the obligation-object shape PRIORITY-1 asked to have scored, unless that object's own creation is separately fenced. Any terminal-gate shape adopted in the next round should be scored explicitly against "does its point-of-no-return act carry a fence/generation token," not just "does it have a lease."

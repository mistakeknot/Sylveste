# adjudication: sentinel-vs-lease contradiction — round 3

## Findings Index
- [P1] sentinel-mischaracterized-as-lease — claim 1's "lease/heartbeat" label for sentinel.Store.Check is a code-reading error; claim 2 holds (§Open Questions 'Terminal-gate shape')
- [P2] lock-manager-uncited-despite-being-the-real-lease — the doc's terminal-gate question omits lock.Manager, the primitive that actually satisfies PRIORITY 1's ask, while the wired-in Stop-hook path (auto-stop-actions.sh:142) uses the wrong one (sentinel) by convenience (§Open Questions 'Terminal-gate shape')

## Findings

### sentinel-mischaracterized-as-lease
- Severity: P1
- Where: core/intercore/internal/sentinel/sentinel.go:12-16,32-85 vs core/intercore/internal/lock/lock.go:29-51,153-184,325-352; doc §Open Questions 'Terminal-gate shape' (line 45)
- What: Claim (1) ("Intercore already contains two tested, durable single-point-of-no-return primitives (sentinel.Store.Check ...; lock.Manager ...) that are mechanistically the 'lease/heartbeat model'") is half right and half a code-reading error. `lock.Manager` genuinely is a lease/heartbeat primitive: `Lock{Owner, PID, Host, Created}`, `Acquire`/`Release` with owner verification (`ErrNotOwner`), and `tryBreakStale` combining a staleness threshold with `pidAlive()` PID-liveness detection — i.e. it can and does distinguish "no recent activity" from "the holder died." `sentinel.Store` cannot: its `Sentinel{Name, ScopeID, LastFired}` struct carries no holder identity, `Check` is a pure atomic UPDATE-if-interval-elapsed throttle with no `Release`/ownership/PID check, and nothing in the file tests process liveness — only a timestamp delta. Claim (2) states this precisely and it is verified against the source: sentinel is "fire-once-per-interval... no holder identity, renewal, or release semantics — not a lease," and "cannot distinguish 'no recent activity' from 'the tending session died.'" Claim (2) also correctly identifies the mechanism risk: sentinel, not lock.Manager, is what's already wired into the goal-cadence Stop-hook path (`auto-stop-actions.sh:142`, `intercore_sentinel_check_or_legacy "goal_cadence_throttle"`), so a terminal-gate design built "by analogy to what's already there" would naturally reach for sentinel and inherit its blind spot for died-mid-work sessions — exactly the failure mode the settled facts already flag (obligation evaporates if the closing session dies).
- Evidence: sentinel.go:12-16 (`Sentinel{Name, ScopeID, LastFired}` — no owner/PID field); sentinel.go:35 (`Check(ctx, name, scopeID string, intervalSec int) (bool, error)` — no owner param); sentinel.go:54-61 (UPDATE gated only on `unixepoch() - last_fired >= intervalSec`, no liveness check); sentinel.go has no `Release` function anywhere in the file. lock.go:30-37 (`Lock{Owner, PID, Host, Created}`); lock.go:153-184 (`Release` verifies `meta.Owner != owner` → `ErrNotOwner`); lock.go:259-282 (`Clean` calls `pidAlive(l.PID)` before removing — genuine liveness check, not just a timer); auto-stop-actions.sh:142 (`intercore_sentinel_check_or_legacy "goal_cadence_throttle" "$SESSION_ID" 60` — confirms sentinel, not lock, is the primitive already in the goal-cadence path).
- Suggestion: n/a (adjudication, not a design gap)
- Remediation: When the terminal-gate section cites intercore's existing lease/heartbeat-adjacent primitives, credit `lock.Manager` (Acquire/Release/tryBreakStale with PID-liveness) as the actual lease-shaped candidate and explicitly flag `sentinel.Store` as a throttle with no holder identity or death-detection — do not present the two as mechanistically equivalent "lease/heartbeat" primitives.

### lock-manager-uncited-despite-being-the-real-lease
- Severity: P2
- Where: docs/brainstorms/2026-07-18-goal-native-cycle-brainstorm.md §Open Questions 'Terminal-gate shape' (line 45); core/intercore/internal/lock/lock.go:15-20 (DefaultStaleAge = 5s, DefaultBaseDir under /tmp)
- What: With claim (1) narrowed to just `lock.Manager`, a new gap surfaces: the doc's terminal-gate open question still cites neither primitive, but `lock.Manager` is not a drop-in fit either — it's process-local (filesystem locks under `/tmp/intercore/locks`, 5-second default staleness, PID-liveness checked via local `pidAlive`) rather than distributed/cross-host, and its staleness window (5s) is tuned for short-lived command-level mutual exclusion, not for "goal spans many runs/sessions across possibly-different machines and days." Proposing it as the terminal-gate lease primitive is directionally right (it is the closest existing single-point-of-no-return-with-death-detection primitive in the codebase) but needs an explicit adaptation note — longer/goal-scoped staleness, and a liveness signal that works if the "owner" session was on a different host than the one checking staleness — not a bare citation.
- Evidence: lock.go:16-19 (`DefaultBaseDir = "/tmp/intercore/locks"`, `DefaultStaleAge = 5 * time.Second`); lock.go's `pidAlive` liveness check is necessarily local-machine-scoped (PID numbers aren't meaningful cross-host).
- Suggestion: If the terminal-gate melange round adopts a lease/heartbeat shape, spec it as "lock.Manager-inspired, not lock.Manager-reused" — same ownership+staleness+liveness pattern, but goal-scoped staleness (hours/days, not 5s) and a host-aware or DB-backed liveness signal instead of local PID checks.
- Remediation: none — this is a downstream design note, not a brief amendment.

## Verdict
Not a taste call. Claim (2) is correct and verified against the source: `sentinel.Store` has no owner/PID/release semantics and is a pure interval throttle, and it is confirmed as the actual primitive wired into the goal-cadence Stop-hook path (auto-stop-actions.sh:142), making the "built by analogy to what's already there inherits throttle semantics" risk concrete rather than hypothetical. Claim (1) is partially wrong: `lock.Manager` genuinely is a lease/heartbeat primitive (owner identity, Release with ownership check, staleness+PID-liveness break), but bundling `sentinel.Store.Check` into the same "mechanistically lease/heartbeat" bucket is a code-reading error the source directly contradicts. The correct synthesis is claim (2) plus the surviving half of claim (1): cite `lock.Manager` alone as the existing lease-shaped candidate, flag it needs goal-scoped staleness tuning, and treat sentinel explicitly as the wrong analogy to build from.

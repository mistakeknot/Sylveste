# fd-routing-kernel-mechanics — round 0

## Findings Index
- [P0] fable-tier-zero-collapses-into-floor-clamp — adding "fable" without extending `ParseModelTier`/`_routing_model_tier` makes it silently indistinguishable from an invalid string and gets clamped to any agent's safety floor (§Phase 1, §Gap 1)
- [P1] go-parity-claim-is-false-for-tier-parsing — plan calls Go-side `ParseModelTier` "optional" for Phase 1, but it already exists and is load-bearing in `applyFloor`; the two resolvers (bash/Go) will silently diverge on fable resolution the moment either one is touched without the other (§Phase 1, §Survey "Reusable mechanism")
- [P1] dual-resolver-divergence-undetectable — `routing_resolve_model`'s Go fast-path skip condition depends on `CLAVAIN_RUN_ID` env var visibility at call time, with no assertion that a subagent/subshell dispatch preserves it; if it's dropped, the Go router (missing agency overrides) silently resolves a different model than the bash path intended, and `routing_decisions.rule_matched` won't distinguish "reached via agency step 0" from "reached via Go default fallback" (§Survey "convenient accident", `lib-routing.sh:903-910`)
- [P2] agency-spec-staleness-no-reload-trigger — `ic agency load <stage> --run=<id>` populates `agency.models.${phase}` once; nothing in the plan re-invokes load or invalidates the kernel-stored value if the spec file or plan changes mid-run, so `routing_resolve_model` step 0 (`lib-routing.sh:926-941`) will keep serving a stale mapping for the rest of the run (§Phase 1 Acceptance, §Design "Fable-window detection")
- [P3] routing_decisions-lacks-fallback-provenance-field — schema (`decision.go` Decision struct) has `FloorFrom`/`FloorTo` for floor clamps but no analogous field pair for fable→opus *availability* fallback, so once implemented, a fable-unavailable fallback and a floor clamp will both just show up as `selected_model=opus` with no way to tell which happened (§Design "Fable-window detection")

## Findings

### fable-tier-zero-collapses-into-floor-clamp
- Severity: P0
- Where: Phase 1 bullet "Add `fable` to the routing vocabulary: `os/Clavain/config/routing.yaml` tiers, `_routing_model_tier` in `lib-routing.sh`, `ParseModelTier` in `internal/routing` (Go change optional for this phase; bash path suffices)."
- What: `_routing_model_tier()` in `lib-routing.sh:66-83` is a `case` statement over known model strings that falls through to `*) echo 0 ;;` (tier "unknown") for anything unrecognized — identical to `ParseModelTier` in `core/intercore/internal/routing/routing.go:17-28`, which returns `TierUnknown` (=0) for any unmatched string. Both feed directly into safety-floor clamp comparisons: bash's `_routing_apply_safety_floor` (`lib-routing.sh:92-113`) does `elif [[ $model_tier -lt $floor_tier ]]; then model="$floor"`, and Go's `applyFloor` (`resolve.go:123-142`) does `if floorTier == TierUnknown || modelTier >= floorTier { return model }` else return floor. If "fable" is added to `routing.yaml` config tiers (as the plan says) but NOT to these tier-ranking functions, `_routing_model_tier(fable)` returns 0, which is `-lt` every real floor tier (1/2/3). Any agent with a safety floor configured (`agent-roles.yaml` `min_model`) will have its "fable" resolution silently clamped down to that floor on the very first call — the opposite of "hard fail or explicit fallback," it's a silent wrong-tier dispatch that looks like a normal floor clamp in the logs.
- Evidence: `lib-routing.sh:66-83` (`_routing_model_tier` case statement, no "fable" arm), `lib-routing.sh:107-111` (clamp logic), `core/intercore/internal/routing/routing.go:9-28` (`ModelTier` const block has no `TierFable`), `resolve.go:136-141` (`applyFloor` uses `ParseModelTier` output directly in an ordinal comparison).
- Suggestion: Phase 1 must add a `fable` case to `_routing_model_tier` (bash) with a rank ABOVE opus (e.g., 4) as a blocking sub-task, not "Go change optional" — the bash tier function is exactly as load-bearing as the Go one for this specific bug, and it's the one this phase claims to touch. Add a one-line regression check: `_routing_model_tier fable` must be non-zero and greater than `_routing_model_tier opus` before the agency spec ships.

### go-parity-claim-is-false-for-tier-parsing
- Severity: P1
- Where: §Survey "Reusable mechanism" and Phase 1: "Go change optional for this phase; bash path suffices."
- What: The plan frames `ParseModelTier` as a Go-only concern that Phase 1 can defer. It's already shipped and called from `resolve.go:136-137` inside `applyFloor`, which the bash fast-path in `routing_resolve_model` explicitly falls back to whenever `CLAVAIN_RUN_ID` is unset (`lib-routing.sh:903-910`, "Fall through on failure — bash implementation is the safety net"). So both resolvers exercise tier-comparison logic on live traffic today, and the plan's own convenient-accident argument (agency-spec runs always have `CLAVAIN_RUN_ID` set, so they skip Go) only protects the *agency-spec* case — any dispatch that resolves "fable" outside an active kernel run (e.g., a stray or malformed run-id, or an agent invoked before the run context is established) still hits the Go path and its unmodified `ModelTier` enum.
- Evidence: `resolve.go:136-141`, `lib-routing.sh:903-910`, `routing.go:9-14` (enum has exactly 3 named tiers).
- Suggestion: Reframe as: "Go-side `ModelTier` enum addition is required in Phase 1, gated by the same regression check as the bash side, specifically to keep the two resolvers' floor-clamp behavior from diverging on any input that reaches the Go path." Cheapest fix: add `TierFable ModelTier = 4` and a `"fable"` case in both `ParseModelTier` and its `String()` method.

### dual-resolver-divergence-undetectable
- Severity: P1
- Where: §Survey "Convenient accident" paragraph; Phase 1 acceptance criteria.
- What: The plan asserts "the bash router deliberately skips the Go fast-path when `CLAVAIN_RUN_ID` is set... which is exactly the agency-spec case" as a load-bearing invariant, but nothing in the plan specifies how `CLAVAIN_RUN_ID` propagates to nested subagent dispatches (Task-tool spawns, background agents, `codex-delegate`). If a subagent's shell environment doesn't inherit or re-export `CLAVAIN_RUN_ID` (a common failure mode for subprocess/subshell boundaries), `routing_resolve_model` silently takes the Go fast-path for that one dispatch, which has no agency-override support — it'll resolve "executing" to whatever `phase.model`/`defaults.model` says in the static Go-loaded config, not the loaded agency spec's sonnet/fable mapping. `routing_decisions.rule_matched` (`decision.go:23`) would record a plausible-looking value (e.g. `"phase_model"` or `"default"`) with no signal that this diverged from what the bash path would have produced for the same (phase, category, run) tuple.
- Evidence: `lib-routing.sh:892-910` (the skip condition and its comment acknowledging the Go router "doesn't support kernel overrides yet"), `decision.go:23` (`RuleMatched string` — single value, no divergence-detection field).
- Suggestion: Add a cheap detectability fix: when `CLAVAIN_RUN_ID` is set but the Go fast-path condition somehow still fires (defensive check), log a distinct warning and force the bash fallback rather than trusting the Go result. Alternatively, add an assertion in `routing_resolve_model` itself — if `CLAVAIN_RUN_ID` is set in the environment at function-entry but the Go path was still taken (detectable via a sentinel check before the `ic route model` call), emit a `_routing_emit_verification` event flagging the anomaly, the same mechanism already used for calibration shadow-mode no-ops (`lib-routing.sh:995-998`).

### agency-spec-staleness-no-reload-trigger
- Severity: P2
- Where: Phase 1 "Wire `/sprint` to `ic agency load` the spec when the session model is fable"; Design considerations section is silent on re-load.
- What: `ic agency load <stage> --run=<id>` is a one-shot write into kernel state consumed by `intercore_state_get "agency.models.${phase}"` (`lib-routing.sh:926-941`). If a plan is re-scoped mid-run (e.g., `/write-plan` re-invoked after scope change, a common pattern per this project's iterative workflow) or if the spec file itself is edited, nothing re-triggers `ic agency load`, so the kernel-stored `agency.models.executing` keeps serving the original mapping for the rest of the run — including through Phase 2's escalation ladder, which will re-resolve models per the same stale spec.
- Evidence: `lib-routing.sh:926-941` (step 0, reads via `intercore_state_get`, no staleness/TTL check visible in this function), Phase 1 acceptance criteria only test initial-load correctness, not re-load.
- Suggestion: Smallest fix: hash the spec file content at load time, store the hash alongside `agency.models.*` state, and have `routing_resolve_model` step 0 compare the on-disk spec hash to the stored one on each call (or at minimum on phase-transition boundaries), emitting a warning if they've diverged. Full re-load automation can be deferred, but silent staleness should at least be observable.

### routing_decisions-lacks-fallback-provenance-field
- Severity: P3
- Where: §Design considerations "Fable-window detection... with opus fallback baked into resolution."
- What: `Decision` struct (`decision.go:11-34`) has `FloorApplied`/`FloorFrom`/`FloorTo` for safety-floor clamps but no equivalent triple for a *tier-unavailability* fallback (fable→opus because fable isn't reachable this session). Once Phase 1 ships, `routing_decisions` rows for a fable-unavailable case and a floor-clamped case will both just show `selected_model=opus, rule_matched=<something>` — an operator debugging "why didn't this run use fable" can't distinguish "fable wasn't available" from "fable was available but got floor-clamped to opus" from the decision log alone.
- Evidence: `decision.go:11-34` (no `fallback_from`/`fallback_reason` fields), Design section explicitly anticipates this exact fallback path without specifying its audit trail.
- Suggestion: Add `fallback_applied bool` + `fallback_from *string` columns (mirroring the floor fields) to `routing_decisions` and populate them whenever the fable-unavailable branch fires, before Phase 4's metrics start reading this table as ground truth for routing effectiveness.

## Verdict
The precedence hierarchy itself (overrides > phase.category > phase.model > defaults) is sound and the agency-spec injection point is real and correctly identified. But the plan treats tier-vocabulary extension as bash-only busywork when it's actually a shared invariant across two independently-maintained resolvers, both of which silently degrade "unknown tier" to "tier 0" and feed that straight into an ordinal safety-floor comparison — this is the single highest-leverage bug the phased plan could introduce if Phase 1 ships as written.

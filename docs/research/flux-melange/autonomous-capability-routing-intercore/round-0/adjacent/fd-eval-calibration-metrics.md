# fd-eval-calibration-metrics — round 0

## Findings Index
- [P1] escalation-credit-attribution-undefined-in-plan_execution_outcome — Phase 4's schema ("plan author model, executor model, validator model, criteria pass/fail counts, escalation count") has exactly one `executor_model` slot per outcome record, with no field distinguishing "which tier's attempt actually produced the passing result" when escalation occurred within the chain — this reproduces the exact confound the lens's own severity calibration names as canonical (§Phase 4)
- [P1] acceptance-criteria-objectivity-has-no-gate-before-feeding-the-metric — Phase 3 ships a "structured, machine-checkable acceptance-criteria block" but nothing in Phase 3's three bullets specifies who/what verifies a given criterion is actually machine-checkable (vs. restating "follows the design" in checklist clothing) before quality-gates trusts it as a validator rubric — the plan's own open-questions section names this exact gap ("nothing lints a plan for use-your-judgment steps") but Phase 3 doesn't close it, only Phase 3's *sibling* open question does (§Phase 3, §Design considerations)
- [P2] pilot-2-3-items-treated-as-a-gate-not-a-sample-size-question — Rule 6 ("pilot 2-3 items through the full loop before fanning out") is carried into the plan as a literal checkpoint count with no confidence-interval or minimum-sample language attached before Phase 4's aggregation "gates widening autonomy" off the resulting pass-rate (§Phase 4, doctrine Rule 6)
- [P2] task-difficulty-confound-in-tier-pair-aggregation — Phase 4 aggregates plan-pass-rate "per (author_tier, executor_tier) pair" with no mention of controlling for task complexity (the same complexity classification — B2 — the escalation-ladder phase already uses for the <30-min exception); if harder tasks get routed to one tier pair systematically (e.g., fable-authored plans go to harder problems by construction, since fable is reserved for "hard problems that stalled on lesser models" per doctrine Rule 5), the pass-rate difference between tier pairs conflates tier capability with task difficulty (§Phase 4, doctrine Rule 5)
- [P3] no-inter-validator-agreement-check-specified — Phase 3's plan-conformance verdict is produced by a single validator dispatch per run; nothing in the plan proposes even a spot-check of inter-run/inter-validator agreement (does the same plan + same execution get the same pass/fail from two validator invocations), which is the standard sanity check before trusting a pass/fail rubric as ground truth for a metric that will "gate widening autonomy" (§Phase 3, §Phase 4)

## Findings

### escalation-credit-attribution-undefined-in-plan_execution_outcome
- Severity: P1
- Where: Phase 4: "New evidence type `plan_execution_outcome` written at validation time: plan author model, executor model, validator model, criteria pass/fail counts, escalation count."
- What: The schema as described has a single `executor_model` field alongside a separate `escalation_count` integer. Consider the sequence the escalation-ladder lens's Decision Lens names explicitly: sonnet fails attempt 1, sonnet fails attempt 2, escalates to opus, opus's attempt passes validation. What does `plan_execution_outcome.executor_model` record — `sonnet` (who was assigned first) or `opus` (who actually produced the artifact that passed)? If it's `sonnet` (the naive reading of "the executor" as the originally-routed model), the aggregated (author_tier, executor_tier) pass-rate in `/interspect:calibrate` credits sonnet with a pass it never actually delivered — inflating confidence in sonnet-executor routing on exactly the cases where sonnet failed and had to be bailed out. This is the precise failure mode the doctrine (Rule 4, escalation) and the metric (Rule 7, "measure plan→execution pass rate") are both trying to make visible, and a single-field schema makes it invisible instead.
- Evidence: Phase 4's field list has no "attributed_tier" or "final_executor_tier" distinct from an "original_executor_tier"; Phase 2's escalation design (reviewed independently by fd-escalation-retry-ladder) confirms escalation chains do produce multiple executor attempts at different tiers per logical task, so this isn't a hypothetical — it's guaranteed to occur once Phase 2 ships.
- Suggestion: Split into `executor_tier_initial` and `executor_tier_final` (or `executor_tier_attributed`, meaning whichever attempt's output the validator actually scored). `/interspect:calibrate` should aggregate pass-rate by `executor_tier_final`, and separately track "escalation-rescued" as its own bucket — a plan that needed escalation to pass is meaningfully different from one sonnet nailed on attempt 1, even though both currently look like a single "pass" in a flat schema.

### acceptance-criteria-objectivity-has-no-gate-before-feeding-the-metric
- Severity: P1
- Where: Phase 3: "`/clavain:write-plan` emits a structured, machine-checkable acceptance-criteria block (commands to run, files that must exist, tests that must pass)." Compare to §Design considerations: "nothing lints a plan for 'use your judgment' steps. Possible cheap check in write-plan or plan-review."
- What: Phase 3's three bullets (emit criteria block → store as artifact → validator scores against it) assume the criteria block is objectively checkable by construction, but the plan's own open-questions section admits this isn't enforced anywhere — it's listed as a "possible cheap check," not a Phase 3 deliverable. Concretely: a criterion like "tests pass" (with a specific command) is machine-checkable; a criterion like "follows the intended API design" is not, but nothing in Phase 3 as scoped would reject the latter from the acceptance-criteria block before it's handed to quality-gates as "the rubric, never judgment" (doctrine Rule 3, restated in the plan's Goal section line 15). If Phase 3 ships without this check, the validator dispatch scoring "follows the intended API design" against the plan is just judgment-based review wearing a checklist — the exact regression Rule 3 exists to prevent — and Phase 4's pass-rate metric would then be measuring validator-judgment-agreement, not plan-conformance.
- Evidence: Plan's own §Design considerations names this gap for write-plan generally, but Phase 3's three-bullet scope doesn't reference it or make it a blocking sub-task — it appears only as a "possible" aside, disconnected from the phase whose entire premise (objective validator rubric) depends on it.
- Suggestion: Give a concrete objectivity/executability bar directly in Phase 3's scope, e.g.: an acceptance criterion is valid only if it resolves to (a) a shell command with a defined pass/fail exit code, (b) a file-existence check, or (c) a structural diff/grep pattern — anything that requires semantic judgment (contains words like "appropriate," "intended," "correct design") gets rejected by a lint step in `write-plan` before the criteria block is stored as an artifact. Example of a criterion that WOULD pass this bar (grounded in the plan's own text): "`routing_decisions` table has a row with `rule_matched='agency'` after running `routing_resolve_model --phase=executing`" (Phase 1's own acceptance line 51). Example that would NOT pass: "validator confirms the escalation ladder doesn't oscillate" (no defined check — this is exactly the kind of criterion Phase 3 risks accepting unless the lint exists).

### pilot-2-3-items-treated-as-a-gate-not-a-sample-size-question
- Severity: P2
- Where: Phase 4: "This is the north-star metric that gates widening autonomy (pilot 2–3 items first, per doctrine Rule 6)."
- What: Doctrine Rule 6 ("pilot 2-3 items through the full loop before fanning out a plan backlog") is carried forward verbatim as if 2-3 completed pilots constitutes sufficient evidence to widen autonomy. For a binary pass/fail metric, 2-3 samples cannot distinguish a true pass-rate of, say, 33% from a true pass-rate of 80% with any useful confidence — a single unusually hard pilot item flips the observed rate dramatically. The plan doesn't specify a minimum sample size, a confidence-interval requirement, or even an explicit acknowledgment that 2-3 is a vibes-based starting checkpoint rather than a statistically defensible gate before `/interspect:calibrate` starts trusting the aggregated number.
- Evidence: Phase 4 bullet 3 ("Reported via `/interspect:delegation-status` or a new routing-effectiveness view") and bullet 4 (the north-star framing) both treat the metric as ready to drive decisions immediately post-pilot, with no stated stopping rule.
- Suggestion: State explicitly in Phase 4 that the 2-3 item pilot is a smoke test for pipeline correctness (does the plumbing work end-to-end), not a sample-size-sufficient basis for the pass-rate metric itself — and that the pass-rate metric should carry a visible confidence caveat (e.g., "n=3, do not act on this number alone") until a stated minimum (e.g., n≥15-20 per tier-pair, informed by the same statistical reasoning already used for interspect's other calibration thresholds, if any exist) is reached.

### task-difficulty-confound-in-tier-pair-aggregation
- Severity: P2
- Where: Phase 4: "`/interspect:calibrate` aggregates into a plan-pass-rate metric per (author_tier, executor_tier) pair." Compare doctrine Rule 5 (restated in Goal, line 17): "hard problems that stalled on lesser models keep frontier in the execution loop."
- What: Rule 5 explicitly means fable-tier execution is *reserved for tasks that already failed on lesser models* — i.e., fable-executor tasks are selection-biased toward harder problems by the doctrine's own design, not randomly assigned. If Phase 4 aggregates raw pass-rate by (author_tier, executor_tier) without controlling for task difficulty/complexity (the same B2 complexity classification the escalation-ladder phase already references for the <30-min exception), a lower pass-rate for, say, (fable-author, opus-executor) doesn't necessarily mean opus executes fable's plans worse — it may just mean opus disproportionately gets the tasks sonnet already failed. This is precisely the ambiguity the lens's own Decision Lens poses (40% vs 85% pass rates across tier pairs) and the plan doesn't specify a way to tell the difference.
- Evidence: Phase 4's aggregation description has no complexity/difficulty dimension in the (author_tier, executor_tier) key; the escalation-ladder Phase 2 already tracks B2 complexity for a different purpose (skip-pipeline exception), so the data likely exists but isn't wired into Phase 4's metric key.
- Suggestion: Add complexity/B2-tier as a third dimension in the aggregation key, or at minimum stratify the reported metric by complexity bucket so a routing decision-maker can see "(fable-author, opus-executor, C3-complexity)" separately from "(fable-author, opus-executor, C1-complexity)" rather than a single blended number.

### no-inter-validator-agreement-check-specified
- Severity: P3
- Where: Phase 3: "quality-gates gains a plan-conformance verdict... returns pass/fail per criterion."
- What: Even with objective criteria (addressed above), a single validator dispatch invocation is one sample of "would this pass." LLM-as-judge pipelines are known to have run-to-run variance even on ostensibly objective criteria (e.g., ambiguity in what counts as "the file exists in the expected location" when multiple plausible locations exist). The plan doesn't propose even an occasional spot-check — re-running the same validator dispatch against the same plan/execution pair to confirm it reaches the same verdict — before this pass/fail signal becomes the input to a metric that gates autonomy widening.
- Evidence: Phase 3's description is single-pass ("the validator dispatch receives the criteria as its rubric, returns pass/fail per criterion") with no repeat-run or agreement-check language anywhere in the plan.
- Suggestion: Low-cost addition: during the pilot phase (2-3 items, per Rule 6), re-run the plan-conformance validator dispatch twice per pilot item and record agreement rate as a diagnostic — cheap insurance against building Phase 4's north-star metric on top of a noisy single-sample judge.

## Verdict
Phase 3 and 4 correctly identify the right questions in their own open-questions/design sections but don't close them within the phases as scoped — the rubric-objectivity lint and the escalation-attribution field are both named as risks elsewhere in the document without being pulled into the phase deliverables that structurally depend on them. As written, Phase 4's pass-rate metric is at meaningful risk of measuring judge-noise and task-difficulty confounds rather than the tier-capability signal the doctrine needs to make autonomy-widening decisions safely.

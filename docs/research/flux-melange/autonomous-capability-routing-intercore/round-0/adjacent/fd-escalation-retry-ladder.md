# fd-escalation-retry-ladder — round 0

## Findings Index
- [P0] retry-copies-model-verbatim-tier-step-has-nowhere-to-attach — `Retry()` in retry.go builds the new dispatch by copying `Model: orig.Model` field-for-field (no tier parameter exists), so "attempt 3 re-dispatches at the next tier up" requires a new code path entirely, not an "extension" of the existing copy — as scoped, the plan risks the escalation being bolted on as a caller-side patch that the retry chain's own bookkeeping (`ParentDispatchID`, `RetryCount`) doesn't know about (§Phase 2, `retry.go:112-130`)
- [P0] retrycount-and-tier-are-the-same-counter-conflated-by-construction — `RetryCount` in retry.go is a single monotonic int (`attempt := orig.RetryCount + 1`, line 110) used both for backoff computation (`Backoff(attempt)`) and — per the plan — would need to double as the tier-step trigger ("attempt 3 re-dispatches"); nothing in the current struct separates "how many times retried" from "which tier this attempt is at," so a chain that escalates once (sonnet→opus) and then needs a second same-tier retry at opus has no way to reset the attempt-vs-tier relationship without either resetting RetryCount (losing backoff history) or overloading its semantics further (§Phase 2, Decision Lens)
- [P1] shouldretry-maxretries-ceiling-blocks-the-third-attempt-by-default — `ShouldRetry()` (`retry.go:65-83`) returns false once `d.RetryCount >= policy.MaxRetries`, and `DefaultRetryPolicy()` sets `MaxRetries: 3`; the plan's "attempts 1-2 same model, attempt 3 escalates" needs attempt 3 to actually execute, but under the current policy, attempt 3 (RetryCount=2 going to 3) is the last one allowed at MaxRetries=3 — the escalated attempt would fire but no attempt 4 (the second escalation tier, opus→fable) could ever be checked, because attempt 4 requires RetryCount=3 which already equals MaxRetries and fails `ShouldRetry`'s guard before the escalation logic is even consulted
- [P1] no-verdict-parse-failure-mode-specified-for-escalation-trigger — the plan says "consume the verdict sidecars dispatch.sh already emits" but doesn't specify what happens when `_extract_verdict` can't parse Codex output cleanly; if the ambiguous/malformed case defaults to "retry" (same-tier) rather than "error" (escalate), a broken executor result burns through attempts 1-2 as ordinary retries and the tier-step never fires for a task that should have escalated on quality grounds, not just failure-count grounds
- [P2] chain-id-scoping-not-specified-for-cross-session-persistence — the plan's own open question ("escalation loop guard: two-strikes must not oscillate... cap at one escalation per dispatch chain") assumes a "dispatch chain" concept that persists the escalation count across a re-triggered task; `ListRetryChain` (`retry.go:171-215`) walks `ParentDispatchID` links within the existing dispatch store, which is plausible, but the plan doesn't state whether a human re-triggering the same logical task after a frontier-tier failure creates a *new* root dispatch (resetting the chain) or is expected to resume the old chain — if it's the former, the "cap at one escalation" guard silently resets every time the task is re-run

## Findings

### retry-copies-model-verbatim-tier-step-has-nowhere-to-attach
- Severity: P0
- Where: Phase 2: "Extend `internal/dispatch/retry.go` with an escalation policy: attempts 1–2 same model, attempt 3 re-dispatches at the next tier up (sonnet→opus→fable), recording the failure mode."
- What: `Retry()` (`retry.go:97-145`) constructs the new `Dispatch` struct with `Model: orig.Model` (line 121) — a direct, unconditional copy. There is no `TargetModel` parameter, no tier-lookup call, nothing that would let a caller say "give me the next tier up." The plan describes this as an "extension," implying incremental modification, but tier-stepping requires: (a) a way to compute "next tier" from `orig.Model` (this doesn't exist in the `dispatch` package — tier logic lives in `internal/routing`, a different package with no visible import relationship shown in this file), and (b) a branch in `Retry()` or a new sibling function that overrides `Model` instead of copying it, conditioned on attempt number. As scoped, this is a new function or a materially different `Retry()` signature, not a small diff.
- Evidence: `retry.go:112-130` (full field-copy list, `Model: orig.Model` at line 121), `retry.go:36-41` (`RetryPolicy` struct has no tier-related fields at all — `MaxRetries`, backoff params only).
- Suggestion: Name the concrete smallest change: add a `TierEscalation` field to `RetryPolicy` (e.g., `EscalateAt int` = attempt number to step tier, `TierSequence []string` = the escalation ladder), and in `Retry()`, replace the unconditional `Model: orig.Model` with `Model: nextModel(orig.Model, attempt, policy)` — a new small helper, not a rewrite of the copy logic. This also forces the plan to answer where `nextModel` gets its tier ordering from — presumably importing `routing.ParseModelTier`/`ModelTier`, which creates a new `dispatch` → `routing` package dependency worth calling out explicitly in Phase 2's scope.

### retrycount-and-tier-are-the-same-counter-conflated-by-construction
- Severity: P0
- Where: Decision Lens: "attempt1(sonnet)-fail, attempt2(sonnet)-fail, attempt3(opus)-fail, attempt4(fable)-fail — does the plan specify a hard stop, or can the ladder re-enter at a lower tier and restart the two-strikes count?"
- What: `RetryCount` (used at `retry.go:72`, `110`, `137`, `157`) is a single field serving two roles simultaneously once escalation is added: it's the backoff exponent input (`policy.Backoff(orig.RetryCount)`) AND, per the plan, it would gate the tier-step ("attempt 3"). If tier and attempt-within-tier are conflated into one counter, there is no way to express "this is attempt 1 at the *opus* tier" versus "this is attempt 3 overall" — which matters for the two-strikes rule itself: the doctrine's "two-strikes" means two failures *per tier*, not two failures total before permanently escalating past all tiers. Under a single-counter model, "attempt 3 escalates, attempt 4 escalates again" collapses two-strikes-per-tier into one-strike-per-tier for every tier after the first, silently violating the doctrine's Rule 4 as documented in the plan's own Goal section (line 16: "Two-strikes escalation: executor fails 2x... escalate").
- Evidence: `retry.go:72,110,137,157` (all four uses of `RetryCount` as a flat monotonic value), plan Goal section rule 4 (two-strikes is per-decision-point, implying per-tier, not global).
- Suggestion: Split into two orthogonal fields before implementing Phase 2: `AttemptCount` (retries at current tier, resets on tier-step) and `TierIndex` (position in the sonnet→opus→fable ladder, monotonically increasing, never resets). `ShouldRetry`'s guard and the backoff calc key off `AttemptCount`; the tier-step trigger keys off `AttemptCount >= 2`, then increments `TierIndex` and resets `AttemptCount` to 0. This directly answers the Decision Lens question: the ladder must NOT re-enter at a lower tier — `TierIndex` never decreases, giving a provable termination bound of `len(TierSequence) * 2` total attempts.

### shouldretry-maxretries-ceiling-blocks-the-third-attempt-by-default
- Severity: P1
- Where: Phase 2, implicitly assumes `retry.go`'s existing retry-count machinery accommodates a 3rd (escalated) attempt without adjustment.
- What: `ShouldRetry()` (`retry.go:65-83`) hard-stops at `d.RetryCount >= policy.MaxRetries`. `DefaultRetryPolicy()` (`retry.go:19-28`) sets `MaxRetries: 3`. Under the doctrine's ladder (sonnet attempt1, sonnet attempt2, escalate to opus attempt3, opus attempt4 if needed, escalate to fable attempt5), the *existing* `MaxRetries=3` ceiling would block at exactly the escalation boundary the plan cares about most — attempt 4 (RetryCount would need to reach 3, which already equals MaxRetries, so `ShouldRetry` returns false before any tier-aware logic runs). This isn't a hypothetical: it's the current, shipped default that Phase 2 would inherit unless explicitly overridden.
- Evidence: `retry.go:69-72` (guard order: `MaxRetries <= 0` check, then `RetryCount >= MaxRetries` check — both precede the status-based logic), `retry.go:19-28` (`MaxRetries: 3` as the shipped default).
- Suggestion: Phase 2 must explicitly decide and state whether `MaxRetries` counts total attempts across all tiers (in which case it needs raising to accommodate the full ladder, e.g., `MaxRetries: 5` for a 3-tier, 2-strikes-each ladder) or whether the escalation path bypasses `MaxRetries` entirely via a separate policy dimension (the cleaner fix, consistent with the `AttemptCount`/`TierIndex` split above — `MaxRetries` then bounds `AttemptCount` per tier, and a new `MaxTiers` bounds `TierIndex`).

### no-verdict-parse-failure-mode-specified-for-escalation-trigger
- Severity: P1
- Where: Phase 2: "Consume the verdict sidecars dispatch.sh already emits."
- What: The plan treats verdict consumption as a solved input without specifying the failure-closed behavior for unparseable output. If `_extract_verdict` (dispatch.sh) defaults an ambiguous/malformed Codex response to `"retry"` rather than `"error"`, then a genuinely broken executor result (garbled output, truncated response, wrong-format completion) gets treated as an ordinary same-tier retry — consuming attempts 1-2 on noise rather than triggering the escalation the doctrine wants for a result that couldn't even be judged. This silently defeats the two-strikes ladder's purpose: escalation is supposed to fire on repeated *failure*, but if failure-to-parse routes to "retry" instead of "error," the count that should trigger tier-stepping never accumulates correctly.
- Evidence: Plan's own Task Context statement (from the lens brief) explicitly flags this as an open question; the plan document itself doesn't mention verdict-parse-failure handling anywhere in Phase 2's three bullets.
- Suggestion: Add one explicit sentence to Phase 2's scope: "Unparseable/ambiguous verdict sidecars are treated as `error` (fail-closed), not `retry` — an executor result that can't be judged is worse than a result that failed cleanly, and must count toward the escalation trigger, not the plain-retry budget."

### chain-id-scoping-not-specified-for-cross-session-persistence
- Severity: P2
- Where: §Design considerations "Escalation loop guard: two-strikes must not oscillate... Cap at one escalation per dispatch chain; after that, surface to the human."
- What: The oscillation guard depends on "dispatch chain" being a durable, re-identifiable concept. `ListRetryChain` (`retry.go:171-215`) reconstructs a chain by walking `ParentDispatchID` pointers within the dispatch store for a given `dispatchID` — this works fine *within* a single logical task's dispatch tree, but the plan doesn't specify what happens when a human, after seeing a frontier-tier failure surfaced (per the open question's own scenario), re-triggers "the same task." If re-triggering creates a fresh root `Dispatch` (new `dispatch_id`, no `ParentDispatchID` linking back to the failed chain), then `ListRetryChain` on the new root sees an empty ancestry and the "one escalation per chain" cap resets to zero — exactly the unbounded-fable-budget scenario the lens's own severity calibration names as the canonical P0.
- Evidence: `retry.go:171-186` (chain-walk starts from a given `dispatchID` and stops when `ParentDispatchID` is empty — a fresh dispatch has no way to be linked to a prior failed chain unless something explicitly sets that field at creation time, which `Retry()` only does for retries it creates itself, not for externally re-triggered tasks).
- Suggestion: Introduce a stable, task-level `ChainID` (distinct from `dispatch_id`/`ParentDispatchID`) derived from something durable across re-triggers — e.g., a hash of (bead_id, plan_artifact_path) rather than the ephemeral dispatch tree — and require the escalation cap to be looked up by `ChainID` in a persistent store (interspect evidence or a dedicated kernel table), not reconstructed by walking `ParentDispatchID` from whatever dispatch happens to be the current root.

## Verdict
The doctrine's ladder is well-specified in prose but the plan proposes extending `retry.go` as if the escalation step were a parameter tweak; in reality `RetryCount` is currently a single conflated counter serving backoff and retry-ceiling duty, `Model` is copied verbatim with no tier-aware branch point, and the existing `MaxRetries=3` default would truncate the ladder before the second escalation could even be evaluated. None of this is unfixable, but Phase 2 needs a genuine attempt/tier separation as a design decision made explicit in the plan, not discovered mid-implementation.

# fd-swordsmith-transmission — round 0

## Findings Index

- [P1] no-inspection-rubric-means-master-signs-own-work — quality-gates validators score their own review findings today; Phase 3's "criteria as rubric" is proposed but nothing yet forces the validator dispatch to receive the plan's criteria instead of generating its own judgment (§Phase 3, §Gap 4)
- [P2] no-canonical-form-lint-for-judgment-calls — the doctrine forbids "use your judgment" steps in execution-grade plans, but the plan only names this as an "open question," with no owner or mechanism proposed (§Design considerations, "Executor no judgment calls enforcement")

## Findings
### retry-re-strikes-same-hand
- Severity: P1
- Where: §Phase 2 — "Extend `internal/dispatch/retry.go` with an escalation policy: attempts 1–2 same model, attempt 3 re-dispatches at the next tier up (sonnet→opus→fable)"
- What: I read `core/intercore/internal/dispatch/retry.go`. `Retry()` (line 97) builds the new dispatch by copying every config field from the original, including `Model: orig.Model` (line 121) verbatim, and `ShouldRetry()` (line 65) only checks `RetryCount >= policy.MaxRetries` and status — there is no tier field, no model-escalation branch, and no distinction between "same-hand retry" and "escalated re-dispatch." In forge terms: today's `Retry` is a master handing the apprentice the exact same hammer for the exact same fold, over and over, up to `MaxRetries=3` (`DefaultRetryPolicy`, line 20-28) — the cardinal rule of a functioning lineage (never let the same untrained hand re-strike a botched weld a third time the same way) is violated by the current code path that Phase 2 is extending, not replacing.
- Evidence: Source domain — a forge's correction protocol always changes *who holds the tongs* after a repeated failure, not just *how many more times* they try. Target — `retry.go:113-130` `Retry()` struct literal preserves `Model: orig.Model`; there is no `EscalationPolicy` type, no `NextTier(model)` function, and `ListRetryChain` (line 171) walks `ParentDispatchID` links but records no per-link model transition. Phase 2's plan language ("attempt 3 re-dispatches at the next tier up") describes the desired forge discipline but the plan doesn't identify that it must *replace* `Retry`'s model-copy behavior, not layer on top of it — a naive extension (e.g., a wrapper that calls `Retry` 3 times then does something else) would still produce two silent same-model retries indistinguishable from three, because `ShouldRetry`/`Retry` have no concept of "this is escalation attempt, use a different model."
- Suggestion: Phase 2's acceptance criteria should explicitly require a test that asserts `Retry`'s 3rd-attempt call receives a `Model` field different from attempts 1-2 (e.g., `TestRetry_EscalatesModelOnThirdAttempt`), and that the `RetryPolicy` struct gains a tier-escalation table (`sonnet→opus→fable`) consulted by attempt number — not just a policy comment in the plan doc.

### no-inspection-rubric-means-master-signs-own-work
- Severity: P1
- Where: §Phase 3 — "quality-gates gains a plan-conformance verdict distinct from review findings: the validator dispatch receives the criteria as its rubric, returns pass/fail per criterion" and §Gap 4 — "Validators don't check plan acceptance criteria... nothing threads the plan's verify blocks / Must-Haves to the validator as a rubric"
- What: The doctrine's Rule 3 ("Opus validates against the plan's acceptance criteria, never its own judgment") is the master-inspects-against-the-jig discipline — the inspector holds a fixed gauge, not an opinion. The plan correctly diagnoses (Gap 4) that this doesn't exist today, but Phase 3 describes the fix only at the level of "receives the criteria as its rubric" without specifying the mechanism that prevents the validator from *also* running its normal flux-drive review and blending the two into one verdict. If the plan-conformance verdict and the review-findings verdict share a gate or a scoring function, the master's fixed-gauge inspection collapses back into "the master's opinion, informed by a checklist" — which is exactly the failure mode Rule 3 exists to prevent.
- Evidence: Source domain — a master inspector's jig-and-water-test never gets averaged with "my gut sense the blade looks good"; a blade either passes the jig or it doesn't, full stop, and that result is never blended with taste. Target — `/clavain:quality-gates` → flux-drive currently produces one pass/fail per gate (per the survey's "Validation gate" bullet); Phase 3 needs to specify whether plan-conformance is a *separate, blocking* gate that can independently FAIL regardless of how flux-drive's stylistic/architectural findings score, or whether it's folded into the same verdict object where a strong review score could offset a failed criterion.
- Suggestion: State explicitly in Phase 3 (not left implicit) that plan-conformance is an independent, non-overridable gate: any criterion `false` → gate FAIL, regardless of flux-drive review severity distribution. Add this as an acceptance-criterion of Phase 3 itself ("gate FAILs when criteria=false even if all flux-drive findings are P3").

### no-canonical-form-lint-for-judgment-calls
- Severity: P2
- Where: §Design considerations — "Executor 'no judgment calls' enforcement: the doctrine requires execution-grade plans. Phase 3's criteria block helps, but nothing lints a plan for 'use your judgment' steps. Possible cheap check in write-plan or plan-review."
- What: This is filed as an open question, not a phase deliverable — meaning the plan as currently scoped can complete Phases 1-4 and still ship execution-grade plans that silently contain "use your judgment" steps handed to a sonnet-tier executor. In forge terms, this is the difference between transmitting a canonical form (exact heat, exact fold count, exact quench timing) versus transmitting "get it about right" — the latter is fine for a master's own hands, catastrophic for an apprentice who has no calibrated judgment yet to fall back on.
- Evidence: Source domain — canonical transmission in a lineage is enforced by rote repetition of an exact sequence with no tolerance for improvisation at the apprentice grade. Target — `/clavain:write-plan` (referenced in Phase 3) is the natural enforcement point, but the plan only speculates about it ("possible cheap check") rather than committing to it as a Phase 3 acceptance criterion or a Phase 5 backlog item with an owner.
- Suggestion: Promote this from "open question" to an explicit Phase 3 sub-task: a regex/lint pass in write-plan or plan-review that flags phrases like "use your judgment," "as appropriate," "if needed" in execution-grade (sonnet-targeted) plan sections, surfaced as a plan-review warning before the plan is handed to the executor tier.

### failure-record-shape-unspecified
- Severity: P3
- Where: §Phase 2 — "Record `escalation` evidence to interspect (agent, from_model, to_model, failure_mode, attempts)."
- What: The fields listed (agent, from_model, to_model, failure_mode, attempts) are a good start, but `failure_mode` — the one field that lets Phase 4's aggregation and future planners actually learn from repeated faults — has no defined vocabulary (is it a free-text string from the verdict sidecar? an enum of error classes? a link to the specific failing acceptance criterion?). A lineage's failure record is only useful if faults of the same *kind* can be counted and compared across incidents; an unstructured field defeats that.
- Evidence: Source domain — a forge's transmitted failure record names the specific fault (cracked at the shoulder from over-quenching, not "the blade broke") so the next apprentice is warned about the specific mechanism, not just told "failure happened." Target — `os/Clavain/scripts/dispatch.sh`'s `_extract_verdict` already emits pass/warn/error/retry sidecars (per the survey); Phase 2 should specify whether `failure_mode` is derived from that same fixed vocabulary or is a new open-ended field, since Phase 4's per-(author_tier, executor_tier) pass-rate aggregation (Rule 7) will need failure_mode to be a joinable, not free-text, dimension.
- Suggestion: Define `failure_mode` as a closed enum in Phase 2 (e.g., derived from existing verdict categories or a new small fixed set: `criteria_unmet`, `timeout`, `tool_error`, `scope_drift`), not a free-text field, so Phase 4 can aggregate it meaningfully.

## Verdict
The plan correctly names the swordsmith's two cardinal risks — apprentice-grade hands doing master-grade work, and the master inspecting his own strike — as Gaps 2 and 4, but leaves both fixes at the level of intent rather than binding acceptance criteria. The retry.go code as it stands today is a textbook same-hand-re-strike machine, and Phase 2's escalation language doesn't yet commit to replacing that behavior rather than layering on top of it.

# fd-hydraulic-diversion — round 0

## Findings Index
- [P0] escalation-oscillation-uncapped — the escalation ladder (sonnet→opus→fable) has no stated per-dispatch-chain cap or terminal relief valve to a human once fable itself fails, so a failing chain can recirculate without ever draining (§Phase 2, §Design considerations "Escalation loop guard")
- [P1] fable-unavailability-clamp-not-universal — the fable→opus fallback is only committed for "resolution calls" and "session model == fable" detection; subagent/dispatch call sites that select fable independently aren't confirmed to hit the same clamp, so a levee can still give way at an unaudited inlet (§Phase 1, §Design considerations "Fable-window detection")
- [P2] wrong-gauge-during-pilot-window — Phase 4 (the true gauge, plan→execution pass rate) depends on Phase 3, but Phases 1-2 ship and presumably run "in production" (pilot per Rule 6) before Phase 4's gauge exists, meaning the pilot itself is read by the old gauge (shipped count / delegation_outcome) it's supposed to replace (§Phase 4, §Rule 6, §Rule 7)
- [P2] no-dredging-cadence-for-routing-decisions — `routing_decisions` (every routing call) and escalation records are described as accumulating but the plan names no retention/aggregation cadence, so the sediment (unbounded decision log + escalation record growth) has no scheduled dredge before Phase 4's aggregation query runs (§Phase 4, "Cost telemetry" design note)

## Findings
### escalation-oscillation-uncapped
- Severity: P0
- Where: §Design considerations — "Escalation loop guard: two-strikes must not oscillate (escalate → frontier fails → re-plan → re-execute → fail again). Cap at one escalation per dispatch chain; after that, surface to the human."
- What: This is the single most dangerous gap in the plan and it is filed as an *open question*, not a phase deliverable with an owner or acceptance criterion. The text says "cap at one escalation per dispatch chain" as if it were already decided, but no phase (1-4) actually implements this cap — Phase 2 only says "attempt 3 re-dispatches at the next tier up," which describes the *upward* diversion, not the *terminal* relief valve when the diverted flow (fable) itself fails. Without a hard, code-enforced cap that routes to a human channel, a chain that escalates to fable, has fable's re-plan fail (fable is not infallible), and then re-enters at sonnet execution, has no stated mechanism preventing it from re-triggering its own two-strikes counter and escalating to fable again — a standing wave that consumes fable-tier tokens (the scarcest, most rationed resource in the whole system per the windowed-availability constraint) indefinitely.
- Evidence: Source domain — a diversion that surges back and forth without a fixed relief mark scours its own banks and eventually breaches; the Dujiangyan works' Feishayan spillway exists precisely so excess flow has exactly one designed exit, never a second lap through the same channel. Target — I read `core/intercore/internal/dispatch/retry.go`: `RetryCount` (used in `ShouldRetry`, line 72) is scoped to a single dispatch's retry chain via `ParentDispatchID`, and `ListRetryChain` (line 171-215) can enumerate a chain's full history — but nothing in the plan specifies that a *new* dispatch chain spawned from a failed escalation (e.g., fable's re-plan output feeding a fresh sonnet execution dispatch) inherits or checks the original chain's escalation count. If the re-plan creates a structurally new `ScopeID`/dispatch lineage rather than continuing the same `ParentDispatchID` chain, `RetryCount` resets to 0 and the two-strikes counter — and therefore the escalation cap — silently resets too.
- Suggestion: Make "cap at one escalation per dispatch chain" a Phase 2 acceptance criterion, not a design note: define what "chain" means across a re-plan boundary (does a fable re-plan spawn a new `ScopeID`, and if so, how is the escalation count propagated to it?), and require a test that a chain which fails after escalating to fable surfaces to the human rather than silently starting a fresh chain with `RetryCount=0`.

### fable-unavailability-clamp-not-universal
- Severity: P1
- Where: §Phase 1 — "Graceful degradation: fable availability is windowed (subscription). Router must clamp/fallback fable→opus when unavailable, never hard-fail." and §Design considerations — "Simplest: treat session model == fable as the signal (the spec only loads then), with opus fallback baked into resolution for subagent dispatches that can't reach fable."
- What: The plan states the *intent* (never hard-fail) and sketches *one* signal (session-model check) but the survey itself documents that `_routing_model_tier` in `lib-routing.sh` (verified: line 68, tiers are haiku=1/sonnet=2/opus=3, no fable entry exists yet) is the safety-floor clamp function, and Phase 1 must add fable as a 4th tier to it. A graduated diversion structure needs the clamp enforced at *every* inlet where fable could be selected — but the plan names only two: the top-level "session model == fable" gate and "opus fallback baked into resolution." It doesn't enumerate the dispatch call sites (Codex delegate dispatches, subagent spawns inside a sprint that never see the interactive session's model context) as a checklist, so a spillway could exist at the top of the works while a side channel downstream still has a plain levee.
- Evidence: Source domain — a conservancy audits every gate along the main channel and every offtake, not just the headworks, because floodwater finds whichever inlet lacks a spillway. Target — `os/Clavain/scripts/lib-routing.sh:903-910` (per the survey) is the fast path Clavain's bash router already delegates to; the survey separately notes the Go router in `internal/routing` "doesn't support kernel overrides yet," meaning any dispatch path that goes through the Go fast-path instead of the bash path bypasses the agency-spec mechanism entirely — which would also bypass whatever fable-clamp Phase 1 adds only to the bash side, unless Phase 1 explicitly confirms the Go path can never independently select fable (it likely can't today only because fable doesn't exist in its vocabulary yet — the moment Phase 1 or a later phase adds fable anywhere the Go router touches, this needs re-auditing).
- Suggestion: Phase 1's acceptance criteria should include an explicit enumeration of every call site that can resolve to fable (bash router, Go router fast-path, subagent dispatch, Codex delegate), with a test proving each one clamps to opus when the fable-availability signal is false — not just the primary `routing_resolve_model --phase=planned --category=planning` example given.

### wrong-gauge-during-pilot-window
- Severity: P2
- Where: §Phase 4 (depends on Phase 3) vs. §Rule 6 ("Pilot 2–3 items through the full loop before fanning out a plan backlog") and §Rule 7 ("Measure plan→execution pass rate, not shipped count")
- What: The plan sequences the gauge (Phase 4, plan_execution_outcome) *after* the mechanism it's meant to validate (Phases 1-3). But Rule 6 says to pilot 2-3 items through "the full loop" before fanning out — and the only loop that exists to pilot during Phases 1-2's rollout is the pre-Phase-4 world, where the only available readings are shipped count and delegation_outcome (codex-delegate pass rate), which the plan itself calls the wrong gauge in the Gap 5 analysis. This means the pilot phase — the most safety-critical moment, when trust in the new escalation ladder is lowest — is judged by exactly the metric the plan says must not be trusted (Gap 5), and the correct gauge only comes online after Phase 3 ships.
- Evidence: Source domain — a conservancy never commissions a new channel's pilot flow while reading last year's water-level mark; it either waits for the new gauge stone to be carved, or runs the pilot at deliberately low volume specifically because it's flying blind on the new mark. Target — the plan has no equivalent "run Phases 1-2 pilot at deliberately reduced volume / cheap-to-revert scope" statement; it also doesn't say whether Phase 4's `plan_execution_outcome` can be backfilled retroactively for the Phase 1-2 pilot items once it lands, which would let the pilot's true pass-rate be recovered after the fact even though it wasn't visible in real time.
- Suggestion: Either (a) explicitly sequence Phase 4 (or a minimal slice of it — just the evidence-write, not the full aggregation view) earlier, ahead of or parallel with Phase 2, so the pilot's escalation events are captured under the correct gauge from day one, or (b) if sequencing must stay as-is, add an explicit note that Phase 1-2 pilot items get their plan_execution_outcome backfilled once Phase 3/4 land, so the pilot's true pass rate isn't lost to the old gauge.

### no-dredging-cadence-for-routing-decisions
- Severity: P2
- Where: §Design considerations — "Cost telemetry: `routing_decisions` + interstat session-cost should let us verify the doctrine's economic premise... Worth a dashboard query once Phase 4 lands." and §Phase 4 — "`/interspect:calibrate` aggregates into a plan-pass-rate metric"
- What: `routing_decisions` persists every single routing call (per the survey: "Every decision persists to a routing_decisions table"), and Phase 2 adds escalation records on top. The plan treats both as inputs to a future dashboard/aggregation query but never states a retention policy, pruning cadence, or index strategy — the equivalent of a conservancy that plans to read the water-level mark next year but never schedules the annual dredge that keeps the channel bed at a known depth. If `routing_decisions` grows unbounded across every kernel-tracked sprint and every dispatch (not just escalations), Phase 4's aggregation query risks the same fate as any analytics table without a maintenance cadence: it slows down, or gets queried against partial/stale data because nobody defined what "current" means for a rolling pass-rate metric.
- Evidence: Source domain — sediment un-dredged doesn't just look bad, it raises the bed until the channel's capacity for its designed flow silently shrinks. Target — the survey confirms `routing_decisions` records agent/model/rule_matched/floor_applied/candidates/excluded/complexity per call — a wide row, likely written on every single dispatch across every sprint, with no stated TTL or archival step anywhere in the four phases.
- Suggestion: Add a Phase 4 (or Phase 5 backlog) line item defining the retention/aggregation cadence for `routing_decisions` and escalation records — e.g., roll up to a per-day/per-week summary table that `/interspect:calibrate` reads, with raw rows pruned or archived past a fixed window — so the north-star metric is read from a maintained gauge, not an ever-growing raw log.

## Verdict
The plan's most severe latent risk is the escalation-oscillation guard being filed as an unresolved design question rather than a Phase 2 deliverable — the one place a real standing wave (repeated fable escalation with no terminal relief) could silently burn the scarcest resource in the system. The fable-clamp and gauge-sequencing gaps are real but secondary: they degrade quality and trust during rollout rather than risking an unbounded resource drain.

## Findings

### [P1] Sealed-standard has no custody lock

**Where:** `docs/brainstorms/2026-07-05-autonomous-capability-routing-intercore.md:62-64` (Phase 3, Sylveste-fc5.3)

**What:** The plan states criteria are emitted by `/clavain:write-plan` and "stored as a run artifact (`set-artifact acceptance-criteria`)," then later "the validator dispatch receives the criteria as its rubric." Nothing in the phase description specifies that the artifact is write-once. In the assay office, the reference fineness is a standard held in trust *before* the piece is presented — the assayer cannot accept a new standard handed over by the maker mid-assay, because that collapses the "measured against an external fixed point" property into "measured against whatever the maker now says it should be." Two-strikes escalation (Phase 2) explicitly allows re-dispatch after a failure — if the escalated attempt is preceded by, or triggers, another `write-plan` pass (e.g., fable replanning after two sonnet failures, per Rule 4's "escalate to frontier tier" going through planning again), and that pass calls `set-artifact acceptance-criteria` again on the same run, the artifact the validator checks against is now authored *after* seeing why the first attempt failed — the standard has been reshaped by information the maker wasn't supposed to have when the "trial plate" was cast. This is not the already-flagged "criteria regenerated by the same model family" case (P1 in the lens's own severity table, which is about the executor's tier authoring the rubric) — this is about the *artifact's mutability window*, independent of which tier writes it.

**Evidence:** Line 63: "Criteria stored as a run artifact (`set-artifact acceptance-criteria`)" — no versioning, no immutability flag, no distinction between "initial seal" and "amended after escalation" mentioned anywhere in Phase 2 or Phase 3. Phase 2 (lines 53-59) describes escalation attempts but never states whether an escalated attempt is barred from touching the plan/criteria artifact set at Phase 3's seal point.

**Suggestion:** Smallest viable fix — `set-artifact acceptance-criteria` should be call-once per run (kernel rejects a second write to the same key, or requires an explicit `--supersede` with a superseding evidence record naming the reason), and Phase 2's escalation path should be checked against "did this run already seal criteria" before allowing any write-plan re-invocation to touch that key.

### [P1] Chain-of-punches breaks between the gate and the ledger

**Where:** `docs/brainstorms/2026-07-05-autonomous-capability-routing-intercore.md:64` (Phase 3 gate) and `:68` (Phase 4 evidence)

**What:** Phase 3's gate "returns pass/fail per criterion; gate FAIL blocks advancement when any criterion fails" — so per-criterion results exist transiently at gate-evaluation time. Phase 4 then wants to write `plan_execution_outcome` with "criteria pass/fail counts" as one of its provenance fields. But Phase 3 never states that the per-criterion breakdown is itself persisted anywhere the Phase 4 evidence-writer can read from — only that the *gate's aggregate* (advance/block) is acted on by `clavain-cli enforce-gate` (per the Reusable Mechanism section, line 31). This is the hallmark equivalent of the assayer weighing each grain of the sample separately, calling out a verdict, and then the office's permanent register recording only "passed" or "failed" for the whole piece with no line for which grain was under-fine — Phase 4's stated intent ("criteria pass/fail counts") requires a punch that Phase 3 as scoped never strikes into durable storage. If the per-criterion counts are reconstructed post-hoc from gate logs rather than a structured evidence write at gate time, Phase 4 either can't deliver the field it promises or silently substitutes a coarser signal (e.g., re-deriving counts from unstructured flux-drive output), and the plan-pass-rate metric in Phase 4 is then built on a field that was never actually punched at the point of assay.

**Evidence:** Phase 3 bullet ends at "gate FAIL blocks advancement" (line 64) with no artifact-write step named. Phase 4 bullet (line 68) lists "criteria pass/fail counts" as a `plan_execution_outcome` field with no back-reference to where in Phase 3 that per-criterion structure gets persisted (vs. the gate's own pass/warn/error/retry verdict sidecars already emitted by `dispatch.sh` for the review-finding gate, per the Reusable Mechanism section — those sidecars are a different, coarser mechanism than "per acceptance-criterion pass/fail").

**Suggestion:** Phase 3's acceptance criteria should specify that the validator dispatch writes a structured per-criterion result set (criterion id → pass/fail) as its own evidence record at gate-evaluation time, and Phase 4 should read from that record rather than assuming the field materializes for free. One diff hunk: add "validator writes `plan_conformance_result{criterion_id, pass}[]` evidence alongside the gate verdict" to Phase 3's acceptance criteria.

### [P2] Trial-of-the-Pyx metric blind spot: validator drift is invisible in the wrong axis

**Where:** `docs/brainstorms/2026-07-05-autonomous-capability-routing-intercore.md:68-69` (Phase 4, Sylveste-fc5.4)

**What:** `plan_execution_outcome` captures "plan author model, executor model, validator model" (line 68) — so the validator identity *is* recorded, which is good custody practice. But the aggregation step immediately narrows the lens: `/interspect:calibrate` "aggregates into a plan-pass-rate metric per (author_tier, executor_tier) pair" (line 69) — validator_tier is captured in the record but dropped from the reporting dimension. In the assay-office frame this is subtler than "nobody tries the assayer" (the lens's own P2, which is about the *absence* of any audit mechanism) — here the raw material for detecting assayer drift exists in the ledger, but the published hallmark statistics collapse across it. If opus (the validator) becomes systematically more lenient over time — say, after a prompt or context change makes it pattern-match "looks like it followed the plan" rather than checking criteria literally — every (author_tier, executor_tier) pair's pass rate rises together. Because the metric is sliced only by author/executor, that rise reads as "sonnet execution quality improved" or "fable planning improved," which is exactly the false-positive that would justify Rule 6's "pilot 2-3 items then widen autonomy" — widening autonomy on a signal that is actually validator drift, not execution improvement. The office's own trial-plate exists in the data model (the validator_model field) but is never read back out as its own trend line.

**Evidence:** Line 68 lists validator model as a captured field; line 69's aggregation key is `(author_tier, executor_tier)` only — validator_tier does not appear in the aggregation key or anywhere in the reporting surface described ("`/interspect:delegation-status` or a new routing-effectiveness view," line 70).

**Suggestion:** Add validator_tier (or validator_model) as a reportable slice — at minimum, a per-validator pass-rate trend view so a sudden across-the-board rise for one validator model, uncorrelated with executor/author changes, is distinguishable from genuine capability improvement. This is a query/view addition, not a schema change, since the field is already captured.

### [P2][t] Fable-window self-attestation has no office-side counter-punch

**Where:** `docs/brainstorms/2026-07-05-autonomous-capability-routing-intercore.md:80` (Design considerations, "Fable-window detection")

**What:** The plan's own open question proposes: "Simplest: treat session model == fable as the signal (the spec only loads then)." In the assay-office frame, this is the maker declaring his own material grade and the office accepting the declaration as the trigger for which inspection regime applies — the gravest hallmarking offense the lens tracks (forging/self-applying the standard mark) is usually about the *output* mark, but here the self-attestation is upstream of that: the session's self-report of "I am fable" is what loads the capability-routing agency spec that then determines which tier plans, which executes, and which validates for the entire run. If the self-report is wrong (a session is actually running as opus but the environment variable, config flip, or probe the plan mentions as candidate mechanisms misreports "fable"), the whole tier assignment for that run is built on an unverified assertion from the party whose work will later be assayed against criteria that same tier-assignment-collapse determines who writes. This is tagged aesthetic/thin because the plan already flags it as an open design question rather than a settled mechanism (it's explicitly unresolved, not a shipped gap) — but it's worth naming because none of the three candidate options listed (env var, probe, static config flip) include a kernel-side independent verification step, and the doctrine's entire tier-separation guarantee (Rule 3: "Opus validates... never its own judgment") rests on tier identity being trustworthy at assignment time, not just at validation time.

**Evidence:** Line 80: "Simplest: treat session model == fable as the signal (the spec only loads then), with opus fallback baked into resolution for subagent dispatches that can't reach fable" — no mechanism proposed for the kernel or agency-spec loader to independently confirm the self-reported tier before trusting it as the routing switch.

**Suggestion:** When this open question is resolved (likely early Phase 1 implementation work), prefer a signal source outside the session's own self-report — e.g., a kernel-side capability probe or a session-start hook that inspects the actual model binding rather than trusting an in-session variable the running model itself could (accidentally or via a compromised subagent prompt) misreport.

## Verdict

The design's core custody idea is sound — Phase 3 introduces a real sealed-artifact concept (`set-artifact acceptance-criteria`) and Phase 4 captures the right provenance *fields* (author/executor/validator model) in principle. But as scoped, two punches in the chain are still soft: the seal has no stated immutability lock against a later write-plan pass (P1), and the per-criterion detail the gate produces has no named durable-write step for Phase 4 to actually consume (P1) — meaning Phase 4's headline field ("criteria pass/fail counts") may not exist to aggregate from. The Trial-of-the-Pyx material exists in the schema (validator_model) but is invisible in the reporting dimension chosen (P2), so the one signal that would catch a drifting assayer is captured and then discarded at aggregation time. None of this requires a rewrite: a write-once constraint on the criteria artifact, a per-criterion evidence write at gate time, and a validator_tier slice in the calibrate output would close all three at the diff-hunk level the lens prizes.

# fd-routing-kernel-mechanics — round 1

## Findings Index
- [P1] escalation-cap-has-no-substrate — oscillation risk is real: `RetryCount`/`ParentDispatchID` reset to zero on any fresh `Create()`, and nothing ties a "dispatch chain" identity across re-triggers (§Design considerations "Escalation loop guard")

## Findings

### escalation-cap-has-no-substrate
**Severity:** P1
**Where:** `core/intercore/internal/dispatch/dispatch.go:105-118` (`generateID`), `retry.go:97-145` (`Retry`), `retry.go:169-215` (`ListRetryChain`)
**What:** The prior cluster (f-005/f-016) is **confirmed** — the oscillation risk is real, and worse than "no cap," it's "no substrate to cap." `Dispatch.ID` is a fresh random 8-char ID on every `store.Create()` call (dispatch.go:106-118), with no default relationship to any prior dispatch. The *only* mechanism that links a new dispatch to an old one is `ParentDispatchID`, and that field is populated in exactly one place: `Retry()` (retry.go:128), which only runs when `ShouldRetry()` (retry.go:65-83) is true — i.e., `d.RetryCount < policy.MaxRetries` (default 3, retry.go:22) and status is Failed/Timeout. The moment a task is **re-triggered as a new top-level dispatch** (e.g., `/sprint` re-invoked after a fable failure, a fresh `ic dispatch` call, or a new session picking the task back up), it calls `store.Create()` directly with `ParentDispatchID` left at its zero value `""` and `RetryCount` at `0`. `ListRetryChain` (retry.go:171-215) walks backward via `ParentDispatchID` to find the "root," but a dispatch with `ParentDispatchID == ""` *is* a root by definition — there is no way to distinguish "genuinely new task" from "same task, escalation ladder already exhausted, being re-tried by a human/session that doesn't know that." `ScopeID` (dispatch.go:62, spawn.go:26/96) is the only cross-dispatch grouping primitive that survives a fresh `Create()`, but it's caller-supplied free-form grouping (used today for coordination/observation, sentinel.go, phase.go), not an escalation-chain identity — nothing currently writes or reads it for retry/escalation purposes (confirmed via grep: zero hits for "escalat" in dispatch.sh or any non-test dispatch/*.go file — Phase 2 is fully greenfield on both bash and Go sides).
**Evidence:** `generateID()` at dispatch.go:105 has no seed/parent parameter. `Retry()` at retry.go:113-130 builds a new `&Dispatch{...ParentDispatchID: originalID, RetryCount: attempt...}` — this is the *only* call site across the package (non-test) that sets `ParentDispatchID` to anything but empty. `grep -rn "escalat" core/intercore/internal/dispatch/*.go os/Clavain/scripts/dispatch.sh` returns nothing outside a Windows process-kill comment — confirming Phase 2 has zero existing state to build the cap on top of.
**Suggestion:** Do not try to detect "is this a re-trigger of an exhausted chain" by walking `ParentDispatchID` from a fresh root — that graph edge doesn't exist across a re-trigger, by construction. The cap needs an identity that outlives the dispatch row itself (see next finding).

### minimal-fix-is-chain-id-on-scope-or-artifact
**Severity:** P1
**Where:** Phase 2 plan (brainstorm §Phase 2, "Extend `internal/dispatch/retry.go` with an escalation policy"); `core/intercore/internal/dispatch/spawn.go:26,96` (`ScopeID` as the existing grouping primitive); the doctrine's "acceptance-criteria block stored as a run artifact" pattern already used in Phase 3 (`set-artifact acceptance-criteria`)
**What:** The minimal guard that survives re-triggering across sessions is **one new persisted key, not a dispatch-table field** — because the dispatch table's own identity (`ID`, `ParentDispatchID`, `RetryCount`) is exactly what resets on re-trigger. Concretely: introduce a stable `EscalationChainID` derived from something that *is* stable across re-triggers — the bead/task ID plus phase (e.g., `<bead-id>:<phase>`, since a given plan-execution slot for a given bead is the natural unit doctrine Rule 4 is scoped to) — and store escalation count against that key in a place that outlives any single dispatch: either (a) a new `intercore_state` key (`escalation.count.<bead-id>.<phase>`, read the same way `agency.models.${phase}` is read today per the brainstorm's own "critical hook, verified" pattern) or (b) a row in a new small table keyed by that composite ID with a `TerminalAt`/`SurfacedToHuman` flag. `Retry()` should take this ID as an explicit parameter (not infer it), and the two-strikes ladder in Phase 2 should check-and-increment it *before* creating the new dispatch, refusing (returning "surface to human" rather than silently creating a fresh root) once the cap is hit — regardless of whether the new call is a `Retry()` continuation or a brand-new `store.Create()`. This is the only design that closes the gap identified above: the cap must live keyed on task identity, not dispatch-chain identity, precisely because dispatch-chain identity doesn't survive the re-trigger case the brainstorm is worried about.
**Evidence:** The brainstorm's own Phase 1 already establishes the pattern this borrows from: `intercore_state_get "agency.models.${phase}"` is read as "step 0" ahead of everything else (brainstorm line 29) — a per-run state key that isn't tied to any single dispatch row. The same mechanism generalizes to a per-task escalation counter.
**Suggestion:** Add `EscalationChainID string` (or reuse `ScopeID` if it's guaranteed task-stable, which needs verification — see open question below) as an explicit parameter to a new `EscalateOrRetry()` function in retry.go, and persist the count via `intercore_state_set`/`_get` keyed on it, not via `RetryCount` on the dispatch row. Flag as a question: is `ScopeID` already guaranteed to be stable and task-derived across every call site that would re-trigger a task (sprint re-invocation, manual re-dispatch, session restart)? If yes, reuse it directly instead of adding a new field. If `ScopeID` is sometimes session-derived or randomly generated per invocation (unverified in this pass — spawn.go:96 shows it's caller-supplied with no stability contract), a new dedicated key is required.

### retry-go-has-no-tier-stepping-hook-today
**Severity:** P2
**Where:** `core/intercore/internal/dispatch/retry.go:112-130`
**What:** Separate from the chain-identity gap, the mechanical seam for "attempt 3 re-dispatches at the next tier up" doesn't exist yet either. `Retry()` builds the new `Dispatch` with `Model: orig.Model` (retry.go:121) — a hardcoded same-model copy. `RetryPolicy` (retry.go:11-17) has no model-escalation field at all (no `EscalateModelFn` or `TierLadder []string`). Phase 2 will need to either add a policy field (e.g., `EscalateAt int` + a tier-lookup callback) or branch in the caller before invoking `Retry()`. This is a smaller, more mechanical gap than the chain-identity one — noted for completeness since it's the literal code Phase 2 says it will extend, but it doesn't independently threaten correctness the way the missing chain identity does (it's an additive change, not a data-modeling gap).
**Evidence:** retry.go:121 `Model: orig.Model,` is the only place model is set in the retry path; `RetryPolicy` struct (retry.go:11-17) has five fields, none referencing model/tier.
**Suggestion:** Add `EscalateModel func(currentModel string, attempt int) (newModel string, escalated bool)` to `RetryPolicy`, call it in `Retry()` before constructing `d.Model`, and record `escalated`/`from_model`/`to_model` alongside the existing retry evidence — matches the brainstorm's own "Record `escalation` evidence to interspect (agent, from_model, to_model, failure_mode, attempts)" requirement in Phase 2.

## Verdict
The prior cluster's claim is **confirmed and sharpened**: the oscillation risk isn't just "no cap exists" — it's that the two fields that *would* naturally carry a cap (`RetryCount`, `ParentDispatchID`) are scoped to a single dispatch-row lineage created by `Retry()`, and that lineage is severed by construction the instant a task is re-triggered as a new top-level `store.Create()` call (no special re-trigger detection exists or is planned). The minimal fix is not "add a cap field to `Dispatch`" but "key the cap on task identity that outlives any dispatch row" — a new `intercore_state`-backed counter (or table row) addressed by `<bead-id>:<phase>` or a verified-stable `ScopeID`, checked before every dispatch creation (retry or fresh), not derived from walking `ParentDispatchID`. Phase 2 as currently scoped ("extend retry.go with an escalation policy") undersells the work: it needs a persistence decision that sits alongside retry.go, not inside it.

## Findings

### Finding 1 — Escalation spillway drains the hard tail from the executor-tier sample before Phase 4's metric is even defined

**Severity:** P0

**Where:** `docs/brainstorms/2026-07-05-autonomous-capability-routing-intercore.md` Phase 2 (lines 53-58) × Phase 4 (lines 66-71); infra: `core/intercore/internal/dispatch/retry.go:97-145` (`Retry`, copies `orig.Model` verbatim, no tier field); target schema: none yet — `plan_execution_outcome` is greenfield.

**What:** Phase 2 designs the two-strikes escalation ladder as a re-dispatch that "re-dispatches at the next tier up (sonnet→opus→fable)" — i.e., the failed attempt's *identity* changes tier mid-chain. Phase 4 then proposes aggregating `plan_execution_outcome` "per (author_tier, executor_tier) pair" as the metric that "gates widening autonomy." Read together: every task hard enough to fail sonnet twice is, by construction, removed from the sonnet-executor population and deposited into the opus-executor (or fable-executor) population at the moment it escalates. The plan never specifies whether an escalated task's outcome record attributes to the *original* executor_tier (sonnet, which "failed") or the *escalated* one (opus, which "passed"), nor whether escalated tasks are excluded from the per-tier pass-rate denominator. Because `retry.go`'s existing `Retry()` creates a brand-new dispatch row with `ParentDispatchID` linking back — the only artifact that could disambiguate "this opus success was actually a sonnet failure's rescue" — and Phase 4 doesn't mention consuming that link, the natural implementation is "each dispatch's own executor_tier," which silently drains sonnet's hardest cases into opus's sample and inflates both tiers' apparent competence simultaneously. This isn't a possible bug to watch for — it's the default behavior of composing an as-designed escalation ladder with an as-designed per-tier aggregation with no stratification rule connecting them.

**Intersection justification:** fd-eval-calibration-metrics alone would flag "aggregating by executor_tier needs a sampling/stratification note" as a generic confound-control gap — true but abstract, the kind of comment that applies to any tiered metric. fd-hydraulic-diversion alone would flag "the escalation path needs to record from_model/to_model for observability" — true but reads as a logging nicety, not a metric-corrupting event. Neither alone reaches the specific causal claim: *this particular spillway (escalation-on-2nd-failure) is the exact mechanism that populates this particular gate-governing number's sample, and it does so asymmetrically by construction* (hard tasks flow one direction, never back). Only fusing "where does escalation physically route the dispatch record" (hydraulic) with "what does the pass-rate metric assume about its sample's independence across tiers" (eval) produces the finding that the doctrine's own economic premise (Rule 7, "measure plan→execution pass rate, not shipped count") is unmeasurable without first deciding how escalated dispatches are attributed — and the plan is silent on that decision.

**Suggestion:** Add one field to the (not-yet-written) `plan_execution_outcome` schema: `escalated_from_tier` (nullable), populated from `Dispatch.ParentDispatchID` → `Dispatch.Model` when non-empty (the linkage `retry.go:184` already walks). Phase 4's `/interspect:calibrate` aggregation should either (a) attribute escalated successes to the *originating* tier's attempt count (fails, then a separate escalation-rescue counter) or (b) explicitly exclude escalated dispatches from the per-tier pass-rate denominator and report `escalation_count` as its own axis, not folded into pass-rate silently. Either is a one-column, one-aggregation-clause fix — not a schema redesign.

### Finding 2 — `calibration.mode: enforce` precedent is the live template Phase 4 will copy, and it shipped on a self-reported N with no stated threshold

**Severity:** P1

**Where:** `os/Clavain/config/routing.yaml:171-172` (`calibration: mode: enforce  # Promoted from shadow 2026-04-01. 21+ sprint sessions + 498 closed beads provide calibration baseline.`) × brainstorm doctrine Rule 6 (line 18, "Pilot 2–3 items through the full loop before fanning out") and Phase 4 (lines 66-71, "This is the north-star metric that gates widening autonomy (pilot 2–3 items first, per doctrine Rule 6)").

**What:** The plan cites Rule 6's 2-3-item pilot as the gate for widening autonomy on the new plan-pass-rate metric, but the codebase already contains the precedent for how that gate actually gets exercised in practice: B3 calibration's own mode flip from `shadow` to `enforce`, justified by a comment citing "21+ sprint sessions + 498 closed beads" — a much larger N than 2-3, but one arrived at by the same evidence-accumulates-then-someone-decides-it's-enough pattern, with no codified minimum-N or statistical-power threshold anywhere in `routing.yaml` or `calibrate.md`. `_interspect_compute_agent_scores` (per `calibrate.md:11`) requires only ">= 3 evidence sessions per agent before scoring" — a threshold clearly aimed at avoiding zero-sample noise, not at ensuring the sample spans stable operating conditions. Phase 4 will almost certainly reuse this same `>=3` sufficiency bar (it's the only precedent in the codebase) for the new per-(author_tier, executor_tier) pass-rate, at exactly the moment doctrine Rule 6 says the sample IS 2-3 pilot items — meaning the "sufficient evidence" gate and the "still-piloting, low-water" state are the same N, and the plan never distinguishes them.

**Intersection justification:** fd-eval-calibration-metrics alone would flag "a 2-3 item pilot has no statistical power to detect a pass-rate difference between tiers" — a pure sample-size critique that exists regardless of any infrastructure. fd-hydraulic-diversion alone would flag "the mode:shadow→enforce transition needs a documented cutover criterion" — a pure plumbing-governance critique about missing process, independent of what the metric measures. The fused finding is narrower and only visible by tracing both together: the *specific* threshold value already hardcoded in the *specific* flow this plan extends (`>=3 sessions`, `calibrate.md:11`) is the same order of magnitude as the *specific* pilot size doctrine mandates (2-3 items), so the existing infrastructure's "sufficient to score" bar and the plan's "still just piloting" bar collide at the same N — a plumbing precedent (this exact enforce-mode flip pattern) directly undermining a measurement-validity requirement (power to detect a real tier difference) that neither the schema nor the doctrine text calls out.

**Suggestion:** Phase 4 should state an explicit minimum-N for the plan-pass-rate metric that is distinct from (and larger than) both the pilot size and the generic `>=3` calibration-sufficiency bar — e.g., require N to be large enough per (author_tier, executor_tier) cell before that cell's rate feeds `interspect:calibrate`'s autonomy-widening decision, and have the pilot phase explicitly marked as excluded from (or separately weighted against) the enforce-worthy sample, mirroring the distinction the plan already almost draws in its "Design considerations" section but doesn't operationalize as a number.

### Finding 3 — Fable-window author_tier is sourced at spec-load time, and the codebase's own retry-chain primitive already proves what "resolved tier at dispatch time" looks like

**Severity:** P1

**Where:** Design considerations § "Fable-window detection" (lines 80, "treat session model == fable as the signal (the spec only loads then), with opus fallback baked into resolution for subagent dispatches that can't reach fable") × Phase 1 acceptance (lines 45-51) × `core/intercore/internal/dispatch/retry.go:169-215` (`ListRetryChain`).

**What:** The plan's own charter (parent fd-hydraulic-diversion's finding #3, already captured in the agent's severity calibration) flags that author_tier is recorded from the loaded agency spec's intent rather than the actually-dispatched tier post-fallback. What sharpens this into an actionable, non-redundant finding at the fused level is that the codebase already contains the exact mechanism needed to source the correct value: `ListRetryChain` (`retry.go:169-215`) walks `Dispatch.ParentDispatchID` to reconstruct which model actually executed at each link in a chain — proving the dispatch layer already tracks "resolved tier per attempt" as a first-class concept, just not yet threaded to agency-spec author attribution. The plan's Design Considerations section treats fable-window detection as an open question ("how does the router know fable is currently available?") without noticing that the answer the codebase needs isn't better *availability detection* — it's *recording resolution outcome after the fact*, which `retry.go` already models for escalation chains and Phase 1 could reuse for spec-load fallback (opus-standing-in-for-fable) with zero new mechanism, only a wiring change.

**Intersection justification:** fd-eval-calibration-metrics alone would say "author_tier must reflect actual production, not intent" — a standard construct-validity point. fd-hydraulic-diversion alone would say "the fallback path needs a clamp/fallback event to be observable" — a standard plumbing-observability point. The fusion is the specific, falsifiable claim that the *plumbing fix already exists in the repo* (the retry chain's parent-link resolved-model walk) and the measurement gap is purely a wiring omission, not a missing primitive — which changes the suggested fix from "design a resolved-tier tracking mechanism" (expensive) to "reuse `ListRetryChain`'s pattern for spec-load fallback" (cheap), a claim only visible by cross-referencing the flow-mechanics code against the metric's sourcing requirement simultaneously.

**Suggestion:** When `/sprint` loads the capability-routing agency spec and fable is unavailable (opus fallback fires per line 48), write a `routing_decisions` row (already the sanctioned mechanism, `decision.go:80-122`) with `rule_matched="agency-fallback"` and `floor_from="fable"`/`floor_to="opus"` (the `FloorFrom`/`FloorTo` fields already exist in the `Decision` struct at `decision.go:25-26` and are unused for this case). Phase 4's `author_tier` should be sourced by joining `plan_execution_outcome` to the nearest preceding `routing_decisions` row's `selected_model`/`floor_to`, not the agency spec's declared intent — the join key and fallback-tracking fields already exist; nothing new needs building.

## Findings

### third-plugin-agent-has-no-dispatch-path
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` Track 1 Wire (step 1) and Key Decision 1; grounding at `interverse/interflux/skills/flux-engine/references/agent-roster.md` lines 9-13 and 26-42.
- **What:** `agent-roster.md`'s Step 1.2 taxonomy has exactly three dispatchable categories: **Project Agents** (`.claude/agents/fd-*.md`, invoked as `general-purpose` with the file content pasted into the prompt), **Plugin Agents (interflux)** (invoked via `subagent_type: interflux:review:fd-*`), and **Research Agents / Oracle**. fd-integration is registered by `interverse/intertrace/.claude-plugin/plugin.json` (`"agents": ["./agents/review/fd-integration.md"]`) — it is a **third-party plugin agent**, structurally distinct from both categories the roster's dispatch logic actually branches on. The brainstorm's "wire" step (add a roster entry) treats this as a bookkeeping gap, but there's no confirmed `subagent_type` string (e.g. `intertrace:review:fd-integration`) for a plugin-owned agent outside interflux itself, and no roster section that says how to invoke one.
- **Evidence:** `agent-roles.yaml:49` has the line (`- fd-integration  # intertrace: cross-module integration review`), confirming the brainstorm's claim it's absent from `agent-roster.md` (zero grep matches). But `agent-roster.md` lines 9-13 only branch on Project vs. interflux-Plugin; there is no "Plugin Agents (other plugins)" section. Whatever evidence-acquisition shape is picked, it inherits this unresolved dispatch question — the tracer-evidence architecture is moot if the agent can't be invoked with a working `subagent_type` in the first place.
- **Suggestion:** Before scoring (a)/(b)/(c), the wire step needs to nail down and document the actual invocation mechanism for a third-party plugin agent (either a new roster category, or an explicit precedent showing `subagent_type: intertrace:review:fd-integration` already works elsewhere). This is upstream of the evidence-substrate question and changes which shapes are even reachable — e.g., (b)'s orchestrator-injection assumes flux-drive's dispatch code path recognizes fd-integration as a first-class citizen it can pre-feed, which is a stronger assumption than the roster currently supports for non-interflux plugin agents.

### composer-precedent-omitted-from-scoring
- **Severity:** P1
- **Where:** `interverse/interflux/skills/flux-engine/phases/launch.md` Step 2.0.4 ("Composer dispatch plan"); brainstorm Open Questions / "Tracer invocation path."
- **What:** flux-drive already has exactly the orchestrator-pre-computation shape the brainstorm frames as novel and costly: `compose_dispatch()` returns an "authoritative" pre-computed agent plan that (when present) causes the launch phase to **skip Steps 2.0.5–2.1e entirely** and dispatch agents straight from the plan. This is real, live orchestrator-side injection infrastructure, not a hypothetical. Candidate (b) ("flux-drive orchestrator pre-runs tracers and injects typed evidence") is structurally the same shape as Composer's dispatch-plan injection, just for evidence payloads instead of agent-selection payloads. The brainstorm's cost claim — "requires flux-drive engine changes, which conflicts with the pilot's design goal of costing 'one roster entry'" (per the agent's own P1 calibration example) — is asserted without checking whether the Composer's existing plan schema could carry a typed-evidence field, which would make (b) cheaper than assumed, or whether it's already the wrong extension point, which would make it a distinct, confirmed cost. Either way the check wasn't done.
- **Evidence:** `launch.md` lines ~55-60 (Step 2.0.4): "If the Composer is available... query `compose_dispatch`... the plan is authoritative — skip Steps 2.0.5–2.1e... dispatch agents from the plan." This is a concrete, already-shipped precedent for exactly the class of change candidate (b) proposes, and it isn't referenced anywhere in the Open Questions or Key Decisions.
- **Suggestion:** Score candidate (b) against the actual Composer schema — does `compose_dispatch`'s plan format have (or could cheaply gain) a slot for pre-computed evidence blobs per agent? If yes, (b)'s "touches the engine" cost is much smaller than the brainstorm assumes and its scoring should be revisited. If no (Composer is agent-selection-only by design and evidence injection is a different concern), say so explicitly as the reason (b) is deferred, rather than leaving the cost claim unverified.

### no-freshness-contract-for-either-candidate
- **Severity:** P1
- **Where:** `interverse/intertrace/lib/trace-events.sh`, `lib/trace-contracts.sh`, `lib/trace-companion.sh`; brainstorm Track 1 Ground (step 2).
- **What:** All three tracer libs take a snapshot input (`changed_files` string, or for `_trace_companion_scan`, just the monorepo root with no file-list argument at all — meaning it re-derives edges from whatever's on disk *at call time*). Neither candidate (a) (agent invokes the shared entry script itself, presumably at its own dispatch time) nor (b) (orchestrator pre-runs and injects) specifies *when* relative to the diff-under-review the scan executes, or what happens if the working tree changes between capture and the agent's actual read of the diff. For (a), the risk is the agent re-running against a tree that moved since flux-drive computed the diff snapshot it's reviewing. For (b), the risk (already named in the architect agent's own P1 calibration) is evidence captured once at triage start going stale by the time fd-integration is actually dispatched several agents later.
- **Evidence:** `trace-companion.sh` lines 1-4 show `_trace_companion_scan "/path/to/monorepo"` — a single root-path argument, no file list, no commit SHA, no timestamp. It scans live disk state on every call, with no versioning concept. Nothing in the brainstorm's Ground step or Open Questions proposes binding scan output to a specific commit/diff identity.
- **Suggestion:** Whichever shape is chosen, define a freshness contract explicitly: either (a) tracers are always invoked against a pinned commit SHA (requiring the libs to accept a ref, not just scan working-tree state), or (b) injected evidence carries a capture-timestamp/SHA that fd-integration checks against the diff it's actually reviewing and treats staleness as a "declared, not verified" confidence downgrade rather than silently trusting old output.

### fourth-shape-cache-with-explicit-staleness-flag-missing
- **Severity:** P2
- **Where:** `interverse/intersense/README.md` lines 9, 31-36; `AGENTS.md` lines 111-120; brainstorm Task Context alternative-space list.
- **What:** The task explicitly asks to surface shapes not yet considered (evidence as a service, hook-time capture, event-driven, MCP tool surface). There's a fifth, already-implemented-in-this-repo shape none of those five categories quite covers: **detect-once-cache-with-explicit-staleness-check**. `intersense`'s `detect-domains.py` scans a project once, caches the result at `.claude/intersense.yaml`, and exposes `--check-stale` as a first-class, callable operation rather than leaving staleness implicit. This is meaningfully different from "hook-time capture" (no capture-on-write-event coupling) and from "evidence as a service" (no persistent server) — it's a cheap file-cache pattern with a staleness *query*, sitting closer to candidate (a) than (b) but solving the freshness problem the other candidates leave open.
- **Evidence:** `README.md`: "Output is cached at `.claude/intersense.yaml`... so downstream plugins... can inject domain-specific review criteria without re-scanning every time." `AGENTS.md:114`: `python3 scripts/detect-domains.py /path/to/project --check-stale`. `content-hash.py` (AGENTS.md:61) exists specifically to detect when cached results are stale relative to source changes.
- **Suggestion:** Name this as a sixth candidate — "cached-with-staleness-check" — and score it: tracer output written to a per-repo cache file keyed by commit SHA or content hash, with a cheap staleness check fd-integration runs before trusting cached evidence (falling back to live invocation if stale). It reuses an in-repo pattern instead of inventing a new one, and it directly answers the freshness gap flagged above without requiring engine changes to flux-drive.

### pilot-first-cost-not-quantified-for-candidate-b
- **Severity:** P2
- **Where:** brainstorm "Why This Approach" (pilot-first/migrate-under paragraph); Open Questions / "Tracer invocation path."
- **What:** The brainstorm's own leading-candidate framing ("agent-invoked, revisit if a second evidence-based agent appears") implicitly treats (b) as more expensive because it "touches the engine," but no line item ties this to a concrete cost (e.g., "adds N lines to launch.md Step 2.0.4," "requires a new typed-evidence field in the Composer plan schema"). Without that, the pilot-first sequencing argument for choosing (a) is asserted rather than demonstrated — it reads as a heuristic ("less code touched = safer pilot") rather than a scored comparison against the stated sequencing decision.
- **Evidence:** Key Decision 4 locks "pilot-first, migrate-under... accepted cost for evidence velocity" but the cost being accepted for candidate (a) vs. avoided by not picking (b) is never itemized against real launch.md line counts or Composer schema changes.
- **Suggestion:** Add one sentence quantifying the (b) cost against `launch.md` Step 2.0.4 concretely (e.g., "(b) would require compose_dispatch's plan schema to carry an `evidence` field per agent, plus a new Step 2.0.4a to invoke tracers before agent dispatch — roughly N lines, versus (a)'s zero engine lines") so the pilot-first choice is falsifiable, not just directionally plausible.

## Verdict
The brainstorm's two-candidate framing undersells real, already-built alternatives in this repo (the Composer pre-computation path, and intersense's cache-with-staleness pattern) and never establishes a freshness contract for tracer evidence under either candidate — both are P1-grade gaps that should be closed before locking "agent-invoked, revisit later" as the working recommendation. The deeper structural risk is that fd-integration's dispatch identity (third-party plugin agent, not Project or interflux-Plugin) is itself unresolved, which sits upstream of and could invalidate cost comparisons between the evidence-acquisition shapes.

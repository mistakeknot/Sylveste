## Findings

### intertrace-is-confirmed-nested-standalone-repo
- **Severity:** P0
- **Where:** `interverse/intertrace/.git` (own repo root); brainstorm Track 1 stage 3 ("Must work from nested standalone git repos (intertrace itself is one)"), Open Question 4.
- **What:** Directly verified: running `git rev-parse --show-toplevel` from inside `interverse/intertrace` returns `/Users/sma/projects/Sylveste/interverse/intertrace` — its own root — not `/Users/sma/projects/Sylveste`. This is not a hypothetical edge case the brainstorm should worry about someday; it's the actual, present-tense topology of the exact repo the brainstorm names as the must-work case. Any discovery mechanism built on "walk up until you hit a `.git` boundary" (the most naive reading of "upward directory walk," one of the three Open Question 4 candidates) terminates at `interverse/intertrace/.git` and never reaches `docs/companion-graph.json` or `docs/contract-ownership.md` at the Sylveste root. Per this agent's own Severity Calibration, the dangerous failure mode isn't a crash — it's silent, confident degradation: the agent falls back to code-inference for a repo that structurally IS part of the federation, with no signal distinguishing that from a repo that's legitimately standalone.
- **Evidence:** `git -C interverse/intertrace rev-parse --show-toplevel` → `/Users/sma/projects/Sylveste/interverse/intertrace`. `git -C /Users/sma/projects/Sylveste rev-parse --show-toplevel` → `/Users/sma/projects/Sylveste` (not itself a git repo at the top — this workspace root isn't even under version control at this path per the environment's `Is directory a git repo: No`, though the Sylveste subtree at `/Users/sma/projects/Sylveste` is). Either way, a `.git`-boundary walk from intertrace stops well short of the hub docs.
- **Suggestion:** Reject `.git`-boundary walk as the sole mechanism (or at minimum, don't let it silently win as the "obvious" interpretation of "upward directory walk"). If upward walk is kept, it must walk past `.git` boundaries and instead look for a federation marker (e.g. `docs/companion-graph.json` existing at each candidate ancestor) — which folds Open Question 4's "upward walk" and "marker file" options into one mechanism rather than three independent candidates to choose between.

### intersense-precedent-is-cache-classification-not-directory-walk
- **Severity:** P1
- **Where:** `interverse/intersense/README.md` lines 3-9, 31-36, 73; `AGENTS.md` lines 44-46, 60-61, 111-120; brainstorm Open Question 4 ("upward walk to find the Sylveste root? Marker file? Reuse intersense-style detection?").
- **What:** Grounded inspection shows intersense does **domain classification** (is this project a web-api, cli-tool, game-simulation, etc., via signal matching on manifests/directories/dependencies), with results cached at `.claude/intersense.yaml` in the *target* project and a `--check-stale` flag for cache invalidation. There is no directory-walk-to-find-a-shared-root logic anywhere in the repo (`grep` for walk/detect-root/marker patterns across `.sh`/`.md` files returns only an unrelated match in a domain-signal config). Grouping "reuse intersense-style detection" alongside "upward directory walk" and "marker file" in Open Question 4 implies it's a third flavor of the same root-finding problem; it's actually solving a completely different problem (what kind of project is this) with a completely different mechanism (local cache + staleness check, not path traversal). Citing it as a federation-discovery precedent without noting this mismatch risks someone implementing "intersense-style" and discovering it doesn't address root discovery at all.
- **Evidence:** `README.md`: "Domain detection for Claude Code plugins... cached at `.claude/intersense.yaml`... interflux's `detect-domains.py` is a thin stub that delegates here via `os.execv`." No upward-walk or hub-root-resolution code exists in `scripts/detect-domains.py`'s stated purpose or the `AGENTS.md` design description.
- **Suggestion:** Drop "intersense-style detection" as a candidate for the root-*discovery* mechanism specifically, but keep its actual pattern — local per-project cache + explicit `--check-stale` — as a candidate for how federation-resolution *results* get cached once discovery succeeds (this doubles as an answer to the freshness problem the evidence-substrate lens raises separately). That reframes Open Question 4 as two questions instead of a false three-way choice: (1) how do we find the hub root — walk-past-`.git` or marker file; (2) how do we cache/invalidate that result once found — intersense's pattern is the good precedent here.

### monorepo-root-already-an-undeclared-variable-today
- **Severity:** P1
- **Where:** `interverse/intertrace/skills/intertrace/SKILL.md` lines 53-69 (`$MONOREPO_ROOT` used in three tracer invocations); brainstorm Track 1 Generalize framing ("No more silent 404 of the agent's 'First Step (MANDATORY)'").
- **What:** The existing `/intertrace` skill already passes `$MONOREPO_ROOT` into all three tracer scans (`_trace_events_scan "$MONOREPO_ROOT" ...`, `_trace_contracts_scan "$MONOREPO_ROOT" ...`, `_trace_companion_scan "$MONOREPO_ROOT"`), but nowhere in the SKILL.md's Step 1-2 is `MONOREPO_ROOT` assigned a value — no `git rev-parse`, no upward walk, no prompt-the-user fallback shown. This means the *current* system already has an undeclared-variable failure mode: if `/intertrace` is invoked from a shell where `MONOREPO_ROOT` isn't already exported by some out-of-band convention, the tracer calls either fail loudly (unbound variable, if `set -u`) or silently resolve to an empty string, which every one of the three lib functions would then treat as a bad root path. This is a live instance of the exact "silent 404" problem the brainstorm's generalize stage aims to fix for fd-integration's hub-doc reads — but it's already present in the *sibling* tracer-invocation codepath the brainstorm plans to fuse with (Track 1 stage 2 fusion goal), and the generalize stage doesn't mention auditing or fixing it.
- **Evidence:** `SKILL.md` lines 53-69 use `$MONOREPO_ROOT` three times with no assignment visible anywhere earlier in the file (checked lines 1-72, the full Step 1-3 span).
- **Suggestion:** Before or during the generalize stage's federation-discovery work, resolve `MONOREPO_ROOT`'s current assignment mechanism in `/intertrace` (it may be implicit/undocumented, or genuinely unset and silently broken) and make the same resolved-root logic the single source both `/intertrace` and fd-integration's hub-doc lookup use — this is a natural intersection with Open Question 6 (single tracer codepath) and shouldn't be solved twice.

### zero-of-sixty-two-not-sixty-one
- **Severity:** P2
- **Where:** brainstorm "Why This Approach" ("currently the *only* copies; 0/61 plugin repos have their own"); grounding at `find interverse -maxdepth 1 -type d | wc -l` → 63 (62 excluding the `interverse` dir itself).
- **What:** The repo count under `interverse/` is now 62, not 61 — a small drift since the brainstorm's stated research date, consistent with normal repo growth, not a contradiction of the underlying claim (still confirmed: zero of them have their own `companion-graph.json` or `contract-ownership.md`). This is flagged as a P2 hygiene note, not a substantive design flaw: the "0/N" framing is being used as a static fact in a document that will likely be read again after more repos are added, and the number will keep drifting.
- **Evidence:** `find interverse -maxdepth 1 -type d | wc -l` → 63 (includes `interverse/` itself, so 62 plugin dirs). `find interverse -maxdepth 2 -iname "companion-graph.json" -o -iname "contract-ownership.md"` → no results, confirming 0/62.
- **Suggestion:** If this document or its successor plan gets cited again, restate as "0/N plugin repos (N≈60, re-verify at implementation time)" rather than a pinned "0/61," so the claim doesn't read as stale when the repo count has moved by the time someone acts on it.

## Verdict
The P0 finding is grounded, not speculative: intertrace's own git boundary is a real, present obstacle to any naive upward-walk discovery mechanism, and it's the exact repo the brainstorm names as the must-work case — this should block locking in "upward directory walk" without an explicit `.git`-boundary-crossing design. The intersense-precedent mismatch (P1) means Open Question 4 is currently framed as three interchangeable options when it's actually two different problems (root-finding vs. result-caching) wearing one open question's clothes.

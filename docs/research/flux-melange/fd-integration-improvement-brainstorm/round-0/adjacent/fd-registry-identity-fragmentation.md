## Findings

### trust-feedback-schema-has-no-migration-path-named
- **Severity:** P0
- **Where:** `interverse/intertrust/hooks/lib-trust.sh` lines 45-59 (`CREATE TABLE trust_feedback ... agent TEXT NOT NULL`); brainstorm Open Question 5 ("do intertrust/interspect migrate to registry identity, or keep joining on name strings?") and Key Decision 4 (pilot-first/migrate-under).
- **What:** The actual schema confirms the brainstorm's fragmentation claim exactly: `agent` is a plain `TEXT` column with a composite index `idx_trust_agent_project` — there is no foreign key, no UUID, nothing that could be atomically repointed if a registry introduces a new canonical key. If fd-integration accumulates trust rows during the pilot phase under the string `"fd-integration"`, and the registry later assigns it a different canonical identity (a UUID, a namespaced key like `intertrace:fd-integration`, or anything other than the bare string), every existing row in `trust_feedback` becomes an orphan unless a migration explicitly rewrites the `agent` column — and Open Question 5 explicitly leaves open whether intertrust migrates at all. If it doesn't migrate, the registry is decorative from intertrust's perspective: trust scoring keeps joining on the old bare string forever, and a rename anywhere upstream silently desyncs it, which is precisely the P0 scenario named in this agent's own Severity Calibration ("a future rename or registry-key change... silently desyncs trust scores").
- **Evidence:** `lib-trust.sh:46-58` — `CREATE TABLE IF NOT EXISTS trust_feedback (... agent TEXT NOT NULL ...) CREATE INDEX ... ON trust_feedback(agent, project)`. `os/Clavain/cmd/clavain-cli/testdata/routing-overrides.json` confirms the same pattern independently: `{"agent": "fd-game-design", "action": "exclude", ...}` — interspect's override format is also a bare string key with zero indirection.
- **Suggestion:** The registry's definition of done (not just "interflux consumes it as sole roster source," per the brainstorm's stated success criteria) must include either (a) a migration script that rewrites `trust_feedback.agent` and `routing-overrides.json[].agent` to the new canonical key with row counts verified before/after, or (b) an explicit decision that the registry's canonical key IS the existing bare name string (i.e., no re-keying happens, ever) — in which case say so as a design decision, not leave it as an open question, because it changes what "the registry" actually accomplishes.

### fifth-identity-surface-not-counted
- **Severity:** P1
- **Where:** brainstorm "Why This Approach" ("fragmentation across five files/four owners... interflux `agent-roster.md`, `.index.yaml`, `agent-roles.yaml`; intertrust's SQLite trust table; interspect's `routing-overrides.json`"); grounding at `interverse/intertrace/.claude-plugin/plugin.json` and `interverse/interflux/skills/flux-engine/references/agent-roster.md` lines 9-13.
- **What:** The fragmentation count misses at least one more identity surface: **the owning plugin's own manifest**. `intertrace/.claude-plugin/plugin.json` declares `"agents": ["./agents/review/fd-integration.md"]` — this is itself an identity assertion ("fd-integration exists, and intertrace is its source of truth for what it is") that's independent of all five files counted. It's not one of the four owners named (interflux/intertrust/interspect + implicitly Clavain), and it doesn't join on any of their keys at all — it's the plugin manifest that should arguably be upstream of everything else, since it's the only place the agent's actual system-prompt content lives. Separately, `agent-roster.md`'s dispatch taxonomy (Project vs. interflux-Plugin, no "other plugin" category — see companion evidence-substrate finding) is itself a sixth fragmentation point: even after the registry exists, *how a plugin-owned agent gets invoked* is still undecided, which is an identity-adjacent question the registry track doesn't claim to own but that blocks the registry from being useful for fd-integration specifically.
- **Evidence:** `intertrace/.claude-plugin/plugin.json`: `"agents": ["./agents/review/fd-integration.md"]`. `agent-roster.md` lines 9-13: only "Project Agents (.claude/agents/fd-*.md)" and "Plugin Agents (interflux)" sections exist; no category matches an agent that's both plugin-owned and non-interflux.
- **Suggestion:** Recount the fragmentation surface to include the owning-plugin manifest as a sixth source of identity truth, and note explicitly whether the registry is meant to subsume plugin-manifest agent declarations (i.e., does registering with the new registry replace or duplicate the `plugin.json` `"agents"` array?) — if it duplicates, that's a seventh place identity can drift, not a consolidation.

### pilot-evidence-carry-forward-unspecified
- **Severity:** P1
- **Where:** brainstorm Key Decision 4 (pilot-first, migrate-under) and Success Criteria ("trust rows accumulating with ≥60% accept after ~20 findings"); grounding at `agent-roles.yaml:49` and `hooks/lib-trust.sh:46-58`.
- **What:** The success criterion explicitly wants ≥20 trust-feedback rows accumulated **before** the registry migration happens (pilot-first is designed to "start the evidence clock immediately"). Those rows will exist keyed on whatever string `agent-roles.yaml:49`'s hand entry uses (`fd-integration`) joined against `project` in `trust_feedback`. The brainstorm frames "fd-integration migrates... to become the registry's first external registration" as a clean handoff, but doesn't specify: does the registry's registration process for fd-integration re-use the exact string `"fd-integration"` as its canonical key (making the migration a no-op for intertrust), or does it mint something else (making the accumulated 20 rows need explicit re-attribution)? This is the same P1 scenario already named in this agent's own Severity Calibration, and grounding it against the real schema (single `TEXT` column, indexed but not keyed) shows the re-attribution, if needed, is a straightforward `UPDATE trust_feedback SET agent = ? WHERE agent = ?` — cheap to do, but only if someone decides to do it. Nothing in the plan commits to running it.
- **Evidence:** `agent-roles.yaml:49` — `- fd-integration  # intertrace: cross-module integration review`. This exact string is what any pilot-phase dispatch would log against in `trust_feedback.agent` and any `routing-overrides.json` entry.
- **Suggestion:** State explicitly in the migrate-under step: "registry key for fd-integration = `fd-integration` (unchanged)" if that's the intent, or add a one-line migration (`UPDATE trust_feedback SET agent = '<new-key>' WHERE agent = 'fd-integration'`) to the registry's rollout checklist if a new key format is planned. Either resolves the ambiguity cheaply; leaving it open risks the pilot's accumulated evidence starting over at zero exactly when it's supposed to prove the registry's migration path works.

### registry-boundary-question-doesnt-reduce-join-count
- **Severity:** P2
- **Where:** brainstorm Open Question 1 ("identity + eligibility only, or also absorb lifecycle tiers... and model routing (`agent-roles.yaml`)?"); grounding at `agent-roles.yaml` (confirmed to exist and hold both roster-adjacent entries like line 49 and model-tier groupings like lines 46-51, 153-158).
- **What:** `agent-roles.yaml` isn't just a model-routing file — grounding shows it's organized by dispatch role (`reviewer:`, `editor:`) with agents grouped under each, meaning it's doing partial roster/eligibility work today, not purely model assignment. If the registry ships identity+eligibility only (the narrow boundary), interflux's triage still reads `agent-roles.yaml` for both role membership AND model tier — meaning the registry doesn't remove `agent-roles.yaml` from the join path at all, it adds a fourth file alongside it. The "single source of truth" framing in the Why-This-Approach section isn't yet checked against this: a narrow-boundary registry could leave the total file-join-count for a dispatch decision unchanged or even increased (registry + agent-roles.yaml + whatever handles lifecycle tier, versus today's roster + agent-roles.yaml).
- **Evidence:** `agent-roles.yaml` lines 46-51 group `fd-integration` under a `reviewer:` role alongside `fd-quality`, `fd-safety` — this is eligibility/role information, not just a model string, contradicting a clean "registry = eligibility, agent-roles.yaml = model routing only" split.
- **Suggestion:** Resolve Open Question 1 with an explicit before/after file-count accounting (as this agent's Success Criteria calls for) — list exactly which files a dispatch decision reads today, and which it would read post-registry under each boundary option, so "single source of truth" is a checkable claim rather than a slogan.

## Verdict
The schema-level grounding confirms the brainstorm's fragmentation diagnosis is accurate but incomplete — `trust_feedback.agent` and `routing-overrides.json`'s bare-string keys make Open Question 5 a genuine P0 landmine, not a deferrable detail, because leaving it open means the registry ships without ever becoming the join key for two of the four named consumers. The registry's own success criteria (≥20 trust rows accumulated pre-migration) creates a concrete migration obligation the brainstorm doesn't yet acknowledge as such.

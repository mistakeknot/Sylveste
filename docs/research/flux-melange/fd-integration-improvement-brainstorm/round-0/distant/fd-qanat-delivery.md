## Findings

### contention-unmodeled-for-second-consumer
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` §Open Questions ("Tracer invocation path: agent sources the bash libs directly... vs. flux-drive pre-runs tracers... Leading candidate: agent-invoked, revisit if a second evidence-based agent appears").
- **What:** The brainstorm's own leading candidate is explicitly conditioned on "revisit if a second evidence-based agent appears" — but a second consumer is not hypothetical, it's already named as coming: interflux runs up to 12 review agents plus cognitive agents per `agent-roster.md`, and the brainstorm's Track 2 registry work is explicitly designed to onboard "future evidence-based agents" (Track 1 step 2's framing: "Eliminate the current split where the `/intertrace` skill and the agent do overlapping checks via disconnected codepaths" implies more than one consumer of the same tracer output already exists today — the skill and the agent). Under agent-invoked (candidate a), each of N agents in a triage batch that touches cross-module code re-sources `trace-events.sh`/`trace-contracts.sh`/`trace-companion.sh` and re-runs `_trace_companion_scan` against the same unchanged `docs/companion-graph.json` (102 lines) independently — every plot digging its own well into the same aquifer. The brainstorm scores candidate (a) as the leading choice without modeling this cost, then defers the re-evaluation trigger to a future event that has, by its own description, effectively already happened (skill + agent both need this evidence today).
- **Evidence:** `interverse/intertrace/skills/intertrace/SKILL.md:42-70` shows the skill's own Step 2 sources and runs all three tracers fresh, per invocation — this is the exact re-dig pattern that would replicate per-agent under candidate (a) if/when a second fd-* evidence-based agent is added, with no caching or shared run layer named anywhere in the brainstorm.
- **Suggestion:** Model the concrete cost of N agents in one triage batch each re-running `_trace_companion_scan` against the same diff before calling candidate (a) the leading choice — a shared per-review-run cache (even a simple temp-file memo keyed on diff hash) may cost less than the "revisit later" deferral implies, and the trigger condition is arguably already met.

### hook-time-and-event-driven-shapes-never-drawn
- **Severity:** P1
- **Where:** North-star prompt ("Surface genuinely different shapes (e.g. evidence as a service, hook-time capture, event-driven tracing, MCP tool surface)") vs. `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` §Open Questions "Tracer invocation path," which scores only two shapes (agent-invoked, orchestrator-pre-run).
- **What:** Hook-time capture would draw evidence upstream of review time — at commit or event time — releasing water earlier in the channel than either named candidate. This is architecturally *available* today: `interverse/intertrace/hooks/hooks.json` exists as a registered hook surface but is currently empty (`{"hooks": {}}`), meaning intertrace already has the plumbing stub for this shape and the brainstorm doesn't evaluate it. Event-driven tracing likewise goes undrawn despite `fd-integration.md` itself being about event producer/consumer completness (`Watch for the silent-pipeline pattern: _interspect_insert_evidence calls with unregistered hook_ids silently fail`) — the domain the agent reviews is literally event-bus wiring, yet the brainstorm never asks whether tracer evidence itself should be captured via that same event-bus mechanism rather than pulled synchronously at review time.
- **Evidence:** `interverse/intertrace/hooks/hooks.json:1-3` confirmed empty — no existing hook wiring to build on, but the file exists as a stub, meaning "hook-time capture" is a lower-lift shape than the brainstorm's framing suggests (infrastructure slot already present, just unpopulated). `fd-integration.md:22-27` shows the agent's own domain is event producer/consumer completeness, i.e. the reviewer already reasons about upstream event capture as its subject matter.
- **Suggestion:** Score hook-time capture explicitly: would populating `hooks/hooks.json` to snapshot tracer state at commit-time (post-ship, matching /intertrace's existing bead-scoped cadence) deliver fresher-at-lower-cost evidence than review-time pull, and does staleness between commit-time capture and review-time diff matter enough to reject it? Currently this shape is invisible in the document despite being named as in-scope by the review goal and despite a stub hook surface already existing to receive it.

### stage-2-shippability-of-ground-untested-against-tap-vs-release
- **Severity:** P2
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` Track 1 step 2 ("Ground") vs. step 3 ("Generalize... federation path-discovery so any Sylveste-family repo resolves the hub docs") and §Why This Approach ("keeps every stage independently shippable").
- **What:** Stage 2 ("Ground") claims fd-integration will be "fused with intertrace's three tracer libs" and its findings will be "grep-verified, evidence-typed... not LLM impressions" — independently of stage 3's federation path-discovery. But the tracer libs themselves need a resolved root to scan: `_trace_companion_scan` takes `$MONOREPO_ROOT` as an argument (per SKILL.md Step 2c), and today that root is only resolvable inside the monorepo itself (companion-graph.json exists only at `docs/companion-graph.json` in this repo, confirmed 0/61 plugin repos have their own copy per the brainstorm's own text). If stage 2 ships before stage 3's federation discovery, does grounding "hold water alone" outside the monorepo, or does it silently degrade to a 404 exactly like the failure the brainstorm opens with ("No more silent 404 of the agent's First Step (MANDATORY)")? The brainstorm asserts independent shippability as a design property but doesn't test stage 2 against the case where the reviewer runs in a standalone plugin repo (e.g., intertrace itself, explicitly named in §Open Questions as a nested standalone git repo) before stage 3 lands.
- **Evidence:** Brainstorm text: "hub docs... currently the *only* copies; 0/61 plugin repos have their own" — meaning grounding (stage 2) run outside the monorepo, before stage 3's discovery mechanics exist, has nothing to resolve against and would reproduce the exact silent-404 failure mode the brainstorm names as the reason to fix this in the first place.
- **Suggestion:** State explicitly whether stage 2's "grep-verified, evidence-typed" claim holds only inside the monorepo until stage 3 ships, and if so, note that stage 2 alone waters only the monorepo's own field, not the 61 plugin repos — which is fine as a staging choice, but should be named rather than implied by the "independently shippable" claim.

### silting-risk-in-dual-codepath-explicitly-flagged-but-unresolved
- **Severity:** P2
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` §Open Questions ("Single tracer codepath: after fusion, do `/intertrace`... and the agent... share one library entry point to prevent re-drift?").
- **What:** The brainstorm correctly identifies the silting risk (two hands transcribing the same source drift slowly and invisibly) but leaves it as an open question rather than a decision, even though Track 1 step 2's stated goal is explicitly to "Eliminate the current split where the `/intertrace` skill and the agent do overlapping checks via disconnected codepaths." The goal and the mechanism to guarantee it don't yet match: without a shared entry point decided now, the two codepaths could each independently source `lib/trace-*.sh` with slightly different invocation parameters (SKILL.md passes `$MONOREPO_ROOT` and `$changed_files` computed from bead-derived commits; an agent invocation at review-time would need to compute an equivalent from the diff under review) and drift silently — no single review would catch this because each codepath looks locally correct.
- **Evidence:** `SKILL.md:18-41` (Step 1: Resolve Bead to Changed Files) computes `changed_files` from `git log --all --grep=<bead_id>` — a bead-scoped, post-hoc resolution. An agent operating at review time under candidate (a) would need a diff-scoped resolution instead (the diff under review, not a bead's historical commits). These are two different computations feeding the same tracer functions; nothing in the brainstorm specifies they'll be unified rather than merely calling the same `.sh` files with divergent argument-construction logic.
- **Suggestion:** Elevate "single tracer codepath" from an open question to a stage-2 acceptance criterion: define one shared function (e.g., `_trace_resolve_scope`) that both /intertrace and the agent call to go from their respective inputs (bead ID vs. diff) to the same `changed_files` format, so silting is structurally prevented rather than hoped against.

### roster-double-dig-during-migrate-under-window
- **Severity:** P3
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` §Key Decisions item 4 ("pilot-first, migrate-under... Roster path deliberately changes twice (hand entry now, registry swap later)").
- **What:** During the window between hand-entry and registry-swap, the hand-wired roster entries in `agent-roster.md`/`agent-roles.yaml` and the eventual registry both potentially exist as parallel channels feeding the same triage step. The brainstorm doesn't say whether the swap is an atomic cutover (hand entry deleted the moment registry entry lands) or a period of dual-source overlap where triage could theoretically read stale hand-wired state alongside registry state — a minor silting risk given the fd-integration incident already shown to occur from exactly this kind of dual-file drift (roster vs. routing.yaml mismatch, per §Why This Approach).
- **Evidence:** §Success Criteria states "interflux consumes registry as sole roster source (`agent-roster.md` deleted or generated)" — "deleted or generated" leaves the cutover mechanism ambiguous (hard delete vs. generated-and-kept-in-sync), which is exactly the two-hands-drift shape the diplomatics lens and this lens both flag independently.
- **Suggestion:** Pick one of "deleted" or "generated-from-registry-and-checked-in" explicitly in the plan stage; "generated" without a regeneration trigger is a silting risk in its own right.

## Verdict
The brainstorm scores its two named tracer-invocation candidates reasonably but never draws the hook-time or event-driven shapes the review goal explicitly asked for, despite intertrace already having a stub hook surface (`hooks/hooks.json`) ready to receive one — that is the most concrete gap. The agent-invoked leading candidate is chosen partly on a "revisit if a second consumer appears" clause that undersells contention risk, since a second consumer (the /intertrace skill itself, or the next fd-* evidence-based agent Track 2 is explicitly built to onboard) is already effectively present rather than hypothetical.

## Findings

### no-tier-in-findings-index-contract
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` Track 1 step 1 ("make its output comply with the Findings Index contract") and step 2 ("findings are grep-verified, evidence-typed... not LLM impressions"); grounded against `interverse/intertrace/skills/intertrace/SKILL.md` Step 3 which defines P1/P2/P3 as *evidence-strength* ranks (contract-declared-with-zero-evidence, partial, docs-only) — a severity axis, not a provenance axis — and against `interverse/interflux/skills/flux-engine/references/agent-roster.md`, which documents the Findings Index format only as agent selection/invocation metadata with no mention of a confidence-tier field.
- **What:** The brainstorm commits fd-integration to two things that collide: (1) comply with interflux's existing Findings Index contract (a P0-P3 *severity* line format), and (2) carry a verified/declared/missing *evidence-tier* through to synthesis. Intertrace's own P1/P2/P3 already means "evidence strength," not "severity" — the SKILL.md's own scheme conflates urgency and confidence in a single number. If fd-integration's findings are forced into the same single P0-P3 slot the other eleven interflux reviewers use, the tier collapses into severity and there is no field left in the Findings Index line to carry "this was grep-verified against trace-events.sh" vs. "this was the agent's read of companion-graph.json prose." A later reader of the synthesized report, or of a trust-table row keyed on this finding, cannot reconstruct which.
- **Evidence:** `interverse/intertrace/skills/intertrace/SKILL.md:74-87` defines P1="contract declares consumer + zero code evidence" (i.e., *finding confidence*, expressed by grep results) — the exact same three-letter label space the brainstorm elsewhere treats as ship-blocking severity (Track 1 step 1). `agent-roster.md:1-40` documents no per-finding tier field in the Findings Index format it references.
- **Suggestion:** Before Track 1 step 1 ships, force every candidate architecture to name the exact line-item field that carries confidence tier through to the stored finding, independent of the P0-P3 severity slot. If none can name one, that is itself the P1.

### mcp-tool-surface-has-no-custody-answer
- **Severity:** P1
- **Where:** North-star prompt ("Surface genuinely different shapes (e.g. evidence as a service, hook-time capture, event-driven tracing, MCP tool surface)") vs. `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` §Open Questions "Tracer invocation path," which only frames two candidates: agent-sources-bash-libs-directly vs. flux-drive-pre-runs-and-injects.
- **What:** The review goal explicitly asks for genuinely different shapes including an MCP tool surface, but the brainstorm document itself never names or scores that shape — it only scores (a) agent-invoked script and (b) orchestrator pre-run. An MCP tool surface is a *third* custody topology with its own chancery problem: a tool call crossing a process/protocol boundary (client → MCP server → tracer lib → JSON-RPC response → agent) has more hops than either named candidate, and JSON-RPC tool results have no standard field for "this value was grep-verified vs. summarized by the server." If this shape is evaluated later without the custody question being asked explicitly, it is exactly the failure mode this lens exists to catch — a new hop invented after the brainstorm was written, unaudited.
- **Evidence:** Brainstorm §Open Questions lists only two tracer-invocation candidates; the intertrace plugin `CLAUDE.md` states "Thin plugin over intermap — no MCP server (stateless analyzer)" as an existing design decision, meaning an MCP surface would be new infrastructure the brainstorm doesn't discuss standing up.
- **Suggestion:** Add the MCP tool surface as a scored candidate with an explicit custody-chain trace (tracer lib → MCP server → JSON-RPC payload → agent), or explicitly rule it out in the brainstorm with the reason (e.g., "rejected: adds a protocol hop with no standard confidence-tier field and intertrace already declared itself server-less").

### hand-entry-to-registry-swap-breaks-attribution
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` §Key Decisions item 4 ("Sequencing: pilot-first, migrate-under... Roster path deliberately changes twice") and §Track 2 ("fd-integration migrates from its hand entry to become the registry's first external registration").
- **What:** fd-integration's identity — how it's keyed for trust-table rows, roster entries, and routing — changes representation twice: (1) hand-entered into `agent-roster.md` / `agent-roles.yaml` now, (2) swapped to registry identity later. The brainstorm names the roster-path change explicitly but never states whether the trust-table rows and stored findings accumulated under regime 1 (joined on the bare string `fd-integration` per `intertrust`'s SQLite table, confirmed in brainstorm's own Why-This-Approach paragraph) remain attributable to the same agent after regime 2, or whether the registry swap silently starts a new, disconnected identity thread. §Open Questions "Identity keys" asks whether intertrust/interspect migrate to registry identity — but doesn't ask what happens to *history* produced before the migration.
- **Evidence:** Brainstorm text: "replacing the fragmentation across five files/four owners (interflux `agent-roster.md`, `.index.yaml`, `agent-roles.yaml`; intertrust's SQLite trust table; interspect's `routing-overrides.json`, all joining on bare name strings)" — confirms the current join key is a bare string, which is exactly the kind of key that silently continues to "work" across a registry swap while actually pointing at two different identity records with no explicit link.
- **Suggestion:** Name the exact field (bare string continuity, explicit alias table, or migration-time backfill) that lets a reader of a trust-table row from week 1 confirm it's the same agent as a registry-sourced row from week 6. If the answer is "bare string, unchanged" say so explicitly and treat that as the corroborating link — currently it's implicit.

### inference-fallback-has-no-declared-marker
- **Severity:** P2
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` §Key Decisions item 2 ("hub path-discovery for federation repos + code-inference fallback elsewhere") and Track 1 step 3 ("code-inferred edges in non-federation repos as fallback").
- **What:** The brainstorm names the substrate split (hub-declared vs. code-inferred) as a considered tradeoff but doesn't specify whether a finding produced via the inference codepath carries a marker distinguishing it from one produced via the hub-declared codepath once it reaches the Findings Index. Inference-derived edges are, by the brainstorm's own admission in §Open Questions ("Inference-fallback noise control: undeclared edges were invisible by design; inference makes them visible-and-noisy"), lower-confidence than hub-declared ones — but nothing downstream (trust calibration, severity assignment) is described as tier-aware of *which* substrate path produced the evidence.
- **Evidence:** `docs/companion-graph.json` (102 lines) is confirmed as the sole existing hub-declared source (brainstorm: "currently the *only* copies; 0/61 plugin repos have their own"). Grounding against `fd-integration.md:13-16` ("First Step (MANDATORY)... `docs/companion-graph.json` for declared module relationships") shows the current agent reads the hub file directly with no inference codepath at all — so the inference-fallback tier distinction the brainstorm proposes doesn't exist yet anywhere to model against.
- **Suggestion:** When the plan stage designs the substrate, require inference-sourced findings to carry an explicit tag (e.g., `source: inferred` vs `source: declared`) that survives into the stored finding, not just into agent reasoning.

### single-authority-registry-names-no-corroborating-witness
- **Severity:** P2
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` §Track 2 ("A thin new interverse plugin owning reviewer-agent identity and dispatch eligibility as one source of truth") and §Success Criteria ("interflux consumes registry as sole roster source (`agent-roster.md` deleted or generated)").
- **What:** The registry is explicitly designed as the sole source of truth, replacing five files across four owners. Diplomatically, a sole uncorroborated authority is a single point of forgery/drift risk: nothing in the brainstorm names a check that would catch the registry itself silently diverging from ground truth (e.g., a plugin disabled but not deregistered, per §Open Questions "Registration mechanism... staleness handling when a plugin is disabled/updated" — which is flagged as an open question, not a decided corroboration mechanism).
- **Evidence:** Confirmed against actual repo state: `agent-roles.yaml:49` has the `fd-integration` model-routing line, but `agent-roster.md` (96 lines, grepped) has **zero** mention of fd-integration — this is precisely the "got a model-routing line but no roster entry, and nothing could notice the inconsistency" failure the brainstorm cites as the motivating incident (§Why This Approach). That incident is proof the *current* multi-file fragmentation has no corroborating check; the brainstorm's fix (single registry) removes the fragmentation but doesn't add a corroborating witness for the registry's own accuracy — it just moves the single-point-of-failure rather than eliminating it.
- **Suggestion:** Name a lightweight corroboration signal for the registry (e.g., a periodic diff against actual `plugin.json`/`.claude/agents/*.md` files on disk, similar to the tracer pattern intertrace already uses for companion-graph vs. code) so a second registry-drift incident is self-detecting rather than silently repeating the fd-integration failure mode.

## Verdict
The brainstorm is well-grounded on wiring and sequencing but treats "evidence-typed" as a property of the tracer output alone, without ever naming the field that carries confidence tier through the Findings Index contract, an MCP tool-surface hop (explicitly requested in the review goal but never scored), or the hand-entry→registry identity swap. The most load-bearing gap is P1 no-tier-in-findings-index-contract: intertrace's own P1-P3 scheme already means evidence-strength, and interflux's Findings Index P0-P3 slot means severity — colliding the two into one line silently launders "grep-verified" and "LLM-asserted" into indistinguishable output unless a plan-stage decision names a separate field.

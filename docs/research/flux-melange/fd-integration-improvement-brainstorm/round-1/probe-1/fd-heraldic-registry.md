# fd-heraldic-registry — round 1

## Findings Index
- [P1] trust-table-second-namespace-collision — intertrust's `trust_feedback` table keys identity on an UNDIFFERENCED (agent, project) pair where `project` is a bare `basename(git-toplevel)` string, a second roll of arms the registry track never inventories or migrates (§Key Decisions item 3; §Open Questions "Identity keys")
- [P1] flux-agent-py-is-an-unacknowledged-fourth-roll — `interflux/scripts/flux-agent.py` is a live grant/promote/record registrar over `.claude/agents/fd-*.md` with its own bare-filename key and its own generated `.index.yaml`, but Track 2 names only "five files/four owners" and never counts this office of arms or reconciles it with the new one (§Track 2 opening paragraph; §Open Questions "Registration mechanism")
- [P2] project-name-collision-is-the-same-defect-twice — the `basename(git-toplevel)` project key in intertrust/interspect is mechanistically identical to the `$MONOREPO_ROOT` silent-404 defect already flagged for path discovery, but here it collides trust *history* across differently-located same-named repos rather than failing to find one (§Open Questions "Federation path discovery mechanics")
- [P3] flux-agent-scope-excludes-plugin-agents-by-construction — `_scan_agents` globs only `.claude/agents/fd-*.md` (Project Agents), so fd-integration as a Plugin Agent is structurally invisible to the one registrar that already has grant/promote/attainder-shaped verbs, meaning the new Track 2 registry cannot simply extend flux-agent.py without first widening its scan scope (§Track 2, "new thin interverse plugin")

## Findings

### trust-table-second-namespace-collision
- **Severity:** P1
- **Where:** `interverse/intertrust/hooks/lib-trust.sh` lines 34-36 (`_trust_project_name`), lines 46-60 (`CREATE TABLE trust_feedback`, `agent TEXT NOT NULL, project TEXT NOT NULL`), lines 290-306 (`_trust_scores_batch`, keys SELECT DISTINCT on bare `agent`)
- **What:** Trust is not a single-axis roll keyed on agent identity alone — it is a two-axis roll of `(agent, project)`, and `project` is derived the same way the settled-fact boundary bug derives `$MONOREPO_ROOT`: `basename("$(git rev-parse --show-toplevel)")`. Two distinct repositories that happen to share a basename (a forked/renamed clone, a nested worktree, a nested standalone repo like intertrace under Sylveste vs. a hypothetical standalone `intertrace` elsewhere) silently pool their trust history under one project string. The brainstorm's registry track (Key Decision 3, Open Question "Identity keys") asks only whether intertrust/interspect *migrate to registry identity* for the **agent** axis — it never notices the **project** axis is its own unregistered roll with the exact same collision shape.
- **Evidence:** Confirmed live: `basename(git rev-parse --show-toplevel)` for `interverse/intertrace` (its own repo root, per the settled fact) returns `intertrace`; for Sylveste it returns `Sylveste`. Any second checkout, fork, or differently-nested repo sharing either basename joins trust rows silently — `_trust_scores_batch` and `_trust_report` (lines 292-306, 311-337) do `SELECT DISTINCT agent FROM trust_feedback` / `GROUP BY agent, project` with no canonicalization, no repo-identity check (e.g. remote URL, root SHA), just string equality.
- **Suggestion:** When the registry defines its canonical identifier for the agent axis, extend the same canonicalization decision to the project axis before Track 2 ships — at minimum, name in Open Questions whether `project` in `trust_feedback` migrates to a canonical repo identity or stays a bare basename join. This is the smallest viable addition: one line in "Identity keys" naming the second axis, not a schema rewrite.

### flux-agent-py-is-an-unacknowledged-fourth-roll
- **Severity:** P1
- **Where:** `interverse/interflux/scripts/flux-agent.py` lines 1-19 (module docstring: "Manages the quality-tiered agent registry... builds a cached index (.index.yaml)"), lines 268-321 (`_scan_agents`, keys on `name = f.stem`), lines 593-669 (`cmd_promote`, `cmd_record` — grant/attainder-shaped verbs already exist)
- **What:** The brainstorm's Track 2 opening line claims fragmentation is "across five files/four owners (interflux agent-roster.md, .index.yaml, agent-roles.yaml; intertrust's SQLite trust table; interspect's routing-overrides.json)" and treats `.index.yaml` as an inert artifact to be superseded. But `.index.yaml` is not a hand-maintained file — it is the **output of a live registrar** (`flux-agent.py index/backfill/stats/prune/promote/record`) that already implements several of the exact heraldic verbs Track 2 proposes building: `cmd_promote` (manual tier assignment — grant-adjacent), `cmd_prune` (stale-stub deletion — attainder-adjacent), `cmd_record` (usage/outcome tracking — augmentation-adjacent). The new "thin interverse plugin" would be a **fifth office of arms**, not a replacement for four, unless flux-agent.py is explicitly folded in, deprecated, or named as the extraction target.
- **Evidence:** `interverse/interflux/scripts/flux-agent.py` docstring line 4: "Manages the quality-tiered agent registry in .claude/agents/." `_scan_agents` (line 268) globs `agents_dir.glob("fd-*.md")` and keys `name = f.stem` — a fourth bare-string identity scheme, distinct from `agent-roster.md`'s markdown table rows, `agent-roles.yaml`'s `agents:` list-under-role structure, and intertrust's SQLite `agent TEXT`. The interflux skill listing (`interflux:flux-agent`) confirms this is an actively maintained lifecycle tool with "Lifecycle for review agents with quality tiers + domain indexing" — i.e., already doing identity-adjacent work the brainstorm assigns to a not-yet-built plugin.
- **Suggestion:** Before Track 2 scaffolds a new plugin, resolve whether flux-agent.py's `.index.yaml` + its command surface *is* the seed of the new registry (extend it) or a fifth roll to be attaindered alongside the other four. The brainstorm's own "Registry plugin boundary" open question ("identity + eligibility only, or also absorb lifecycle tiers (.index.yaml)") gestures at this but frames `.index.yaml` as passive data to absorb, not as a live generator with its own grant semantics to reconcile or retire.

### project-name-collision-is-the-same-defect-twice
- **Severity:** P2
- **Where:** `interverse/interspect/hooks/lib-interspect.sh` line 70-71 (`_interspect_project_name`, identical `basename(git-toplevel)` pattern, called from ~12 sites per grep)
- **What:** This is the identity-lens restatement of the settled path-discovery fact, surfaced because it is a *third* independent implementation of the same unguarded basename pattern (intertrace's `$MONOREPO_ROOT`, intertrust's `_trust_project_name`, interspect's `_interspect_project_name` — the latter two are even textually near-identical, with `_interspect_project_name` at line 153 aliased directly to `_trust_project_name` via `_interspect_project_name() { _trust_project_name "$@"; }` for backward compat). Three consumers independently reinvent an uncanonicalized project key; the registry track's federation path-discovery work (Open Question) will produce a *fourth*, canonical root-resolution mechanism unless it explicitly retrofits the two existing ones.
- **Evidence:** `interverse/intertrust/hooks/lib-trust.sh:153` — `_interspect_project_name() { _trust_project_name "$@"; }` (shim, confirming interspect deliberately delegates to intertrust's implementation rather than reconciling).
- **Suggestion:** When Track 1's federation path-discovery mechanism (upward-walk / marker-file, per Open Questions) is decided, name it as the canonical root-resolution primitive and add a follow-up item to point `_trust_project_name`/`_interspect_project_name` at it — otherwise the new mechanism becomes a *fifth* independent implementation rather than the reconciling one.

### flux-agent-scope-excludes-plugin-agents-by-construction
- **Severity:** P3
- **Where:** `interverse/interflux/scripts/flux-agent.py` line 274 (`for f in sorted(agents_dir.glob("fd-*.md")):`)
- **What:** `flux-agent.py`'s registrar only ever sees files physically present under a project's `.claude/agents/` (Project Agents, per `agent-roster.md`'s own taxonomy). fd-integration ships as a Plugin Agent from intertrace's `plugin.json`, not a project-local file — so even if Track 2 chose to extend flux-agent.py instead of building fresh, today's implementation would need a scope change before it could register fd-integration at all. This is a smaller, corollary point to the P1 above: it's the concrete reason "just extend flux-agent.py" isn't a free lunch.
- **Evidence:** `agent-roster.md` lines 9-13 define "Project Agents (.claude/agents/fd-*.md)" as a category distinct from "Plugin Agents (interflux)"; `flux-agent.py`'s glob targets exactly the Project Agent path pattern and nothing else.
- **Suggestion:** If Track 2 decides to extend flux-agent.py (per the P1 finding above) rather than build fresh, note the scope widening (plugin-shipped agents, not just `.claude/agents/`) as an explicit sub-task, not an assumed side effect.

## Verdict
The registry track undercounts its own fragmentation: it names one axis (agent identity across four files) but misses a second, mechanistically identical axis already live in the same subsystems — project identity, keyed the same unguarded `basename(git-toplevel)` way in both intertrust and interspect — and misses that `.index.yaml` is not inert data but the output of a fifth, already-functioning registrar (`flux-agent.py`) with its own grant/attainder-shaped verbs. A "single roll of arms" that resolves agent-name collisions while leaving project-name collisions and a live shadow registrar unresolved is not single; it is one roll larger than before extraction, with two joins now instead of one.

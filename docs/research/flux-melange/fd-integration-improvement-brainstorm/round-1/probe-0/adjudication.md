## Findings

### both-triggers-fire-composer-is-the-sharper-one
- **Severity:** P1
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` Open Questions, "Tracer invocation path" — "Leading candidate: agent-invoked, revisit if a second evidence-based agent appears."
- **What:** These are not competing claims about the same fact — they are two independent objections to the same conclusion, and both survive scrutiny. Finding (1) says the brainstorm never checked candidate (b)'s claimed engine-change cost against `launch.md` Step 2.0.4's Composer/`compose_dispatch` mechanism, which already does orchestrator-side pre-computation and injection into agent dispatch. Finding (2) says the stated deferral trigger ("revisit if a second evidence-based agent appears") is worded as a future condition but Track 2's registry work is explicitly scoped to onboard future evidence-based agents, so the trigger is either already satisfied or will be satisfied by the very track this brainstorm is committing to in the same document. Adjudicated: **finding (1) holds fully as written; finding (2) holds in substance but its stated premise is overclaimed** (see next finding). Neither is a taste call — both are checkable against repo state, and both check out as real gaps. The compounding effect is worse than either alone: the brainstorm defers re-evaluation to a trigger condition (2) whose target date is inside the same plan, while simultaneously failing to cost the alternative (1) against infrastructure that already exists. That is not "pilot-first, revisit later" — it is "defer the check to a moment that arrives immediately, without having done the check that was possible to do now."
- **Evidence:** `launch.md` lines 53-67 (Step 2.0.4): Composer's plan is "authoritative" when present and causes flux-drive to "skip Steps 2.0.5–2.1e" — a real, shipped orchestrator-injection precedent, confirmed via `docs/solutions/2026-03-03-c3-composer-dispatch-plan-generator.md` ("Go binary is the source of truth for dispatch plans... `compose_dispatch(sprint_id, stage)` returns JSON on stdout"). Track 2 in the brainstorm itself: "interflux triage consumes it as sole roster source; fd-integration migrates from its hand entry to become the registry's first external registration" and "Registration mechanism... staleness handling when a plugin is disabled/updated" (Open Questions) — i.e., the registry is explicitly built to onboard more external plugin agents, which is the condition (2) says would trigger revisiting candidate (b).
- **Suggestion:** Collapse the deferral into an explicit decision now rather than a future trigger: either (a) score candidate (b) against the actual Composer plan schema in this same document (does it have or could cheaply gain a per-agent evidence field?), or (b) state explicitly why Composer's agent-selection injection and evidence-payload injection are different extension points that don't transfer, so the "touches the engine" cost claim is falsifiable rather than asserted.

### second-consumer-claim-conflates-skill-with-agent
- **Severity:** P2
- **Where:** `docs/brainstorms/2026-07-16-fd-integration-improvement-brainstorm.md` Open Questions, "Tracer invocation path"; grounding at `interverse/intertrace/.claude-plugin/plugin.json` lines 14-20.
- **What:** Finding (2) asserts "/intertrace skill itself" is effectively "a second evidence-based agent" already using the tracer libs today. That's true at the level of "a second codepath calls the same shell functions" but imprecise at the level the Open Question's trigger condition was actually written at. `plugin.json` registers `agents: ["./agents/review/fd-integration.md"]` (singular) and `skills: ["./skills/intertrace"]` (singular, separately) — intertrace the skill is not a dispatchable, triage-eligible "evidence-based agent" in the roster/registry sense Track 2 is building toward; it's a user-invoked, bead-scoped post-ship tool with no `subagent_type`, no roster entry, and no trust-scoring row. Conflating the two weakens finding (2)'s argument by overstating how literally the trigger is already met — the honest version of the claim is narrower but still correct: the *tracer-consumer* count is 2 today (skill + agent) even though the *dispatchable-agent* count is still 1, and Track 2 is what will make it ≥2 dispatchable agents, at which point the deferred trigger genuinely fires.
- **Evidence:** `plugin.json` lines 14-20 — separate `skills` and `agents` arrays, one entry each. Prior verified finding (already settled this run): "the existing /intertrace skill already passes an undeclared $MONOREPO_ROOT into all three tracer scans... a live, unaudited instance in the sibling codepath slated for fusion" — this is the same disconnected-codepaths fact finding (2) is drawing on, correctly, as evidence of duplication; it just isn't evidence of a second *agent*.
- **Suggestion:** When resolving the "Tracer invocation path" Open Question, restate the trigger condition precisely: "revisit if a second **dispatchable** evidence-based agent appears" (already partially true via the skill/agent split, and will become fully true once Track 2 onboards more registry members) — and note that the skill/agent duplication is itself a Track 1 step 2 fusion target regardless of which invocation shape wins for fd-integration specifically.

## Verdict
Both prior findings hold — this is not an irreducible taste call. Finding (1) (Composer precedent) is unconditionally correct and the more load-bearing objection: it shows a concrete, already-shipped mechanism the brainstorm should have costed candidate (b) against and didn't. Finding (2) (deferred trigger already met) is correct in substance — Track 2 is explicitly building the mechanism that satisfies its own stated deferral condition — but its supporting premise overstates intertrace's skill as "a second evidence-based agent" when plugin.json shows it's a second tracer-consumer, not a second dispatchable agent; the argument survives on the Track-2-onboards-future-agents point alone. Net effect: "agent-invoked, revisit later" does not survive contact with either alternative and should be replaced with an explicit, scored decision inside this document rather than a future trigger.
